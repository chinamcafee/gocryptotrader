# 03 总体架构设计

> **实现状态（2026-10-11）**：本文档是设计原稿。已实现落点、两处实测偏差（588 合约口径 / KlineWeight 分档）与全部已知残余见 [实现后状态对照](实现后状态对照.md)；进度与缺口以 [`taskProgress/`](taskProgress/) 为准。

## 1. 架构原则

**在 GoCryptoTrader 单体内新增一个决策治理层，不新建交易引擎，不复制行情采集链路。**

三条硬边界：

1. **模型层只能读，不能写。** LLM 和 Jev 通过白名单只读工具获取事实，输出只能是结构化的**候选**和**判断**，永远不是订单。
2. **决策层只能提案，不能放行。** 决策合成产出 `HOLD / REVIEW / REJECT / ALLOW`，`ALLOW` 还必须过独立的硬风控引擎。
3. **执行层只能执行已授权的意图，不能解释策略。** 订单落地复用 `OrderManager.Submit` / `SubmitFakeOrder`，不新建下单路径。

## 3. 组件职责表（含"不允许做的事"）

沿用原项目 `docs/02-architecture.md` 的表格形式，明确写出每个组件的**禁止项**——这是防止职责蔓延的关键。

| 组件 | 职责 | **不允许做的事** |
| --- | --- | --- |
| **ConversationStore** | 持久化会话与消息；策略原文不可变；提供上下文窗口 | 不允许把原始模型文本直接当作交易指令；不允许存储明文模型密钥 |
| **PolicyExtractor** | 用 LLM 从时序对话文本提取**不可执行**的策略提案；缺硬边界时生成澄清问题 | 不允许自行发明风险限额/期限/动作/退出条件（缺失就用 `null` + 提问）；不允许在矛盾指令里静默选一个 |
| **StrategyVersionStore** | 冻结结构化策略版本；维护版本树；记录审批 | 不允许修改已冻结版本；不允许让模型输出改变已批准字段 |
| **CoverageRotator** | 全量 525 个 USDT-M 永续的两层轮询第一层：批量 ticker（1 次/周期）+ 增量 K 线（每合约 weight 1）+ 批量资金费；维护各合约指标状态供触发器扫描（04 §7.4） | 不允许轮询 orderbook（决策时按需拉）；不允许超过 `weightBudgetFraction`（默认 0.6×2400）；不允许在 halt 时继续触发分析 |
| **TriggerScheduler** | 按事件/节奏触发分析（1h 全量扫描 + 4h 决策确认，Q5b）；管理 UTC 滑动窗口频率预算 | 不允许在配对不 READY 时触发；不允许绕过预算 |
| **MarketSnapshotBuilder** | 从数据层构造有界快照（K 线窗口 + 指标 + 盘口 + 资金费 + 账户事实），打数据质量标签 | 不允许把过期数据标成新鲜；不允许升级质量标签；不允许包含未启用交易对 |
| **ReadOnlyToolSet** | 8 个白名单只读函数，作用域锁定到本次运行的账户/策略版本/市场 | **不允许暴露任何下单/撤单/改配置/改杠杆的函数**；不允许返回凭据或含敏感键的数据 |
| **LLMAdapter** | OpenAI 兼容 `chat/completions` 客户端；工具循环；schema 校验；预算与超时控制 | 不允许把未校验的模型输出传给下游；不允许无限轮次；不允许流式内容直接进入风控 |
| **JevAdapter** | `POST /v1/systemone` 客户端；纯函数请求构造器；严格响应校验；证据清单持久化 | 不允许给 Jev 与 LLM 不同的事实；不允许把 Jev 概率换算成收益或仓位 |
| **DecisionSynthesiser** | 按确定性规则合成 LLM 候选 + Jev 判断 → `HOLD/REVIEW/REJECT/ALLOW` | 不允许"模型说好就放行"；不允许在分歧时自行选边 |
| **RiskEngine** | 按用户批准的边界和账户事实判定是否允许提交，以及允许的**最大数量** | **不允许依赖模型"同意"来覆盖硬约束**；不允许读提示词；不允许有 I/O 副作用 |
| **ExecutionGateway** | 把 `ALLOW` 的意图转成 `order.Submit`，调 `OrderManager.Submit`/`SubmitFakeOrder`；管理订单状态机与 `UNKNOWN` 态 | 不允许解释交易策略；不允许新增未批准市场；不允许盲目重试 `UNKNOWN` |
| **AuditStore** | 记录每一次决策的完整链路、哈希、时间、费用 | 不允许 UPDATE/DELETE 事实表 |
| **ModelPairRegistry** | 管理 Provider Profile + Revision + 唯一启用配对 + 单调 `pair_epoch` + 能力探针 | 不允许同类型启用两个；不允许在探针失败时标 READY |
| **HaltController** | 全局/按市场紧急停机标志 | 不允许被模型或提示词清除 |

**LLM 决策落点（Q7 已定案 = A：新建 engine 子系统）**：`LLMManager` 作为独立 engine 子系统直接调 `OrderManager.Submit`/`SubmitFakeOrder`；回测器保持现状不改，仅作历史验证与对照基线（Q24）。模块布局如下。

**为什么 `llm/` 放顶层而不是 `engine/llm/`**：`docs/CODING_GUIDELINES.md` 要求"默认导出交易所类型/函数/方法，让仓库可当库用"。模型客户端是纯粹的 HTTP + schema 逻辑，不依赖引擎，放顶层包可以被独立测试、独立复用，也符合 `exchanges/kline`、`dispatch`、`communications` 这些既有顶层包的定位。

**为什么风控放 `engine/` 而不是 `llm/`**：风控需要读 ExchangeManager、OrderManager、账户事实，属于引擎内组件。而且它必须和 LLM 客户端**在不同包**，物理上隔离"模型"与"约束"。

## 5. 关键数据类型（Go 侧契约）

按编码规范：具名结构、指针使用、`XRequest`/`XResponse` 命名、时间 UTC、带引号数字用 `types.Number`、不许匿名 struct。

### 5.1 数据质量

原项目的 `FULL / TOP20_ONLY / MID_ONLY / PUBLIC_AGGREGATE / GAP / STALE / UNKNOWN` 是为"自建全深度节点"设计的。币安是中心化交易所，REST 直接给完整深度快照，**这个分级需要重新定义**（详见 [04-数据层](04-数据层-K线与指标.md) §5）：

```go
// DataQuality 描述快照中每一类事实的可信程度。
type DataQuality string

const (
    QualityExchangeREST    DataQuality = "EXCHANGE_REST"      // 直接来自币安 REST，权威
    QualityLocalTracked    DataQuality = "LOCAL_TRACKED"      // 本地 PositionController 跟踪，需对账
    QualityDatabaseCached  DataQuality = "DATABASE_CACHED"    // 数据库缓存的历史 K 线
    QualityDerived         DataQuality = "DERIVED"            // 由原始数据计算的指标
    QualityStale           DataQuality = "STALE"              // 超过新鲜度阈值
    QualityGap             DataQuality = "GAP"                // 区间有缺口
    QualityUnknown         DataQuality = "UNKNOWN"            // 无法确定
)
```

### 5.3 候选（LLM 输出）

对齐原项目 `CandidateSchema`，改成 Go：

```go
// Candidate 是 LLM 产出的交易候选。它只是提案，不是订单。
type Candidate struct {
    StrategyVersionID     uuid.UUID      `json:"strategyVersionId"`
    SnapshotID            uuid.UUID      `json:"snapshotId"`
    MarketID              string         `json:"marketId"`       // "Binance:usdtmarginedfutures:BTC_USDT"
    Action                CandidateAction `json:"action"`
    Thesis                string         `json:"thesis"`          // 1-2000 字符
    EvidenceRefs          []string       `json:"evidenceRefs"`    // 1-12 个，首个必须是 snapshotId
    Invalidation          string         `json:"invalidation"`    // 1-1000 字符，什么情况下这个判断失效
    SuggestedEntry        string         `json:"suggestedEntry"`  // 正十进制字符串或 "null"
    SuggestedExit         string         `json:"suggestedExit"`
    ProposedMaxNotionalUSD string        `json:"proposedMaxNotionalUsd"` // 仅上界建议
    Uncertainty           Uncertainty    `json:"uncertainty"`     // LOW / MEDIUM / HIGH
    TTLSeconds            int            `json:"ttlSeconds"`      // 5-300
}

type CandidateAction string
const (
    ActionOpenLong  CandidateAction = "OPEN_LONG"
    ActionOpenShort CandidateAction = "OPEN_SHORT"
    ActionReduce    CandidateAction = "REDUCE"
    ActionHold      CandidateAction = "HOLD"
    ActionReview    CandidateAction = "REVIEW"
)
```

**价格与金额一律用字符串**，不用 `float64`——这是原项目的明确规则（"decimal-string money, no JS float for signed values"），在 Go 侧对应 `types.Number` 或 `decimal.Decimal`。理由：金融数值的 JSON 序列化精度损失不可接受。

### 5.4 风控信封

```go
// RiskEnvelope 是用户批准的、不可变的数值边界。
type RiskEnvelope struct {
    MaxNewEntryIntents    int            // 窗口内最大新增风险意图数
```

> `nil` 的风险金额字段**阻止 LIVE 授权**，不是"无限制"。这条规则直接来自原项目（"`null` 风险金额字段阻止 `LIVE` 授权，不是'无限制'"）。

## 6. 决策流水线时序

```text
触发（K线收盘 / 手动 / 账户事件）
   │
   ├─► 1. 前置门禁（不调模型，零成本）
   │      · 运行模式允许？
   │      · 策略版本状态 == APPROVED 且在有效期内？
   │      · pair 状态 == READY？（否则 STALE_PAIR / INCOMPLETE / DEGRADED）
   │      · 探针新鲜度 OK？
   │      · halt 标志未置位？
   │      · 预算未耗尽？
   │      · 账户已对账？（accountReconciled）
   │      任一失败 → 记 decision_run(reason) 并退出，不消耗模型预算
   │
   ├─► 2. 构造 MarketSnapshot
   │      · 拉 K 线窗口（优先数据库，缺失走 REST）
   │      · 算指标（MACD / SMA / EMA）
   │      · 拉 ticker / orderbook / funding / 账户事实
   │      · 打质量与新鲜度标签
   │      · 新鲜度超阈值 → HOLD / MARKET_SNAPSHOT_STALE，退出
   │
   ├─► 3. LLM 工具循环（共同截止时间 90s，自动候选为 snapshot+10s）
   │      · round 0-2：tool_choice=auto，最多 4 次调用/轮
   │      · round 3：tool_choice=none，强制产出 JSON
   │      · 每次工具返回：作用域校验 → 时间校验（不许未来）→ 体积校验 → 敏感键扫描
   │      · 累计上限：4 轮 / 8 次工具调用 / 24000 token / 响应体 256KB / 内容 12000 字符
   │      · 超限 → 对应错误码 + HOLD
   │
   ├─► 4. Candidate schema 校验
   │      · 四个 ID 与 marketType 必须与上下文逐字一致
   │      · evidenceRefs 必须以 snapshotId 开头，且只引用已知 ref
   │      · 非 HOLD 必须有 ≥1 次工具调用 + 非 null entry/exit + 引用了工具证据
   │      · 服务端 safety() 门禁：质量不足 / 过期 / 证据未验证 → HOLD 或 REVIEW
   │
   ├─► 5. Jev 评估（同源事实）
   │      · 纯函数构造请求：state.evidence = LLM 实际看到的工具响应原文（有界）
   │      · 请求体上限 64 KiB UTF-8，超了整体拒绝（不静默截断）
   │      · 三个独立问题：candidate_action(choice) / evidence_quality(score) / strategy_alignment(noul)
   │      · 响应校验：分布求和 1±0.03、选中项 ≥ max−0.03、加权分一致 ±0.06、模型漂移
   │      · 持久化 inputEvidence 清单（requestSha256 / parsedResponseSha256 / candidateSha256 / 每条工具的 resultSha256）
   │      · 结束前再查一次 pair_epoch → 变了则 STALE_PAIR
   │
   ├─► 6. 决策合成（确定性规则）
   │      · 全局暂停 / 过期 / 未对账 / 数据过期 / 配对失效 → BLOCK
   │      · schema 或证据或作用域不完整 → REJECT
   │      · Jev 无响应 / 不完整 / 版本不匹配 → HOLD 或 REVIEW
   │      · LLM 与 Jev 方向实质性分歧，或 Jev 认为证据不足 → REVIEW / HOLD
   │      · 全部通过 → ALLOW（进入硬风控）
   │
   ├─► 7. 硬风控（纯函数，无 I/O，无模型）
   │      · 授权身份 / 数据质量与新鲜度 / 金额与敞口与日损 / 保证金模式 /
   │        成交保护（限价、滑点、最小深度、标记价偏差、最小名义额、精度）/
   │        频率窗口 / 仓位与委托冲突 / 系统状态
   │      · 重算数量：min(模型建议上限, 批准的单笔上限) → 按合约 step size 向下取整
   │      · 失败 → REJECT + 具体拒绝码 + 实际值 vs 允许值
   │
   ├─► 8. 预算占位 + 意图落库（单事务）
   │      · 写 OrderIntent + 预算 reservation + attempt + audit + outbox
   │
   ├─► 9. 提交前最终校验（PREPARED → SUBMITTING）
   │      · 重查 halt / 审批 / 市场授权 / 配对 / 探针 / 候选与 Jev 方向 / 全部硬风控码
   │      · 新鲜盘口 vs 批准的滑点上限
   │
   └─► 10. 执行
          · PAPER → OrderManager.SubmitFakeOrder
          · TESTNET / LIVE → OrderManager.Submit
          · 回执 → ACKED / REJECTED / UNKNOWN
          · UNKNOWN → 账户标记为需对账，暂停自动执行，绝不盲目重试
          · 推送通知（CommunicationsManager.PushEvent）
```

## 7. 部署拓扑：为什么不用原项目的七进程架构

`hyperliquid-auto-trader` 是 TypeScript monorepo，拆成 `web / api / worker / market-capture / book-rebuilder / executor / signer / ai-worker / wallet / ops` 十个应用，配 Postgres + Redis + ClickHouse + 对象归档。

**本方案不复制这套拓扑**，理由：

| 原项目的拆分动机 | 在 GoCryptoTrader 里是否成立 |
| --- | --- |
| 需要自建 Hyperliquid 非验证节点采集全深度（Ubuntu 24.04 / 16 vCPU / 128GB） | ❌ 不成立。币安 REST 直接给完整深度 |
| 需要 ClickHouse 存海量逐笔 + 盘口 diff（~100GB/天） | ❌ 不成立。低频策略只需要 K 线，SQLite/Postgres 足够 |
| 需要独立 signer 进程隔离钱包私钥（链上签名） | ⚠ 部分成立。币安是 API Key + HMAC 签名，不是私钥签名；GoCryptoTrader 已有配置加密 |
| 需要 ai-worker 进程隔离模型密钥 | ✅ 成立。但可以降级为**包级隔离 + 独立密钥文件** |
| React Web 控制台 | ⚠ 待决策（见 OPEN-QUESTIONS Q21） |

**采用的拓扑**：

```text
┌─────────────────────────────────────────────┐
│  gocryptotrader 进程（单体）                 │
│  ├─ 现有全部子系统                           │
│  ├─ LLMManager 子系统                        │
│  │   ├─ llm/openai  （密钥从 vault 解出）     │
│  │   ├─ llm/jev     （密钥从 vault 解出）     │
│  │   ├─ ReadOnlyToolSet                      │
│  │   ├─ DecisionSynthesiser                  │
│  │   └─ RiskEngine                           │
│  └─ gRPC 9052 / REST 9053                    │
└──────────────────┬──────────────────────────┘
                   │ TLS + Basic Auth（127.0.0.1）
      ┌────────────┴────────────┐
      ▼                         ▼
┌──────────────┐        ┌──────────────────┐
│ gctcli llm   │        │ 可选 Web UI      │
│ （终端对话）  │        │ （待决策 Q21）   │
└──────────────┘        └──────────────────┘
```

**保留的隔离手段**（不靠进程边界）：

1. **包边界**：`llm/` 包不 import `engine/`；`engine/llm_risk.go` 不 import `llm/openai`。风控在编译期就拿不到模型客户端。
2. **接口边界**：LLMManager 通过窄接口访问引擎（沿用 `iExchangeManager` / `iCommsManager` 的模式，`engine/subsystem_types.go:44-52`），工具集只暴露查询方法。
3. **密钥边界**：模型密钥不放 `config.json`，放独立 vault 文件（0600 权限），只有 `llm/secrets` 能解。见 [09-数据存储与配置](09-数据存储与配置.md) §5。
4. **类型边界**：模型输出是 `*Candidate`（有 schema 校验），不是 `*order.Submit`。两者之间隔着 `DecisionSynthesiser` + `RiskEngine` 两层，**没有直接转换路径**。

**如果后续需要更强隔离**（例如多用户、或不想让模型 HTTP 客户端和交易进程同生共死），可以把 `llm/` 抽成独立的 `gct-ai-worker` 进程，通过 Unix socket 通信——这正是原项目 `HAT_AI_WORKER_SOCKET` 的做法。目录结构已经为此预留：`llm/` 不依赖 `engine/`，可以整体搬走。**已定案（Q22 = A 包级隔离）**：部署目标为自己的 Mac（单机单用户），故首期采用包级隔离 + 独立 `llm-vault`；若未来迁到服务器或多用户环境，升级为独立 `gct-ai-worker` 进程（`llm/` 整体抽出，密钥结构不变）。

## 10. 失效与降级

沿用原项目的失效矩阵思路（`docs/06-security-operations.md` §7），针对本项目调整：

| 失效 | 影响 | 降级行为 |
| --- | --- | --- |
| LLM 端点不可用 | 无法产生新候选 | 停止模型驱动的新开仓；**已批准的确定性保护性退出仍可运行**（不依赖模型）；推送告警 |
| Jev 端点不可用 | 无法完成双模型评估 | 同上。所有决策收敛到 `HOLD / JEV_UNAVAILABLE` |
| 配对被切换 | 进行中的决策失效 | `pair_epoch` 递增 → 旧配对任务标 `STALE_PAIR` → 运行中策略暂停 → 已批准授权失效，需重新审批 |
| 币安限频 `-1003` | 数据拉取失败 | 快照标 `GAP` → 强制 HOLD；内置限频器（`-ratelimiter`，默认开）会自动退避 |
| 时钟漂移 `-1021` | 鉴权请求全失败 | 订单进 `UNKNOWN`/`REJECTED`，账户标记需对账，暂停自动执行 |
| 数据库不可用 | 审计无法落库 | **fail-closed**：不允许产生新决策（没有审计的决策是不可接受的） |
| 数据过期 | 快照不新鲜 | 强制 HOLD，不调 Jev，不消耗预算 |
| 预算耗尽 | 不再调模型 | 停止自动分析；手动对话提示预算状态 |
| 紧急停机 | 全部停止 | 阻止新开仓 + 暂停策略 + 撤销机器人挂单（可选显式 reduce-only 平仓） |
