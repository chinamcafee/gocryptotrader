# 07 策略与自动决策引擎

> **实现状态（2026-10-11）**：本文档是设计原稿。已实现落点、两处实测偏差（588 合约口径 / KlineWeight 分档）与全部已知残余见 [实现后状态对照](实现后状态对照.md)；进度与缺口以 [`taskProgress/`](taskProgress/) 为准。

本文定义从"用户的一句话"到"币安上一笔真实订单"的完整链路，重点是**硬风控**——这是本方案必须完全自建的部分（见 [02-现状盘点](02-gocryptotrader现状能力盘点.md) §5.2：GoCryptoTrader 的订单管理器限额配置在本 fork 里未接线）。

## 1. 策略生命周期

沿用原项目（`docs/04-strategy-ai.md`）：

```text
DRAFT
  │  用户自然语言输入，可反复编辑
  ▼
NEEDS_CLARIFICATION ◄────┐
  │  PolicyExtractor 发现缺硬边界或矛盾  │ 用户补充
  │  生成 clarifyingQuestions           │
  └────────────────────────────────────┘
  ▼
READY_FOR_REVIEW
  │  条款完整，等待用户审阅
  ▼
READY_FOR_APPROVAL（冻结）
  │  生成不可变的 reviewable-v1 结构化版本
  │  tradeAuthorized 恒为 false
  ▼
APPROVED ──── 用户逐版限时批准，绑定 pair_epoch + risk_envelope_hash
  │
  ▼
RUNNING ────► PAUSED（用户暂停 / 配对失效 / halt）
  │              │
  │              └──► RUNNING（恢复，需重新审批如果授权已过期）
  ▼
EXPIRED（超过 valid_until）
REVOKED（用户撤销）
```

**关键不变量**：

1. **冻结后不可变。** `READY_FOR_APPROVAL` 之后，策略版本的任何字段都不能改。要改就"继续这版"→ 复制成新 DRAFT → 走完整流程。
2. **一个版本一次审批。** 审批绑定版本 ID，不能复用。
3. **审批最长 7 天。** `validMinutes` 1-10080。
4. **模型不能改任何已批准字段。**

### 2.1 `reviewable-v1` 冻结契约

原项目的 `ReviewablePolicySchema` 关键字段：

```text
state: 'READY_FOR_APPROVAL'
tradeAuthorized: literal(false)        ← 类型层面恒为 false
sourceVersionId, sourceProposalId, sourceHash, proposalHash
account, network, mode (TESTNET | LIVE)
marketScopes: 1-8 个，唯一
validFrom / validTo（≤7 天）
risk（含 maxAccountInventoryAgeMs ∈ {5000, 10000} 可选）
maxNewRiskIntents ≤ 5                  ← 硬上限，不是默认值
pairEpoch, llmRevisionId, jevRevisionId
perp scope ⇒ 必须有杠杆上限
```

**本方案完整继承**，特别注意：

- `tradeAuthorized: literal(false)` —— 在 Go 侧用一个只有 `false` 值的具名类型 + 校验，任何试图设成 true 的代码路径都编译不过或校验失败
- `maxNewRiskIntents ≤ 5` 是**硬上限**，用户不能在策略里写 50
- **永续市场必须有 `maxLeverage`**，null 就不给批准

### 2.2 哈希绑定

审批时计算并存储：

```text
risk_envelope_hash = SHA-256(canonical_json(riskEnvelope))
strategy_hash      = SHA-256(canonical_json(整个冻结版本，去掉 approval 字段))
```

`canonical_json` 必须是**确定性序列化**：键排序、无多余空白、数字用固定精度字符串。否则同样的语义会算出不同哈希。

**用途**：运行时每次决策前重算 `risk_envelope_hash` 与审批记录比对。不一致 → `RISK_ENVELOPE_MISMATCH` → 阻断。这防止了任何路径（数据库直接改、迁移 bug、并发写）悄悄改了限额。

## 3. 市场授权（逐市场）

原项目：`market_trade_grants` 表，≤30 天，逐市场，撤销会级联到审批。

> 可交易市场须逐个审批，市场发现本身不授予交易权限。

```sql
CREATE TABLE market_trade_grants (
    id            TEXT PRIMARY KEY,
    account_id    TEXT NOT NULL,
    network       TEXT NOT NULL,
    market_id     TEXT NOT NULL,          -- Binance:usdtmarginedfutures:BTC_USDT
    granted_by    TEXT NOT NULL,
    granted_at    TEXT NOT NULL,
    valid_until   TEXT NOT NULL,          -- ≤30 天
    revoked_at    TEXT,
    revoked_by    TEXT,
    revoke_reason TEXT,
    UNIQUE (account_id, network, market_id, granted_at)
);
```

**级联规则**：撤销一个市场的授权 → 所有引用该市场的**策略审批立即失效** → 相关运行中策略暂停 → 该市场的挂单进入撤销计划。

**与 gocryptotrader 的关系**：市场授权是**独立于** `currencyPairs.enabled` 的第二道闸。一个交易对可以在 `enabled` 里（能查行情）但没有交易授权（不能下单）。这实现了"看盘 ≠ 能交易"。

## 4. 决策合成

见 [06-Jev接入层](06-Jev接入层-SystemOne.md) §7 的分诊规则。产出 `HOLD / REVIEW / REJECT / ALLOW`。

**只有 `ALLOW` 进入硬风控。** 但注意 [06](06-Jev接入层-SystemOne.md) §7 的最后一条：即使 LLM 和 Jev 完全一致，合成结果也是 `REVIEW / AWAITING_HARD_RISK_AND_APPROVAL`，硬风控通过后才升为 `ALLOW`。

**换句话说：`ALLOW` 只能由硬风控引擎产出，决策合成层永远不产出 `ALLOW`。** 这是职责隔离的关键。

## 5. 硬风控引擎

### 5.1 设计约束

```go
// Evaluate 是纯函数：不做 I/O，不查数据库，不调网络，不接触模型。
// 所有事实由调用方在外部查好后作为参数传入。
func Evaluate(in RiskInput) RiskResult

type RiskInput struct {
    CheckVersion    string              // "new-risk-v1"
    Authorization   AuthorizationFacts  // 审批 + 市场授权 + 有效期 + 哈希
    DataFacts       DataFacts           // 快照新鲜度 + 质量 + 年龄
    Candidate       *Candidate
    JevAssessment   *JevAssessment
    AccountFacts    AccountFacts        // 交易所实时查的，不是本地缓存
    PositionFacts   []PositionFact      // 已有仓位 + 未成交开仓委托
    Envelope        RiskEnvelope        // 从审批记录读，哈希已校验
    FrequencyFacts  FrequencyFacts      // 滑动窗口计数
    ContractSpec    ContractSpec        // tick size / step size / 最小名义额
    SystemFacts     SystemFacts         // halt 标志 / 时钟 / 数据库 / 配对状态
    MarketFacts     MarketFacts         // 盘口 / 标记价 / 资金费率
}

type RiskResult struct {
    Verdict       Verdict            // ALLOW / REJECT / REVIEW
    CheckCodes    []CheckCode        // 每项检查的结果
    ComputedQty   string             // 重算后的数量（十进制字符串）
    ComputedNotionalUSD string
    Rejections    []Rejection        // 码 + 实际值 vs 允许值
}
```

**为什么必须纯函数**：

1. 可测试——固定输入固定输出，不需要 mock
2. 可审计——`CheckCodes` 完整记录每项检查，能回答"为什么拒了"
3. 不可被污染——它拿不到模型客户端，物理上无法"问模型的意见"
4. 可重放——同样的 `RiskInput` 永远得到同样的 `RiskResult`

### 5.2 检查清单

完整继承原项目 `docs/04-strategy-ai.md` §6 的硬风控清单，按币安永续具体化：

#### A. 授权类

| 码 | 检查 | 拒绝条件 |
| --- | --- | --- |
| `RISK_AUTH_MISSING` | 存在有效审批 | 无审批记录 |
| `RISK_AUTH_EXPIRED` | `now ∈ [validFrom, validUntil]` | 超期 |
| `RISK_AUTH_MODE_MISMATCH` | 审批的 mode 与当前运行模式一致 | LIVE 审批用在 TESTNET 或反之 |
| `RISK_AUTH_ACCOUNT_MISMATCH` | 审批的 account 与目标账户一致 | 不一致 |
| `RISK_MARKET_NOT_GRANTED` | 该市场有有效的 `market_trade_grants` | 无授权或已撤销或过期 |
| `RISK_MARKET_NOT_IN_SCOPE` | 该市场在审批的 `marketScopes` 里 | 不在 |
| `RISK_ACTION_NOT_ALLOWED` | 候选 action 在审批的 `allowedActions` 里 | 不在 |
| `RISK_ENVELOPE_MISMATCH` | 重算的 `risk_envelope_hash` 与审批一致 | 不一致 |
| `RISK_PAIR_EPOCH_MISMATCH` | 当前 `pair_epoch` 与审批时一致 | 不一致（`STALE_PAIR`） |
| `RISK_JEV_MANIFEST_NOT_BOUND` | Jev 输入清单状态 == `MANIFEST_BOUND` | 其它状态 |

#### B. 数据类

| 码 | 检查 | 拒绝条件 |
| --- | --- | --- |
| `RISK_SNAPSHOT_STALE` | 快照年龄 ≤ 阈值 | 超时 |
| `RISK_SNAPSHOT_QUALITY` | 关键事实质量为 `EXCHANGE_REST` / `DATABASE_CACHED` | `GAP` / `STALE` / `UNKNOWN` |
| `RISK_ACCOUNT_INVENTORY_STALE` | 账户事实年龄 ≤ `maxAccountInventoryAgeMs`（5000 或 10000） | 超时 |
| `RISK_CANDLE_GAP` | 指标计算窗口无 `addPadding` 补的零值 | 有缺口 |
| `RISK_ORDERBOOK_INVALID` | 盘口未交叉/未锁定（无 `ErrBidEqualsAsk`） | 无效 |
| `RISK_ACCOUNT_NOT_RECONCILED` | `accountReconciled == true` | false |

#### C. 资金类

| 码 | 检查 | 拒绝条件 |
| --- | --- | --- |
| `RISK_ORDER_NOTIONAL_EXCEEDED` | 单笔名义额 ≤ `maxOrderNotionalUsd` | 超过 |
| `RISK_TOTAL_EXPOSURE_EXCEEDED` | 统一敞口 ≤ `maxTotalExposureUsd` | 超过 |
| `RISK_DAILY_LOSS_EXCEEDED` | UTC 日损 ≤ `maxDailyLossUsd` | 超过 |
| `RISK_DAILY_LOSS_UNKNOWN` | 日损基线可计算 | 基线缺失 → `UNKNOWN` → 拒 |

**日损基线实现（Q11 已定案 = B：简化版 + 缺失即拒）**：每日 UTC 00:00 记一次权益快照（`llm_day_start_inventory`）；每小时从 `UAccountIncomeHistory` 的 TRANSFER 类型校正外部划转（`llm_external_flows`，该端点权重 30 故每小时一次）；日损 = 基线 ± 划转 − 当前权益。**基线缺失或划转识别失败 → `RISK_DAILY_LOSS_UNKNOWN` → 拒绝开仓**。触发 `maxDailyLossUsd` 后置 FULL halt 且**人工解除**（Q8c）。
| `RISK_LEVERAGE_EXCEEDED` | 目标杠杆 ≤ `maxLeverage` | 超过 |
| `RISK_INSUFFICIENT_COLLATERAL` | 可用保证金 ≥ 所需初始保证金 + 手续费缓冲 | 不足 |
| `RISK_MARGIN_TYPE_UNEXPECTED` | 实际保证金模式与审批假设一致 | 不一致 |
| `RISK_COLLATERAL_MODE_HEDGE` | 持仓模式为单向 | **双向 → 拒**（wrapper 不传 positionSide） |
| `RISK_FUNDING_UNAVAILABLE` | 需要时能取到资金费率 | 取不到（若审批要求考虑资金费） |

**统一敞口公式**（原项目）：

```text
exposure = 已有仓位的保守名义额
         + 未成交开仓委托的剩余名义额
         + 拟下新委托的名义额
```

"保守名义额"：多头用 `max(开仓价, 当前标记价) × 数量`，空头用 `max(开仓价, 当前标记价) × 数量`——即取更不利的那个，避免低估敞口。

**UTC 日损基线**（原项目 `docs/19-day-start-inventory.md` / `docs/21-utc-day-usd-loss.md`）：

```text
dayStartEquity = UTC 00:00 时刻的账户权益（从固定样本 + 封存的 FILL/FUNDING/LEDGER 窗口重建）
adjustedBaseline = dayStartEquity ± 外部资金流入流出
currentEquity = 当前权益（含未实现盈亏 + 已实现手续费 + 资金费）
dailyLoss = adjustedBaseline − currentEquity
```

**基线缺失 → `UNKNOWN` → 拒绝**。原项目明确："reaches cap or source failure → preflight rejects"。

> **本方案的简化**：原项目为这块写了 `docs/17` 到 `docs/21` 加 `docs/26`-`docs/32` 共十几篇文档和 20 多个迁移，因为它要处理链上 USDC/USD 汇率、外部本金中性化、独立历史源等。**币安是中心化交易所，USDT 余额和权益直接由 `/fapi/v2/balance` 和 `/fapi/v2/account` 给出，不需要外部汇率源。** 这块可以大幅简化：每日 UTC 00:00 记一次 `GetFuturesPositionSummary` + 余额快照作为基线，之后每小时校正一次外部划转。**这是本方案相对原项目最大的简化点之一。见 OPEN-QUESTIONS Q11。**

#### D. 成交保护类

| 码 | 检查 | 拒绝条件 |
| --- | --- | --- |
| `RISK_SLIPPAGE_EXCEEDED` | 按当前盘口估算的滑点 ≤ `maxSlippageBps` | 超过 |
| `RISK_SPREAD_TOO_WIDE` | 买卖价差 ≤ 阈值 | 超过 |
| `RISK_INSUFFICIENT_DEPTH` | 目标名义额在 `depthLevels` 内可成交 | 不足 |
| `RISK_MARK_PRICE_DEVIATION` | 最新价与标记价偏差 ≤ 阈值 | 超过（异常波动） |
| `RISK_INDEX_DEVIATION` | 标记价与指数价偏差 ≤ 阈值 | 超过 |
| `RISK_BELOW_MIN_NOTIONAL` | 名义额 ≥ 合约最小名义额 | 低于 |
| `RISK_PRECISION_INVALID` | 价格符合 tick size，数量符合 step size | 不符 |
| `RISK_AMOUNT_BELOW_MIN` | 数量 ≥ 合约最小数量 | 低于 |
| `RISK_ORDER_TYPE_NOT_ALLOWED` | 订单类型在允许集合（LIMIT / MARKET / STOP_MARKET） | 不在 |
| `RISK_FUNDING_SETTLEMENT_IMMINENT` | 距离资金费结算 > N 分钟（若策略要求避开） | 太近 |

#### E. 频率类

| 码 | 检查 | 拒绝条件 |
| --- | --- | --- |
| `RISK_NEW_RISK_WINDOW_EXCEEDED` | 滚动 300 分钟窗口内新增风险意图 ≤ 5（账户级） | 超过 |
| `RISK_VERSION_WINDOW_EXCEEDED` | 该策略版本窗口内计数 ≤ 审批值 | 超过 |
| `RISK_MARKET_COOLDOWN` | 该市场距上次开仓 > 冷却期 | 未过 |
| `RISK_ALL_ORDER_BUDGET` | 账户级全部订单预算（含撤单）未耗尽 | 耗尽 |
| `RISK_REDUCE_STORM` | Reduce-only 通道的防风暴限额未耗尽 | 耗尽 |

**Reduce-only 平仓和撤单不消耗新增风险预算**，但有独立的防风暴限额（防止模型反复开平刷手续费）。

所有窗口用 **UTC 滑动窗口**，计数持久化到数据库（不是内存，重启不能丢）。

#### F. 仓位与委托类

| 码 | 检查 | 拒绝条件 |
| --- | --- | --- |
| `RISK_UNKNOWN_ORDER_UNRESOLVED` | 该账户无未解决的 `UNKNOWN` 订单 | 有 → 拒 + 要求对账 |
| `RISK_CONFLICTING_RESTING_ORDER` | 无与新意图冲突的挂单 | 有 |
| `RISK_MISSING_PROTECTIVE_EXIT` | `requiresProtectiveExit == true` 时，开仓必须同时提交保护性止损 | 缺失 |
| `RISK_UNRECONCILED_PARTIAL` | 无未对账的部分成交 | 有 |
| `RISK_MAX_CONCURRENT_POSITIONS` | 开仓后仓位数 ≤ `maxConcurrentPositions` | 超过 |
| `RISK_OPPOSING_POSITION` | 单向持仓下，反向开仓会被视为减仓 —— 必须明确意图 | 意图不明 |

**最后一条很重要**：币安单向持仓模式下，有多仓时下 SELL 单是**减仓**而不是开空。模型给出 `OPEN_SHORT` 但账户有多仓时，实际效果是平多。风控必须检测这种情况并要求显式确认，或者自动改判为 `REDUCE`。

#### G. 系统类

| 码 | 检查 | 拒绝条件 |
| --- | --- | --- |
| `RISK_HALTED` | 全局/按市场 halt 标志未置位 | 置位 |
| `RISK_MODE_NOT_PERMITTED` | 当前运行模式允许下单 | `READ_ONLY` / `SHADOW` |
| `RISK_LIVE_NOT_UNLOCKED` | LIVE 模式需 `acknowledgeLiveTrading == "I_UNDERSTAND"` | 未解锁 |
| `RISK_MODEL_BUDGET_EXHAUSTED` | 模型预算未耗尽 | 耗尽 |
| `RISK_DATABASE_UNAVAILABLE` | 审计能落库 | 不能 |
| `RISK_CLOCK_DRIFT` | 本地时钟与币安服务器偏差 < 1000ms | 超过（会触发 `-1021`） |
| `RISK_RATE_LIMIT_DEGRADED` | 币安限频状态健康 | 接近上限 |
| `RISK_PAIR_NOT_READY` | 模型配对 `READY` | `INCOMPLETE` / `DEGRADED` / `STALE_PAIR` |
| `RISK_SUBSYSTEM_DOWN` | OrderManager / ExchangeManager 在运行 | 停了 |

原项目的表述：这些"**均不能被提示词忽略**"。

### 5.3 数量重算

**模型给的 `proposedMaxNotionalUsd` 只是上界建议，不是下单数量。**（原项目："`proposedMaxNotionalUsd` 只给出模型建议的金额上界，不是下单数量"）

重算流程：

```text
1. notionalCap = min(candidate.proposedMaxNotionalUsd, envelope.maxOrderNotionalUsd)
   · 任一为 null → REJECT / RISK_ORDER_NOTIONAL_MISSING
2. 剩余敞口 = envelope.maxTotalExposureUsd − 当前统一敞口
   notionalCap = min(notionalCap, 剩余敞口)
3. 剩余日损额度 = envelope.maxDailyLossUsd − 当前 UTC 日损
   · 用 ATR 或止损距离估算"这笔单最多亏多少"
   · 若 估算最大亏损 > 剩余日损额度 → 按额度反推名义额上限
   notionalCap = min(notionalCap, 反推值)
4. 参考价 = 当前盘口的可成交价（不是最新成交价）
   · 买入用 ask 侧按 notionalCap 的成交均价
   · 卖出用 bid 侧
5. rawQty = notionalCap / 参考成交价
6. 按合约 step size **向下取整**（原项目："rounds quantity down by szDecimals"）
   qty = floor(rawQty / stepSize) × stepSize
7. 校验 qty ≥ 最小数量、qty × 参考价 ≥ 最小名义额
   · 不满足 → REJECT / RISK_BELOW_MIN_NOTIONAL
8. 重算实际名义额 = qty × 参考价
9. 用实际名义额重新跑一遍滑点检查（第 6 步的取整可能改变了深度消耗）
```

**向下取整是硬要求**——向上取整会超出批准的限额。

`ContractSpec` 从 `GetFuturesContractDetails`（`binance_wrapper.go:2790`）取，含 tick size、step size、最小名义额、合约乘数。

### 5.4 价格确定

| 订单类型 | 价格来源 |
| --- | --- |
| `LIMIT` | `candidate.suggestedEntry`，但必须按 tick size 取整，且必须在盘口合理范围内（买入 ≤ best ask × (1 + maxSlippage)，卖出 ≥ best bid × (1 − maxSlippage)） |
| `MARKET` | 不传价格（币安市价单不接受 price） |
| `STOP_MARKET`（保护性止损） | 由 `exitPolicy` 计算：`entryPrice − k × ATR` 或 `entryPrice × (1 − stopPct)`，按 tick size 取整 |

**`candidate.suggestedEntry` 为 null 时不允许开仓**（`CANDIDATE_INCOMPLETE` 已在合成层拦截）。

### 5.5 拒绝时的输出

原项目要求："REJECT（with which limit, actual vs allowed）"。每个拒绝必须带：

```go
type Rejection struct {
    Code        CheckCode  // RISK_TOTAL_EXPOSURE_EXCEEDED
    Message     string     // 人可读
    Actual      string     // "2450.00"
    Allowed     string     // "2000.00"
    Unit        string     // "USDT"
    Field       string     // "maxTotalExposureUsd"
}
```

并且**每次拒绝都推送通知**（`CommunicationsManager.PushEvent`，`base.Event{Type: "llm_risk_reject"}`）——用户需要知道系统在替他们挡什么。

### 5.6 硬风控开关目录（Q8d 定案：可开关、互不冲突、优先级高于提示词）

用户要求：额外硬约束**不做成固定清单**，而是一组独立开关，可随时打开/关闭；打开时优先级高于任何提示词与模型输出，关闭时该约束不生效。切换经配置或 RPC（`LLMSetRiskSwitch`），**每次切换写 `llm_audit_events`**。

| 开关 | 默认 | 触发时拒绝码 | 参数 |

### 6.3 订单状态机

沿用原项目（`docs/03-hyperliquid-integration.md`）：

```text
CANDIDATE
  → BLOCKED（风控拒绝）
  → REVIEW（转人工）
  → PREPARED（意图落库，单事务写 intent + reservation + attempt + audit + outbox）
  → SUBMITTING（提交前最终校验通过，已认领）
  → ACKED（交易所接受）
      → RESTING（挂单中，LIMIT）
      → PARTIALLY_FILLED
      → FILLED
      → CANCELED
  → REJECTED（交易所拒绝）
  → UNKNOWN（结果不明）
```

**`UNKNOWN` 的处理规则**（原项目的核心安全设计）：

- **永不盲目重试。** 因为不知道交易所那边到底成没成交，重试可能导致双倍仓位
- 账户立即标记 `RECONCILIATION_REQUIRED`
- 暂停该账户的自动执行
- 触发对账流程：用 `GetOrderInfo` / `GetOrders` / `GetFuturesPositionSummary` 查实际状态
- 推送紧急通知

**什么情况下会产生 `UNKNOWN`**：网络超时、`-1021` 时钟错误、进程崩溃在 `SUBMITTING` 中、币安返回非确定性错误。

**幂等键**：`ClientOrderID` 每次尝试唯一（原项目用 `cloid`，格式 `/^0x[0-9a-fA-F]{32}$/`）。币安支持 `newClientOrderId`，用它做幂等——同样的 clientOrderId 重复提交，币安会拒绝而不是重复下单。

### 6.4 精度问题（Q13 已定案 = A：decimal + 向下取整 + 容差 step）

`order.Submit.Amount` 和 `Price` 是 `float64`（`exchanges/order/order_types.go:46-117`）。这与原项目"decimal-string money, no JS float for signed values"的原则冲突。

**处理方式**：

1. 风控引擎内部**全程用 `decimal.Decimal`**（`shopspring/decimal`，已在 `go.mod`）
2. 只在最后构造 `order.Submit` 时转 `float64`
3. 转换前**先按 step size / tick size 取整**，保证 float64 能精确表示（币安的 step size 通常是 0.001、0.01、0.1、1 这类，float64 表示 0.001 有微小误差）
4. 转换后再用 `CheckOrderExecutionLimits` 校验一次（`OrderManager.Submit` 内部会做）

**为什么可以接受**：币安 API 本身接受浮点数的字符串形式，wrapper 内部会格式化。而且 `CheckOrderExecutionLimits` 会拦住不合规的值。风险在于极端情况下的 1 ULP 误差导致数量差一个 step——**用"向下取整后再减一个 step 的容差"来规避**（保守）。

**更彻底的方案**：给 `order.Submit` 加字符串字段。但这是改动核心类型，影响面大，**不建议在本项目范围内做**。**见 OPEN-QUESTIONS Q13。**

## 7. 保护性退出

原项目分两类：

| 类型 | 说明 | 有效期 |
| --- | --- | --- |
| **保护性退出授权**（protective exit） | 单次手动 GTC 单 | ≤10 分钟 |
| **条件退出计划**（conditional exit plan） | 止损/止盈，IOC | ≤7 天 |

原项目为此写了 migrations 0090-0099、0104、0113，包括数量分配账本、IOC 准备、提交检查、终态结算、自动消耗、运行时监督（5 秒心跳 / 15 秒过期）、跨期交接。

**本方案的简化**：

币安原生支持 `STOP_MARKET` 和 `TAKE_PROFIT_MARKET`（`binance_wrapper.go:896-940` 的类型映射），所以**不需要自己实现条件单监控**——把止损单直接挂到交易所即可。

```text
开仓流程（requiresProtectiveExit == true 时）：
  1. 提交开仓单（LIMIT 或 MARKET）
  2. 等成交确认（轮询 GetOrderInfo，最多 N 秒）
  3. 成交后立刻提交 STOP_MARKET 止损单，ReduceOnly = true
  4. 止损单价格 = entryPrice − k × ATR（或按 exitPolicy）
  5. 若第 3 步失败 → 立即市价平掉刚开的仓（fail-safe）
```

**止损距离（Q8b 已定案 = ATR 与固定百分比取较紧者）**：

```text
stop = entry − max(k × ATR(14), entry × p)      多头
stop = entry + max(k × ATR(14), entry × p)      空头
小额验证档：k = 1.5，p = 2%
```

按 tick size 取整后挂 `STOP_MARKET` + `ReduceOnly=true`。取较紧者保证：低波动时不被固定百分比放得太宽，高波动时不被 ATR 放得太宽。

**第 5 步是关键**：不能出现"有仓位但没止损"的状态。原项目的 `RISK_MISSING_PROTECTIVE_EXIT` 检查在这里落地。

**为什么不用原项目那套复杂的分配账本**：原项目要处理链上签名的互斥性、agent 钱包的 nonce、单执行器约束。币安是 API Key + HMAC，没有这些约束，而且原生支持 reduce-only 条件单。**这是本方案相对原项目的第二个大简化点。**

**仍然需要保留的**：

- 止损单的生命周期跟踪（挂上了没？被成交了没？被币安撤了没？）
- 跨重启的恢复（程序重启后要知道有哪些止损单在挂着）
- 与主仓位的关联（仓位平了，止损单要撤）

## 8. 紧急停机

原项目：HTTP halt 阻止新风险 + 暂停策略 + 撤销审批，但**不自动撤交易所挂单或平仓**（有界限的撤销计划 CLI 存在，仅合成验证）；**没有 un-halt API**。

**本方案设计**：

```go
type HaltController struct {
    // 三级 halt
    global    atomic.Bool   // 全局：阻止一切新开仓
    perMarket sync.Map      // 按市场：阻止该市场新开仓
    full      atomic.Bool   // 完全停机：阻止一切，包括 reduce-only
}
```

| 级别 | 触发 | 效果 |
| --- | --- | --- |
| `SOFT` | 用户手动 / 配对失效 / 数据长期过期 | 阻止新开仓，暂停策略，**允许 reduce-only 平仓和保护性止损** |
| `MARKET` | 某市场异常（价格剧烈偏离、资金费率异常） | 该市场阻止新开仓，允许平仓 |
| `FULL` | 用户显式紧急停机 / 时钟漂移 / 数据库不可用 / 账户未对账 | 阻止一切模型驱动动作；**确定性保护性止损仍可运行**（不依赖模型） |

**触发后的动作序列**：

```text
1. 置 halt 标志（原子操作，立即生效）
2. 暂停所有 RUNNING 策略 → PAUSED
3. 撤销所有有效审批（可选，用户确认）
4. 撤销机器人下的挂单（复用 OrderManager.CancelAllOrders，engine/order_manager.go:148）
   · 只撤 ClientOrderID 带机器人前缀的，不动用户的单
5. （FULL 级别，需用户显式二次确认）reduce-only 平掉全部仓位
6. 推送通知到所有已启用通道
7. 写 audit_event
```

**un-halt 必须显式**：原项目"没有 un-halt API"是一个缺陷（停机后只能重启进程）。本方案提供 `ClearHalt` RPC，但要求：

- 操作者重新认证
- 清除原因必须记录
- 清除后**策略不自动恢复**，需要用户逐个重新启用
- 清除后**已撤销的审批不自动恢复**，需要重新审批

**为什么第 4 步只撤机器人的单**：用户可能同时在币安 App 上手动操作。撤掉用户的单是不可接受的副作用。用 `ClientOrderID` 前缀（如 `gct-llm-`）区分。

## 9. 对账

原项目的现状：只有有界的部分审计（`BOT_ORDERS_ONLY`、仓位/现货/永续原始 USDC 三差额），完整的双向手续费/资金费/现金流对账、统一账户和组合保证金建模**未完成**（`accountReconciled=false` 到处都是）。

**本方案的最小可行对账**：

```text
每 5 分钟（可配）：
  1. 取本地所有机器人订单（ClientOrderID 前缀匹配）
  2. 调 GetOrders / GetOrderInfo 查交易所实际状态
  3. 比对：状态、成交数量、成交均价、手续费
  4. 调 GetFuturesPositionSummary 查交易所实际仓位
  5. 比对本地 PositionController 的仓位
  6. 差异 → 记 delta_audit + 置 accountReconciled = false + 暂停自动执行 + 告警
  7. 无差异 → accountReconciled = true（有效期到下次对账）
```

**币安特有的对账数据源**：

- `UAccountTradesHistory`（成交历史）
- `UAccountIncomeHistory`（收入历史：手续费、资金费、已实现盈亏）—— 权重 30，别频繁调
- `UAccountInformationV2`（账户信息）
- `UPositionsInfoV2`（仓位信息）
- `UAccountForcedOrders`（强平单）—— **这个很重要**，能检测到被强平

（全部在 `binance_ufutures.go:749-949`）

**`accountReconciled` 是硬门禁**：`RISK_ACCOUNT_NOT_RECONCILED` 会拒绝一切新开仓。这直接实现了底线 4"成交与仓位以交易所查询和对账为准"。

## 10. 与回测器的关系

`backtester` 是本仓库唯一的策略框架，且支持实盘数据 + 真实下单（`LiveData{RealOrders: true}`）。两种集成方式：

### 方式 A：LLM 层独立，回测器只用于历史验证（推荐）

```text
LLMManager（新增引擎子系统）──► OrderManager.Submit / SubmitFakeOrder
backtester（现有，不改）      ──► OrderManager.Submit / SubmitFakeOrder（实盘模式）
```

两者共享 OrderManager，但互不依赖。回测器用于**验证策略思路的历史表现**（用 `.strat` 配置 + 数据库 K 线），LLMManager 用于**实时决策**。

优点：职责清晰，改动最小，回测器的既有能力（滑点模拟、手续费、统计）可以直接用来评估"如果用固定规则会怎样"，作为 LLM 决策的对照基线。

### 方式 B：LLM 作为一个 backtester 策略插件

实现 `strategies.Handler` 接口（`backtester/eventhandlers/strategies/strategies_types.go:20-31`），通过 Go plugin 加载（`backtester/plugins/strategies/loader.go:16`），在 `OnSignal` 里调 LLM。

优点：复用回测器的数据管道、组合管理、统计报告；能在历史数据上"回放" LLM 决策（虽然模型输出不可重放）。

缺点：

- 回测器的 `data.Handler` **不提供 ticker/orderbook**（`backtester/README.md` 列为 planned），而 LLM 需要盘口做滑点估算
- 回测器的策略接口是"每个数据事件调一次 `OnSignal`"，与 LLM 的"事件触发 + 截止时间"模型不匹配
- 回测器是独立进程（`backtester/main.go`），跑实盘时和主 bot 是两个进程，共享 OrderManager 需要额外接线
- 对话式交互无法自然嵌入回测器的事件循环

**已定案（Q7 = A）：方式 A。** 回测器保留作为"历史验证工具"，LLM 决策走独立的引擎子系统。**这个选择需要用户确认，见 OPEN-QUESTIONS Q7。**
