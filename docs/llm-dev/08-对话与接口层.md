# 08 对话与接口层

> **实现状态（2026-10-11）**：本文档是设计原稿。已实现落点、两处实测偏差（588 合约口径 / KlineWeight 分档）与全部已知残余见 [实现后状态对照](实现后状态对照.md)；进度与缺口以 [`taskProgress/`](taskProgress/) 为准。

本文定义用户如何与系统交互：对话分析、策略下达、审批、监控、干预。

## 1. 交互形态选择

原项目是 React 19 + Ant Design 6/X 的 Web 控制台（5 个路由、30 个面板组件、Playwright 验收），loopback-only。

GoCryptoTrader 是**无 UI 的守护进程**，交互入口是 gctcli（终端）+ gRPC + REST 网关。

三种可选形态：

| 形态 | 工作量 | 对话体验 | 审批体验 | 监控体验 |
| --- | --- | --- | --- | --- |
| **A. gctcli 优先**（终端交互） | 小 | 可用（REPL 式） | 可用（结构化输出 + 确认提示） | 弱（要反复查） |
| **B. REST 优先 + 现有工具** | 中 | 需外部客户端（curl / Postman / 自建脚本） | 同 | 弱 |
| **C. 独立 Web UI** | 大 | 好（流式、Markdown、图表） | 好（可视化 diff、倒计时） | 好（实时面板） |

**已定案（Q21 = C）：Web UI 纳入首期交付**，且**原项目（hyperliquid-auto-trader）的 React 19 + AntD X 前端可复用/改造**，M7 工作量从 4-6 周降到 **2-3 周**（主要改数据源：Fastify `/v1/*` → gocryptotrader REST 网关 9053；字段映射：camelCase + `pair` 对象）。

- **主交互 = Web UI**：对话工作区（AntD X Bubble/Sender/Conversations/Sources + 真流式，Q14=C）、K 线图叠加 MACD/EMA/SMA/RSI/布林（Lightweight Charts）、策略版本树与 diff、审批倒计时、决策血缘可视化、Provider 配置页、健康页
- **gctcli `llm` 子命令族仍保留**：作为无 UI 兜底、自动化脚本与 CI 验收入口（M3 先交付，Web UI 在其后）
- **关键设计约束不变**：REST/gRPC 接口从第一天就按"UI 无关"设计，前端只消费 `/v1/*`，不直连引擎

原项目的 UI 规格（`docs/07-ui-delivery.md`）可以作为 C 阶段的需求输入：信息架构（顶部环境栏 / 左侧市场列表 / 中间图表+盘口+成交 / 右侧策略工作区 / 底部标签页 / 独立页面：策略档案、模拟回放、模型配置、钱包设置、监控备份）、设计 token（背景 `#0B111B`、面板 `#111B28`、涨 `#25B49A`、跌 `#EC6A70`、焦点 `#5B9CFF`）、Ant Design X 的对话组件（Bubble / Sender / Conversations / Sources）、TradingView Lightweight Charts。

**见 OPEN-QUESTIONS Q21。**

## 2. 会话模型

### 2.1 两类会话，两条代码路径

| 类型 | 提示词版本 | 输出 | 产生 decision_run | 产生 chat_message | 能触发写操作 |
| --- | --- | --- | --- | --- | --- |
| **分析对话**（chat） | `chat-analysis-v1` | 自由文本 + 证据引用 | ❌ | ✅（含工具转录） | ❌ |
| **策略提取**（policy） | `policy-proposal-v1` | 结构化 `PolicyProposal` JSON | ❌ | ✅ | ❌（只产出草案） |
| **决策分析**（analysis） | `analysis-readonly-v1` | 结构化 `Candidate` JSON | ✅ | ❌ | ❌（候选不是订单） |

**三者共享同一个只读工具集**，但走不同的代码路径和提示词。这是 [05-LLM接入层](05-LLM接入层-OpenAI兼容.md) §6.3 说的"两个模式走两条代码路径，共享工具集"的具体化。

**为什么必须分开**：

- 混在一个提示词里，模型会在对话时想产出 Candidate，或在决策时想聊天
- 对话是**同步、用户在等**；决策是**异步、有截止时间**
- 对话的输出不需要 schema 校验；决策的输出必须严格校验
- 对话失败无所谓；决策失败必须 fail-closed

### 2.2 数据模型

```sql
CREATE TABLE llm_conversations (

CREATE TABLE llm_strategies (
    id              TEXT PRIMARY KEY,

                                               -- / PAUSED / EXPIRED / REVOKED
    source_prompt_cipher BLOB,                 -- 加密的策略原文
    source_prompt_sha256 TEXT NOT NULL,
    proposal_json        TEXT,                 -- PolicyProposal（结构化草案）

    risk_envelope_hash   TEXT,
    clarifying_questions TEXT,                 -- JSON 数组
    proposal_state       TEXT,                 -- NEEDS_CLARIFICATION / READY_FOR_REVIEW
    created_at           TEXT NOT NULL,
    frozen_at            TEXT,
    UNIQUE (strategy_id, created_at)
);

CREATE TABLE llm_strategy_approvals (
    id                     TEXT PRIMARY KEY,
    strategy_version_id    TEXT NOT NULL UNIQUE REFERENCES llm_strategy_versions(id),
    account_id             TEXT NOT NULL,
    network                TEXT NOT NULL,       -- binance-mainnet / binance-testnet
    execution_mode         TEXT NOT NULL,       -- SHADOW / PAPER / TESTNET / LIVE
    approved_market_ids    TEXT NOT NULL,       -- JSON 数组
    risk_envelope_json     TEXT NOT NULL,
    risk_envelope_hash     TEXT NOT NULL,
    pair_epoch             INTEGER NOT NULL,
    llm_profile_revision_id  TEXT NOT NULL,
    jev_profile_revision_id  TEXT NOT NULL,
    valid_from             TEXT NOT NULL,
    valid_until            TEXT NOT NULL,       -- ≤ valid_from + 7 天
    approved_by            TEXT NOT NULL,
    approved_at            TEXT NOT NULL,
    revoked_at             TEXT,
    revoked_by             TEXT,
    revoke_reason          TEXT,
    expired_at             TEXT
);

CREATE TABLE llm_market_trade_grants (
    id            TEXT PRIMARY KEY,
    account_id    TEXT NOT NULL,
    network       TEXT NOT NULL,
    market_id     TEXT NOT NULL,
    granted_by    TEXT NOT NULL,
    granted_at    TEXT NOT NULL,
    valid_until   TEXT NOT NULL,                -- ≤ granted_at + 30 天
    revoked_at    TEXT,
    revoked_by    TEXT,
    revoke_reason TEXT

```

**不可变性**：事实表（`llm_chat_messages`、`llm_strategy_approvals`、`decision_runs`、`audit_events`）用数据库触发器禁止 UPDATE/DELETE（原项目的做法："Immutability enforced by triggers (no UPDATE/DELETE on fact tables)"）。

SQLite 和 Postgres 都支持触发器，迁移文件里各写一份（`database/migrations/` 的既有约定是每个迁移目录含 postgres + sqlite 两份 SQL）。

### 2.3 上下文重建

策略提取时的上下文（原项目规则）：

> 提案提取上下文 = 从会话开始到所选消息的全部用户指令，按时间顺序，上限 **256 条用户消息 / 16000 字符**。超出时需在新会话中写明经用户确认的汇总策略，避免静默截断。

实现：

```go
func BuildPolicyContext(convID string, uptoSeq int) (*PolicyContext, error) {
    msgs := 按 seq 升序取 role='user' 的消息，seq <= uptoSeq
    if len(msgs) > 256 { return nil, ErrPolicyContextTooLong }   // 不截断，直接拒
    total := sum(char_count)
    if total > 16000 { return nil, ErrPolicyContextTooLong }
    解密 → 拼接 → 返回
}
```

**拒绝而不是截断**，并在错误信息里告诉用户"请开新会话并写入经确认的汇总策略"。

### 4.3 REPL 对话的实现要点

gctcli 现有命令都是"一次调用一次输出"。REPL 需要：

- 用 `bufio.Scanner` 读 stdin（注意 `golangci-lint` 对 `bufio.Scanner` 的行长限制，长输入要用 `bufio.Reader`）
- `:help` / `:quit` / `:save` / `:history` / `:evidence <ref>` 等冒号命令
- 每轮调 `LLMSendMessage` RPC，超时用 `--timeout`（默认 30s，对话可能要放宽到 120s，用 `--ignoretimeout` / `--it`）
- 工具调用过程**实时打印**（用 `LLMChatStream` 或在响应里返回转录）
- 证据引用可展开：`:evidence ev_01` 打印该条工具响应的完整 JSON + 哈希

## 5. 事件推送

复用 `CommunicationsManager.PushEvent(base.Event{Type, Message})`（`engine/communication_manager.go:87`）。订单管理器已经在用（`base.Event{Type:"order"}`，`engine/order_manager.go:449-452`、`469-472`）。

新增事件类型：

| Type | 触发 | 消息内容 |
| --- | --- | --- |
| `llm_decision_allow` | 风控放行并即将下单 | 策略版本、市场、动作、数量、名义额、理由摘要 |
| `llm_decision_reject` | 风控拒绝 | 拒绝码 + 实际值 vs 允许值 |
| `llm_decision_review` | 转人工复核 | 原因（模型分歧 / 证据不足 / 策略不对齐） |
| `llm_order_submitted` | 已提交交易所 | 订单号、ClientOrderID |
| `llm_order_filled` | 成交 | 成交量、均价、手续费 |
| `llm_order_unknown` | **结果不明** | ⚠ 高优先级，账户已标记需对账 |
| `llm_pair_changed` | 配对切换 | 新 `pair_epoch`、受影响的策略数 |
| `llm_probe_failed` | 探针失败 | 哪个 profile、哪一层、错误码 |
| `llm_budget_exhausted` | 预算耗尽 | 剩余预约数 = 0 |
| `llm_halt_set` / `llm_halt_cleared` | 停机 | 级别、原因、影响范围 |
| `llm_reconcile_mismatch` | 对账差异 | 差异项、本地值 vs 交易所值 |
| `llm_strategy_expiring` | 审批即将过期 | 剩余分钟数 |
| `llm_protective_exit_failed` | **止损单提交失败** | ⚠ 最高优先级，已触发 fail-safe 平仓 |
| `llm_data_stale` | 数据长期过期 | 哪个事实、年龄 |

**通道配置（Q19 已定案 = Telegram 主 + 新增通用 webhook）**：GoCryptoTrader 原生只有 Telegram / SMTP / Slack / SMSGlobal，**没有通用 webhook**，因此需要**新写一个 `communications/webhook` 通道**（POST JSON 到用户配置的 URL，含事件类型/严重级/摘要/详情链接；失败重试 3 次指数退避；纳入 M5-11）。Telegram 作主通道（国内需 `communications.telegram.proxy`），webhook 接自建告警系统。SMTP / Slack 不启用。

**`requireConfirmation`（已定案 = false）**：通知只用于告知。批准/撤销/清 halt 这类高危操作**必须**在 Web UI 或 gctcli 里带重新认证完成，不在聊天软件里一键完成（防误触）。

## 6. 与现有 RPC 的关系

**不重复造轮子**。LLM 层需要的很多查询已经存在：

| 需求 | 现有 RPC | 是否复用 |
| --- | --- | --- |
| 查 ticker | `GetTicker` / `GetTickers` | ✅ 直接用 |
| 查盘口 | `GetOrderbook` | ✅ |
| 查 K 线 | `GetHistoricCandles` | ✅ |
| 算指标 | `GetTechnicalAnalysis` | ✅ |
| 查仓位 | `GetManagedPosition` / `GetAllManagedPositions` / `GetFuturesPositionsSummary` | ✅ |
| 查资金费 | `GetFundingRates` / `GetLatestFundingRate` | ✅ |
| 查余额 | `GetAccountBalances` / `GetCollateral` | ✅ |
| 手动下单 | `SubmitOrder` / `SimulateOrder` | ✅（**用户手动**，不是 LLM） |
| 启停交易对 | `SetExchangePair` | ✅（**用户手动**） |
| 子系统状态 | `GetSubsystems` | ✅ |

**新增的只是 LLM 特有的**：会话、策略、审批、市场授权、Provider、配对、决策、审计、halt、预算、对账。

**重要边界**：LLM 的只读工具**在进程内直接调 Go 函数**（`ticker.GetTicker`、`kline.LoadFromDatabase` 等），**不走 gRPC 自环**。理由：

1. 性能——避免序列化/反序列化和 TLS 握手
2. 安全——gRPC 需要 Basic Auth，工具层不应该持有 RPC 凭据
3. 简洁——同进程直接调函数是 Go 的惯用法

gRPC 只用于**外部客户端**（gctcli、未来的 Web UI）。

## 7. REST 网关的使用

`grpcProxyEnabled: true` 时，所有新增 RPC 自动获得 HTTP + JSON 端点（`google.api.http` 注解）。这让未来的 Web UI 或第三方脚本能直接接入，不需要写 gRPC 客户端。

```bash
# 查状态
curl -sk -u admin:'<password>' https://127.0.0.1:9053/v1/llm/status | jq .

# 发消息
curl -sk -u admin:'<password>' -X POST https://127.0.0.1:9053/v1/llm/conversations/c_8f3a2b/messages \
  -H 'Content-Type: application/json' \
  -d '{"content":"BTC 1小时 MACD 什么形态？","market_id":"Binance:usdtmarginedfutures:BTC_USDT","mode":"CHAT"}' | jq .

# 查决策链
curl -sk -u admin:'<password>' 'https://127.0.0.1:9053/v1/llm/decisions/dr_a1b2c3/lineage' | jq .
```

OpenAPI 规范会自动出现在 `gctrpc/rpc.swagger.json`（`buf generate` 重新生成，见 `gctrpc/README.md:54-69`）。

**安全**：9052/9053 必须只绑 `127.0.0.1`。Basic Auth 凭据要强。`GetConfig` 会返回完整配置——确认密码强度。

## 8. 前端选型建议（C 阶段）

如果决定做 Web UI，沿用原项目的技术栈选择（`docs/02-architecture.md`、`docs/07-ui-delivery.md`）：

| 层 | 选择 | 理由（原项目的论证） |
| --- | --- | --- |
| 框架 | React 19 + Vite + React Router | 原项目已验证 |
| UI 库 | Ant Design 6 + **Ant Design X** | Ant Design X 提供对话组件（Bubble / Sender / Conversations / Sources），中文暗色紧凑主题成熟。原项目对比过 MUI / shadcn / AG Grid |
| 图表 | TradingView Lightweight Charts | K 线 + 指标叠加 + 成交标记 |
| 服务端状态 | RTK Query（所有 HTTP） | 缓存、失效、重试 |
| 客户端状态 | Jotai | 原子化，适合面板布局状态 |
| WS/流 | 独立的 stream store | 与 RTK Query 分离 |

**必须保留的原项目 UI 规则**：

- 证据卡片显示 `market + sourceTime + snapshotId + dataQuality`
- 价格线若来自非可成交源，标注"公开中间价，非可成交价"
- 三种禁用原因明确展示：`INCOMPLETE` / `DEGRADED` / `STALE_PAIR`
- "当前运行配对"横幅：`LLM × Jev | READY/INCOMPLETE/DEGRADED + pair_epoch`
- 审批倒计时
- 版本 diff 可视化
- **不显示"胜率"、"预期收益"这类由模型概率推导的数字**

**部署**：静态文件 + 只绑 `127.0.0.1`，通过 REST 网关（9053）访问后端。不需要独立后端进程。
