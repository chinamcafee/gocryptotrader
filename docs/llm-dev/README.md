# GoCryptoTrader × LLM + Jev(System One) 智能永续合约交易方案

本目录是把 **OpenAI 兼容 LLM** 与 **TypeSafe Jev（System One）** 双模型能力融入 GoCryptoTrader 的完整技术方案。目标能力：

> 追踪任意一个永续合约的 K 线（MACD、均线）历史数据，提供**对话式实时数据分析** + **自动决策交易策略**。

方案以用户已有的 `hyperliquid-auto-trader` 项目（TypeScript，未完工）为参考蓝本，把其中经过验证的产品理念和安全边界移植到 GoCryptoTrader 的 Go 代码基上，同时利用 GoCryptoTrader 已有的、`hyperliquid-auto-trader` 缺失的能力（技术指标引擎、多交易所抽象、订单管理器、gRPC 接口）。

## 核心设计立场（先读这一段）

方案完整继承 `hyperliquid-auto-trader` 的五条设计底线，并针对 GoCryptoTrader 的实际情况做了调整：

1. **默认只有只读和模拟能力。** 测试网需要显式切换，主网签名与自动执行需要独立解锁。
2. **LLM 与 Jev 都不得直接持有交易所 API Key，也不得调用任意交易接口。** 模型输出只是交易**候选**与**辅助判断**。
3. **资金、频率、杠杆、价格偏差、市场白名单和紧急停机是不可由提示词覆盖的硬约束。**
4. **WebSocket 连接、进程存活或模拟回放不能当作真实下单成功。** 成交与仓位以交易所查询和对账为准。
5. **模型概率不代表上涨概率、收益率或"交易胜率"。** 需要用本项目的历史样本验证与校准。

在此之上，本方案新增三条针对 GoCryptoTrader 的立场：

1. **优先复用，不重写。** GoCryptoTrader 已经有完整的交易所抽象、订单管理器、K 线与技术指标引擎、gRPC 服务、通信通知。LLM 层是**新增的决策来源**，不是新的交易引擎。
2. **技术指标是证据，不是权威。** 用户明确要求 MACD 和均线。它们作为**只读工具的输出**进入模型上下文，和 K 线原始数据、盘口、资金费率一起构成证据链。系统**不写死"MACD 金叉就买"这类规则**——买卖假设由用户策略和当时数据驱动。
3. **一切失败都收敛到 HOLD。** 数据缺失、模型超时、schema 不合法、证据不足、配对失效、预算耗尽——全部产出 `HOLD` 或 `REVIEW`，绝不产出"猜测性下单"。

## 关键架构决策速览

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| LLM 层部署位置 | **进程内新增 engine 子系统** + 可选独立 ai-worker 进程 | 进程内可直接访问 ExchangeManager/OrderManager；独立进程用于密钥隔离，见 [03](03-总体架构设计.md) |
| 数据源 | 复用 `IBotExchange.GetHistoricCandles(Extended)` + 数据库 | 不新建行情采集链路 |
| 指标计算 | 复用 `exchanges/kline/technical_analysis.go` | MACD/SMA/EMA/RSI/ATR/BBANDS 全都已有 |
| 订单落地 | `OrderManager.Submit`（真实）/ `SubmitFakeOrder`（纸面） | 已内建限额校验、币种状态、通信通知、仓位跟踪 |
| 策略框架 | 新增 LLM 决策子系统；回测复用 `backtester` 的 `strategies.Handler` | 主引擎没有策略子系统，backtester 有且支持实盘 |
| 对话接口 | **Web UI 主交互**（React+AntD X，复用原项目前端，Q21=C）+ gRPC/REST + gctcli 兜底；**真流式仅对话模式**（Q14=C） | 接口按 UI 无关设计，前端只消费 `/v1/*` |
| 数据库 | **PostgreSQL**（Q20=B） | 全量 525 合约 + 决策/审计/会话数据量下更稳；迁移仍双份提供 |
| 合约覆盖 | **全量 525 个 USDT-M 永续**，两层轮询（04 §7.4），5-10 分钟全量刷新 | Q2 自定义；权重实测 56.5/min，占上限 2.4% |
| 交付范围 | **M0-M8 全量**（含 Web UI 与 LIVE 小额），约 18-24 周 | Q1=E；TESTNET 验收仍是 LIVE 的硬门禁 |
| 双模型配对 | `active_model_pair` 单行表 + 单调 `pair_epoch` | 直接沿用 hyperliquid-auto-trader 的设计 |
| Jev 契约 | `POST {base}/v1/systemone`，固定模型版本；**Jev 必需、无降级路径**（Q3=A） | TypeSafe 官方契约；账号与额度已具备 |
| 密钥保管 | 独立 `llm-vault`（RSA-OAEP 包裹 AES-GCM）+ **包级隔离**（Q22=A，单机 Mac） | 模型密钥与交易所 Key 物理分离；架构测试锁 import 边界 |
| 通知 | 复用 `CommunicationsManager.PushEvent`（Telegram/SMTP/Slack） | 已有事件通道 |

## 与原项目最大的三处差异

1. **原项目没有任何技术指标计算**（全仓库 grep `MACD|均线|moving average|EMA|indicator` 零命中），这是它刻意的设计："系统不是'写死买卖指标'"。GoCryptoTrader 有完整的指标库，用户明确要求 MACD 和均线。**本方案的处理**：指标作为工具证据暴露给模型，同时保留"指标不是权威"的哲学——见 [04-数据层](04-数据层-K线与指标.md) §6。
2. **原项目追求"全深度盘口"**，需要自建 Hyperliquid 非验证节点（Ubuntu 24.04 / 16 vCPU / 128GB），这是它 22 个未完成点里的 12 个的来源，且**从未真正跑起来过**。币安是中心化交易所，REST 就提供完整深度快照，**这个难题在本项目里不存在**。数据质量分级需要重新定义，见 [04-数据层](04-数据层-K线与指标.md) §5。
3. **原项目是 TypeScript monorepo（Postgres + Redis + ClickHouse + 7 个独立进程）**，GoCryptoTrader 是**单体 Go 程序 + SQLite/Postgres**。本方案不复制那套分布式拓扑，改为在单体内划清模块边界，见 [03-总体架构设计](03-总体架构设计.md) §7。
