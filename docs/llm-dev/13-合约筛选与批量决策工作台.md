# 13 · 合约筛选与批量决策工作台（新增功能技术方案）

> 状态：2026-10-15 立项。本文回答三项新需求（对话筛选合约 / GUI 批量开仓决策 / 持仓复核决策）的现状支撑度、缺口与落地设计。缺口清单见 `OPEN-QUESTIONS-新增功能-待确认.md`（含已按安全默认落地的备查项）。

## 1. 需求与现状评估（证据先行）

### 需求一：对话里用自然语言按任意指标筛选 300+ 合约（TopN）

**现状：不支持。** 证据：

- 八个只读工具（`llm/tools/tools.go:30-40`）除 `listMarkets`（子串列目录、单次 ≤25、非筛选）外全部单市场入参；无 ticker/涨跌幅/资金流工具。
- 工具循环预算 4 轮 / ≤8 次调用 / 单结果 ≤12KB（`engine/llm_tool_loop.go:17-25`）——用现有工具扫 300+ 合约在物理上不可行。
- scope 为闭集（rotator 覆盖集合，`llm/tools/tools.go:481-540`）：证据出圈即拒。

**缺口如何补（设计见 §3.1）**：新增一个**确定性全宇宙筛选器**（Go 服务）+ 一个 `screenMarkets` 工具挂进现有工具循环。LLM 负责把自然语言翻译成结构化 criteria（指标-比较符-阈值 + 排序 + TopN），筛选器在引擎内一次扫全宇宙——**"子 Agent"能力由既有工具循环承担，不需要引入 Mastra**：

| 问题 | Mastra（TS Agent 框架） | 本方案（Go 原生） |
| --- | --- | --- |
| 多轮工具调用 | 框架 plan/act 循环 | 已有：`RunToolLoop` 4 轮/8 调用/24k token |
| 工具治理 | 需重建 scope/证据/预算闸 | 已有：scope 闭集、ToolEvidence 信封、预算预约 |
| 落库/审计 | 需桥接 | 已有：转录落 decision_runs、聊天证据卡自动渲染 |
| 部署 | 额外 Node 服务 + 进程间协议 | 同进程函数调用，零新增运维面 |

结论：**不引入新框架**；筛选能力=确定性计算（Go）+ LLM 调度（现有循环）。指标"不硬编码"的含义=**指标注册表**（可枚举、可扩展的 metric registry），LLM 按注册表选指标组 criteria，而不是每加一个指标改一次提示词。

### 需求二：GUI 对选中合约（单/批量）调 Jev 生成开多/开空决策

**现状：单市场已具备完整链，批量与 GUI 缺。** 证据：

- `LLMTriggerAnalysis` / `LLMPreviewDecision`（`gctrpc/rpc.proto:1863-1873`，请求仅 `strategy_version_id + market_id`）→ `runShadowDecision` → 分析 → Jev → 合成 → 风控 → 数量重算 → 三表落账（`engine/rpcserver_llm_strategy.go:513-547`）。RPC 路径**只记录不下单**（结构性承诺，`rpcserver_llm_strategy.go:506-512`）。
- 无批量 RPC；`LLMListDecisionRuns` 的 decision_runs 表**无 market 字段**（market 在 snapshots 表），GUI 列表需 join 或补字段。

**缺口如何补（设计见 §3.2）**：引擎内**批量作业运行器**（异步 job：串行执行 N 个市场的完整决策链，逐个落账；RPC 起批 + 轮询进度/结果）+ decisions 列表补 market 字段（迁移 v20 或 join 快照，见 §4）+ 新前端页「筛选与开仓决策」。

### 需求三：持仓复核（自开仓后综合走势）→ 持有/平仓决策（单/批量）

**现状：不支持复核语义，数据与列表可复用。** 证据：

- 无持仓复核入口：trigger/preview 的提示词是"分析行情→产候选"，不带"持仓自开仓以来怎么走"的语境；候选动作集合已含 `REDUCE`（`llm/candidate/candidate.go:17-29`）。
- 持仓列表：核心 RPC `GetAllManagedPositions`（`rpc.proto:2764`，`/v1/getallmanagedpositions`）+ 快照内账户事实（`snapshot.AccountFacts.Positions` 已随 `Assemble` 进入每次运行）；webUI 已有 `useGetManagedPositionsQuery` 未用定义（`gctApi.ts:187-190`）。
- K 线缓存提供**零权重**历史读取（`KlineCache.closedCandles`，`engine/llm_kline_cache.go:124`），"自开仓后走势"可从缓存切片。

**缺口如何补（设计见 §3.3）**：新增决策触发类型 `MANUAL_POSITION_REVIEW`（手动持仓复核）：同一决策链、不同用户消息框架（附持仓事实 + 自开仓窗口 K 线与派生指标 + 资金费与未实现盈亏）→ 候选只应给 `HOLD`/`REDUCE` → Jev 复核 → 落账；批量走同一作业运行器；新前端页「持仓决策」。

## 2. 数据缺口修复（两处已实锤）

1. **USDT-M 批量 ticker 丢字段**：`U24HrPriceChangeStats` 含 `PriceChangePercent/Volume/QuoteVolume/Count`，但 `binance_wrapper.go:373-398` 批量路径只拷 Last/High/Low/Volume/QuoteVolume/Open——`PercentChange24Hour` 恒 0（快照 ticker 事实同样受害，`engine/llm_snapshot.go:383-412`）。**修复**：批量路径与单对 `UpdateTicker` 同步补写 `PercentChange24Hour`、`Bid/Ask`（响应无 bid/ask，留空）、`Last`/`High`/`Low` 已有。
2. **K 线 taker 字段被弃**：`FuturesCandleStick.TakerBuyBaseAssetVolume`（`cfutures_types.go:45-62`）在转 `kline.Candle` 时丢弃（`binance_wrapper.go:1610-1618`），`kline.Candle` 无该字段——**净流入不能从缓存算**。**修复**：不走全局结构改动，净流入由筛选器按需向交易所读（见 §3.1 数据源）。

## 3. 设计

### 3.1 全宇宙筛选器（`engine/llm_screener.go` + `llm/screener/`）

**数据源三档**（每指标标注档位与新鲜度，结果里如实带出）：

| 档 | 读法 | 权重成本 | 涵盖指标 |
| --- | --- | --- | --- |
| T0 | 24h 批量 ticker（rotator 每周期刷缓存，修复 §2.1 后） | 0（已缓存） | `change24h`、`quoteVolume24h`、`count24h`、`lastPrice` |
| T1 | K 线缓存 `closedCandles`（默认 1h，rotator 全量重载 250 根/市场） | 0（已缓存） | `change4h`、`change48h`、`macd`（状态/柱向/交叉）、`atrPercent`、`highLowRange24h` |
| T2 | 交易所按需读（仅当 criteria 需要；并发受限） | 每市场 1 次 | `netFlow24h`（taker 买−卖报价额）、`takerBuyRatio24h`、`fundingRate` |

**T2 的覆盖面纪律**（净流入为例）：`/futures/data/takerBuySellVol` 类端点为逐符号读，588 市场全量逐符号在权重与延迟上都不可接受 → 采用**成交量优先的前 K 扫**（`screener.flowScanLimit`，默认 100，按 quoteVolume 降序取前 K；K 可配）。超出 K 的市场的 T2 指标记 `null`；任何依赖 null 的 criteria 把这些市场**排除并在结果元数据里如实计数**（不静默当 0——沿用全仓"缺席不伪装"纪律）。

**Metric registry（不硬编码的关键）**：`llm/screener/metrics.go` 注册表——每个指标=名字+档位+纯函数+描述；新增指标=增一行注册，提示词里的指标清单由 `Specs()` 自动生成进 `screenMarkets` 工具 schema。criteria 结构：

```json
{"metric": "change24h", "op": "gte", "value": "-10"}
{"metric": "macd", "state": "BULL_CROSS", "withinBars": 4}
```

**排序与截断**：`sort: [{metric, desc}]` + `limit ≤ 50`（默认 20）。结果=逐行 `{marketId, 各指标值, quality 档位, asOf}` + `meta{universeSize, scannedT1, flowScannedT2, excludedByNull}`。

**`screenMarkets` 工具契约**：入参 `{criteria[], sort[], limit, interval?}`；实现挂 `engine/llm_tools.go` 执行器 switch（第 9 个工具）；证据信封 `Quality` 按混合来源标 `DATABASE_CACHED`（缓存主档；T2 读数在 Data 内自带 `source: EXCHANGE_REST` 标注）。**工具结果有 12288 字节硬限**：超大结果在**工具路径**按尾部诚实裁剪并在 `notes` 标注省略行数（`fitScreenResultToEvidenceBudget`——Top20 行约 4-6KB 常态安全，limit=50 且多指标时触发；GUI RPC 直调不经此限）。scope 校验：只在覆盖集合内命名市场（天然满足）。

**新鲜度纪律**：T1 数据来自上次全量重载（≤1 个旋转周期，默认 10 分钟内）；`asOf` 逐行带出，结果 meta 标 `dataAgeSec`。T0 同理。

### 3.2 批量决策作业（`engine/llm_batch_runner.go` + 2 RPC）

- **作业模型**：内存作业表 `{jobId, kind: OPEN_DECISION|POSITION_REVIEW, strategyVersionId, markets[], 逐市场状态(pending/running/done/failed+reason), results[](decisionRunId, decision, reason), createdAt}`；**串行**执行（并发=1，保护预算与去抖语义）；单市场失败隔离（沿用消费者纪律）。
- **RPC（proto 新增，纯增量）**：
  - `LLMStartBatchDecision{strategy_version_id, market_ids[](≤ batchMaxMarkets，默认 10), kind, actor}` → `{job_id}`
  - `LLMGetBatchDecision{job_id}` → 进度+逐行结果（含 decisionRunId 供跳转血缘）
- **权限与安全**：沿用 trigger/preview 同一 fail-closed 装配检查；RPC 路径**只记录不下单**（与现承诺一致）；每市场 run 仍走去抖 + 预备 + 预算预约 + 全部门禁（拒绝也落账）。
- **绑定版本**：GUI 默认自动选"当前活跃审批（READY 配对）的 FROZEN 版本"；无活跃审批 → 起批拒绝（fail-closed）。多版本时由用户显式选择（下拉）。
- **审计**：每次起批落 `BATCH_DECISION_STARTED`（actor=操作者、subject=jobId、detail=kind/版本/账号/网络/市场数）；**审计写失败即拒绝起批**（fail-closed，与 `MODE_SWITCHED` 同级）。
- **market 字段补齐**：`decision_runs` 增列 `market_id TEXT NULL`（迁移 v20，纯增列+回填 null；写入端自 `candidateMarketID` 已持有值填）——列表/工作台据此展示与过滤；老行以 snapshot join 兜底。

### 3.3 持仓复核（`MANUAL_POSITION_REVIEW`）

- 新触发常量 + 新用户消息框架（`engine/llm_analysis.go` 分叉）：附 **持仓行**（venue+本地对账后）、**自开仓窗口**（entryTime→now 的缓存 K 线切片 + change/max adverse excursion/当前 RSI-MACD 状态）、未实现盈亏、自开仓资金费累计、保护性止损现状。
- 开仓时刻来源：本地 intents 表 `FILLED/PARTIALLY_FILLED` 最近一行（`ListOrderIntents...` 已有查询）→ 缺失时以 48h 窗口兜底并如实标注。
- 候选契约不变（HOLD/REDUCE 上限）；Jev 复核与落账复用现链；批量=同一作业运行器 `kind=POSITION_REVIEW`，市场集合=GUI 勾选的持仓市场。
- 无持仓市场运行复核 → 入口拒绝（GUI 禁用 + 引擎校验）。

### 3.4 GUI（webUI）

- 新路由 **`/screener`「筛选与开仓决策」**：左=筛选条件（指标下拉来自后端 metric registry RPC `LLMGetScreenerMetrics`、比较符、阈值、排序、TopN；或"去对话里让 LLM 筛"提示入口）；中=结果表（行选择、指标列、质量/新鲜度标注）；右/下=决策区（版本选择、`生成开仓决策` 单/批量按钮、进度轮询、逐行裁决+血缘链接）。
- 新路由 **`/positions-review`「持仓决策」**：持仓表（`getallmanagedpositions`）+ 自开仓摘要列 + `生成持有/平仓决策` 单/批量 + 结果列。
- 代理/mock 同步：新路径全走 `llm/*`（GET 免白名单、POST 收 `GCT_ALLOW_WRITES` 闸）；mock-gateway 增补三个端点（screener metrics / batch start / batch get）以保离线开发链。
- 证据卡片：对话里 `screenMarkets` 结果经既有证据卡通道自动出 Sources（`engine/llm_chat_cards.go` 零改动）。

## 4. 与现有纪律的兼容

- **只读红线**：对话侧唯一新增能力是 T0-T2 读；无任何下单路径。GUI 批量=决策记录（与 trigger/preview 同级），执行仍走模式桥/审批流。
- **不发明**：T2 缺席记 null 不入算式；持仓复核的"自开仓窗口"缺失时标注兜底窗口。
- **预算**：批量作业逐 run 走既有预约/就绪/预算门禁；批量上限默认 10/批（可配），保护 100/24h 预约池。
- **失败关闭**：无活跃审批/无持仓/去抖中/预算尽 → 逐市场落拒绝理由，不静默跳过。
