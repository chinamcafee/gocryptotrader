# 16 · 对话配置能力对齐评估（2026-10-17）

> 问题：`对话` Tab 能否以自然语言覆盖 `合约覆盖`、`筛选与开仓决策`、`持仓决策` 三个 Tab 的全部配置能力（创建/修改/删除），并保持双线路（手动 / 对话）1:1 对齐？

## 0. 结论

**现状不能覆盖，且不是「补几个按钮」的量级。** 两个事实决定了差距：

1. **对话侧目前只有读能力**：9 个只读工具（`listMarkets` / `getCandleWindow` / `getIndicators` / `getOrderBookSummary` / `getFunding` / `getAccountState` / `getStrategyHistory` / `getRiskBudget` / `screenMarkets`）+ 流式回复 + 证据卡。**没有任何写/提案能力**——筛选可以跑，但「对选中合约发起开仓决策」「发起持仓复核」都只能回 GUI 手动点。
2. **`合约覆盖` 页当前没有手动配置面**：MarketsPage 是纯只读展示（统计、列表、预算计划值）；启停合约的 `LLMSetMarketTracked` 端点与行内开关属于 **N10-N13（已立项未实现）**。也就是说这一项今天连「手动线路」都不存在，对话 1:1 对齐无从谈起，必须先补手动面。

**建议补齐路线**：核心机制是「**对话提案 + 确认卡片 + 确定性执行**」——模型永不直接写（`模型只读` 红线不破），对话只输出结构化 proposal；确认卡片展示动作/参数/绑定/风险，用户点「确认」后由前端调用**与手动完全相同的 RPC**（写闸、审批绑定、审计全部同源）。这样双线路天然 1:1，而不是两套写路径各自演化。

## 1. 现状盘点

### 1.1 三个 Tab 的手动配置面

| 能力 | 现有手动动作 | 创建 | 修改 | 删除 | 持久化 |
| --- | --- | --- | --- | --- | --- |
| 合约覆盖 | **无**（只读展示；N10-N13 未实现） | — | — | — | enabledPairs（配置层，页面不可改） |
| 筛选与开仓决策 | 条件构建器（指标/操作符/值/区间/类别）、排序+方向+limit、运行筛选、结果勾选、批量开仓作业（策略版本+操作者）、单市场发起 | 运行筛选 / 批量作业 | 改条件重跑 / 改勾选 | **无取消** | 无预设；策略版本存 localStorage |
| 持仓决策 | 持仓表、勾选/全部/单市场、批量复核作业（策略版本+操作者） | 复核作业 | 改市场选择 | **无取消** | 无预设；策略版本存 localStorage |

### 1.2 对话侧现状

- 只读工具 9 个；筛选用 `screenMarkets` 已覆盖「自然语言 → 条件 → 全宇宙结果 + 证据」。
- 输出协议：流式 delta + `final`（正文、toolTranscript、evidence 卡片）；`EvidenceCard` 由 `engine/llm_chat_cards.go` 从工具证据包络提取。
- 机器化边界：`engine/llm_chat_safety_test.go` 对输出字段做白名单断言——**新增输出字段必须同步该白名单**（这是设计护栏，不是障碍）。
- 红线：模型只读；对话层不得出现 Order/Decision 型写字段。

## 2. 差距矩阵（1:1 对齐）

| 手动动作 | 对话现状 | 缺口 | 补齐方式 |
| --- | --- | --- | --- |
| 运行筛选（条件/排序/limit） | ✅ `screenMarkets` 已可 | 无 | 已对齐（可附「筛选条件确认卡」提升可控性） |
| 对选中合约发起开仓决策（批量作业） | ❌ 不能发起 | 提案 + 确认卡 + 调 `LLMStartBatchDecision` | I2 |
| 单市场开仓决策 | ❌ | 同上（marketIds 单元素） | I2 |
| 发起持仓复核（选中/全部/单市场） | ❌ 不能发起 | 提案 + 确认卡 + 调 `LLMStartBatchDecision(kind=POSITION_REVIEW)` | I2 |
| 合约启用/停用 | ❌（手动面也不存在） | 先实现 N10-N13 手动面，再接提案 | I3 |
| 取消批量作业 / 删除预设 | 两端都没有 | 不发明（若需要，两端同时新增） | 暂缓 |

**结论：筛选线路已对齐；开仓决策与持仓复核只差「发起动作」；合约覆盖缺的是整条手动面 + 对话面。**

## 3. 方案设计

### 3.1 总原则

1. **模型永不写**：新增工具只产出 `proposal` 结构化数据，零副作用；工具名不含 write/execute 语义。
2. **执行同源**：确认卡片的「确认」由前端调用现有 mutation（`LLMStartBatchDecision` 等），与手动按钮走同一个 RPC、同一套校验、同一份审计。不新增旁路 RPC。
3. **双层校验**：工具 JSON schema 先约束；服务端在生成提案与执行时分别复用现有校验器（指标目录、市场 id、活跃审批绑定），提案本身不豁免任何闸门。
4. **人类确认是执行前提**：模型输出只是建议；卡片完整展示动作、参数、策略版本/审批/epoch 绑定与影响面；确认后写闸与审批绑定照旧生效。
5. **注入防御**：提案参数只来自用户语义 + 服务端目录；卡片逐项渲染参数，不渲染模型自由文本为可执行控件。

### 3.2 新增组件

- **后端只读工具 `proposeAction`**（`llm/tools` 注册）：schema 判别 `action`：
  - `START_OPEN_DECISION_BATCH`：`marketIds[]`、`strategyVersionId`、`actor`（可选，默认 `webui-operator`）
  - `START_POSITION_REVIEW`：`marketIds[]`（或 `all=true`）、`strategyVersionId`、`actor`
  - （I3）`SET_MARKET_TRACKED`：`marketId`、`tracked`
  - 输出 `candidate.Proposal` 包络（新增类型：动作枚举 + 参数 + 服务端校验后的摘要 + 将调用的 RPC 名 + 风险提示）。
- **对话输出协议**：`ChatTurnResult.Proposals []ProposalCard`，随 `final` 下发并随消息 transcript 落库（审计可回读）；同步 `llm_chat_safety_test.go` 白名单。
- **前端 `ConfirmationCard`**：动作标题、参数表、绑定信息、影响面提示、[确认执行] / [取消]；确认后调用现有 mutation，就地展示结果/错误；执行完成刷新列表/任务面板。
- **审计**：提案生成随 transcript 落库；确认执行沿用现有 RPC 的审计事件（批量起批已有 `BATCH_DECISION_STARTED`）。

### 3.3 覆盖能力前置（N10-N13）

对话配置不能先于手动面存在，否则 1:1 不成立。顺序：`LLMSetMarketTracked`（proto+handler+审计+`RefreshMarkets`）→ MarketsPage 行内开关 → 对话提案接线。N10（全量宇宙按需取数）与 N13（启用优先）可与本项并行/随后，不影响开关本身的对话化。

### 3.4 明确不做

- 取消/删除：当前手动面没有，两侧都不发明；如需要，两端同时新增。
- 筛选预设持久化：当前没有该配置，不发明。
- 对话直接执行任何写操作的「快捷键」：与红线冲突，永不提供。

## 4. 实施分批

| 批次 | 内容 | 依赖 |
| --- | --- | --- |
| I1 | proposal 工具契约 + 输出协议 + 前端确认卡 + safety/契约测试 | 无 |
| I2 | 开仓决策批量 / 持仓复核 两类提案接线（后端校验复用 + 浏览器实测） | I1 |
| I3 | N10-N13 手动面（端点+页面开关）+ `SET_MARKET_TRACKED` 对话提案 | I1 |
| I4 | 电池（engine 整套/lint/misc/前端）+ 台账与文档定稿 | I1-I3 |

## 5. 拍板结果（2026-10-17）

1. **范围**：I1+I2+I3 全量。
2. **覆盖开关治理**：普通配置写（写闸 + 审计），不额外要求操作口令。
3. **删除/取消**：两端同时新增「取消批量作业」。

## 6. 实施状态（2026-10-17，I1-I4 已落地）

- **I1 框架**：`proposeAction` 只读工具（四动作 schema + 逐动作必填校验 + 作用域核对 + `proposeAction` 结果作为证据数据返回）；`ChatTurnResult.Proposals` 随 `final.proposals` 下发；前端 `ProposalCard`（字段可编辑：市场列表/策略版本/操作者/市场/作业号 + 确认/忽略 + 就地结果）；safety 白名单同步（提案是惰性数据，不是指令）。
- **I2 接线**：`START_OPEN_DECISION_BATCH` / `START_POSITION_REVIEW`（含「全部当前持仓」确认时解析）→ 与手动页相同的 `LLMStartBatchDecision`；策略版本需活跃审批（与手动一致）。
- **I3 覆盖**：`LLMSetMarketTracked`（proto + handler + 审计先于变更 + `RefreshMarkets`）；MarketsPage 行内启停开关；对话提案 `SET_MARKET_TRACKED`。**N10（未启用按需取数）与 N13（启用优先）仍待实现**，本轮只做配置面。
- **I4 取消**：`BatchRunner.Cancel`（待跑行立即 CANCELLED、在途市场经上下文取消、先审计后生效）+ `LLMCancelBatchDecision` RPC + 两页「取消作业」按钮 + 对话提案 `CANCEL_BATCH_JOB`。
- **已知边界**：提案卡只存在于当前回合（消息表不存 transcript，刷新后不可恢复；操作可重新发起）；模型不能在提案里发明市场/策略版本（服务端作用域与执行端点双重校验）。
- **实弹证据**：对话「启用 DOGE_USDT」→ 模型自动 `listMarkets` + `proposeAction` → 卡片确认 → `MARKET_TRACKED_CHANGED` 审计 + enabledPairs 实际变化 → 停用复原；覆盖页开关 0G_USDT 启停往返；engine 整套、lint、misc、前端 tsc/oxlint/build 全绿（详见 workLog session-54 §二十三）。
- **Jev 开盘机会评估（2026-10-17 深夜）**：筛选结果可继续追问「4-8 小时是否有机会开仓」；`assessOpeningOpportunities` 对每个市场做两段 Jev 有界选择（机会 → 方向），每市场 1-2 次调用、预算与作用域生效；最终只呈现「机会 + 方向」结论，方向仅在判为 open 时询问。表格中的市场列只写合约名（如 AGT_USDT），不写交易所前缀。
- **运维前提（2026-10-17 补充）**：对话筛选读取 coverage 轮询维护的行情缓存，因此 `llm.coverage.enabled` 必须为 true（否则 screener 会以明确文案拒绝，而不是给出空结果）；冷启动后缓存按权重计划在 5-10 分钟内预热完成。模型偶发以 DSML 文本发起工具调用时，引擎会解析并继续执行，气泡层永不展示原始标记（workLog §二十四）。**2026-10-17 深夜补充**：筛选默认覆盖全量 available∪enabled（`llm.screener.fullUniverse`，默认 true；589 合约约 90 秒，进度卡实时显示），并按 N10 同步扩大证据作用域；未启用市场的资金费率读取仍待补齐（模型会如实标注不可用，workLog §二十五）。
