## P0：阻塞性决策

### Q1. 首期交付到哪个运行模式？

**背景**：方案定义了五级运行模式 `READ_ONLY / SHADOW / PAPER / TESTNET / LIVE`（[01-需求](01-需求与产品目标.md) §5）。原项目的现状是"自主范围 100%，但真实交易 `NOT_READY / executionAuthorized=false`"——**它从未完成一笔真实订单**。这是它最大的遗憾。

**可选项**：

| 选项 | 交付范围 | 工作量 | 风险 |
| --- | --- | --- | --- |
| A | 到 `READ_ONLY`（只有对话分析，不决策不下单） | M0-M3，约 5-7 周 | 最低。但拿不到"自动决策交易策略"这个核心需求 |
| B | 到 `SHADOW`（自动决策但只记录不执行） | M0-M4，约 9-12 周 | 低。能评估模型质量，但验证不了执行链路 |
| C | 到 `PAPER`（走 `SubmitFakeOrder`，本地仓位跟踪） | M0-M5，约 12-16 周 | 中低。验证了订单构造和仓位逻辑，但没验证交易所交互 |
| **D** | **到 `TESTNET`（币安测试网真实下单）** | M0-M6，约 13-17 周 | 中。**推荐** |
| E | 到 `LIVE`（主网真实资金） | M0-M8，约 16-20 周 + 数周观察期 | 高 |

**取舍**：

- 选 A/B 会重蹈原项目覆辙——设计精美但执行链路从未被真实验证
- 选 D 的关键优势：**币安测试网可以自助领取模拟资金**，不像 HyperLiquid 测试网需要"同地址先有主网充值历史"（这正是原项目 T040 被阻塞的原因）
- 选 E 不合适作为"首期"——LIVE 应该在 TESTNET 跑通 + SHADOW/PAPER 各 2 周以上之后再单独决策

**推荐：D（到 TESTNET）**，LIVE 作为独立的后续决策，且必须满足 [11-实施路线图](11-实施路线图.md) §10 的全部前置条件。

**影响范围**：决定 M5、M6 是否纳入首期；决定风控引擎的完成度要求（TESTNET 必须完整，SHADOW 可以只实现拒绝路径）。

**你的决定**：**E（到 LIVE）**。首期范围扩为 M0-M8。注意这不改变安全门禁：TESTNET 全链路验收（M6）仍是进入 LIVE 的**硬门禁**；LIVE 三重解锁（`acknowledgeLiveTrading="I_UNDERSTAND"` + 审批 `execution_mode=LIVE` + 风控信封金额字段全部非 null）照常生效；且必须先跑满 SHADOW/PAPER 各 ≥2 周。

### Q2. 首期支持多少个永续合约？

**背景**：你的需求是"追踪**任意一个**永续合约"。币安 USDT-M 永续有 **300+ 个合约**。但 `enabled` 列表越长，SyncManager 的 REST 轮询压力越大（币安永续**没有 WebSocket**，全靠轮询）。

**可选项**：

| 选项 | `enabled` 数量 | 轮询压力 | 说明 |
| --- | --- | --- | --- |
| A | 1-3 个（如 BTC、ETH） | 极低 | 最稳，但"任意合约"名不副实 |
| **B** | **5-20 个（主流币）** | 低 | **推荐**。覆盖绝大多数实际需求 |
| C | 20-100 个 | 中 | 需要精细控制轮询频率和权重预算 |
| D | 全部 300+ | 高 | 每分钟 300×2 = 600 次请求，权重会撞上限 |

**取舍**：

- 权重预算：币安 USDT-M 是 2400 weight/min。ticker 批量接口（`TickerBatching: true`）一次能拿全部，权重约 40；orderbook 按深度分档 2/5/10/20 权重。如果只同步 ticker 不同步 orderbook，300 个合约可行；但下单前需要盘口，所以 orderbook 不能省
- **区分"追踪"和"能交易"**：`available` 可以放全部 300+（启动时自动刷新），`enabled` 只放常用的。**市场授权（`market_trade_grants`）是第三道闸**，只有授权的才能下单
- 方案已经支持运行时动态增删（`SetExchangePair` / `gctcli pair enable`），所以"任意合约"可以通过**按需启用**实现，不需要一次性全开

**推荐：B（5-20 个常驻 enabled）+ 按需动态添加 + `available` 全量**。

具体建议：常驻 `BTC_USDT, ETH_USDT, SOL_USDT, BNB_USDT, XRP_USDT, DOGE_USDT, ADA_USDT, LINK_USDT, AVAX_USDT, LTC_USDT`（10 个），其它按需 `setexchangepair --action enable`。

**影响范围**：SyncManager 的 `numWorkers` 配置；权重预算；数据库体积（每个合约 × 每个间隔的 K 线）；[04-数据层](04-数据层-K线与指标.md) §7 的实现。

**你的决定**：**自定义：覆盖全部 USDT-M 永续（实测 TRADING 状态 525 个），但不追求高频**。设计目标：全量合约的最新一批数据在 **5-10 分钟内刷新完**。权重测算（见下）证明可行：ticker 用批量端点一次拿全部（weight 40），K 线增量拉取每合约 weight 1，10 分钟周期合计约 565 weight ≈ 56 weight/min，远低于 2400 上限。盘口**不进轮询**，改为决策时按需拉取。据此新增 04-数据层 §7.4「全量覆盖的轮询预算设计」。

### Q3. Jev 是否为必需组件？如果它没有增量价值怎么办？

**背景**：你明确要求"LLM API + Jev（System One）兼容 API"。但原项目自己的任务清单里，**T019（Jev adapter & probe）标记为 open**，理由是"no trading-context quality eval, no cost gate"——也就是说，**Jev 在真实交易语境下的判断质量从未被评估过**。原项目唯一验证过的是它能正确返回结构化答案（T039 合成链路，Jev 返回 `hold`）。

这是一个真实的风险：Jev 可能只是增加成本和延迟，而不增加决策质量。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **A** | **Jev 必需**：无 Jev 则 `pair_readiness != READY`，一切自动决策停止（原项目的设计） |
| B | Jev 可选：缺失时降级为"仅 LLM + 硬风控"，但明确标注降级状态，且不允许 LIVE |
| C | 先按 A 实现，SHADOW 阶段做对照实验（有 Jev vs 无 Jev），根据数据决定是否改成 B |

**取舍**：

- **A 的价值**：Jev 提供**独立性**。它是不同厂商、不同架构、不同提示词的模型，被同一个提示注入同时攻陷的概率远低于单模型。这是 [10-安全](10-安全与风控.md) §2.2 第 4 层防护
- **A 的成本**：每次决策多 1.5-2 秒延迟 + 约 1000-2000 输入 token；多一套 Provider Profile / 探针 / 配对治理；多一个故障点
- **B 的风险**：降级路径一旦存在，就容易在"Jev 临时不可用"时被滥用，削弱安全设计
- **C 最诚实**：先按必需实现（保证安全设计完整），同时用 SHADOW 数据回答"Jev 到底有没有用"。原项目的教训正是**把这个评估推到了最后，结果一直没做**

**评估方法（如果选 C）**：SHADOW 期间同时记录"仅 LLM 的合成决策"和"LLM+Jev 的决策"，比较：

1. Jev 推翻 LLM 的次数 / 总决策数
2. 被推翻的那些，事后人工标注哪个对
3. Jev 的 `evidence_quality.score` 与人工标注的证据充分性的一致性（校准度）
4. 分歧时"取保守方"是否降低了假阳性

样本量至少 100 条决策（[11-实施路线图](11-实施路线图.md) M6-03）。

**推荐：C（先按必需实现，SHADOW 阶段做对照评估，M6 结束时根据数据决定是否放开 B）。**

**影响范围**：`pair_readiness` 判定逻辑；M1-04 到 M1-08 是否可延后；成本预算；[06-Jev接入层](06-Jev接入层-SystemOne.md) 全文。

**你的决定**：**A（Jev 必需）**。无 Jev 则 `pair_readiness != READY`，一切自动决策停止；**不提供降级路径**。SHADOW 阶段的有/无 Jev 对照实验仍保留（作为评估数据，但不作为降级依据）。

### Q7. LLM 决策的落点：新建 engine 子系统，还是做成回测器策略插件？

**背景**：GoCryptoTrader 主引擎**没有策略子系统**，唯一的策略框架在 `backtester/`（`strategies.Handler` 接口 + Go plugin 加载）。回测器**支持实盘数据和真实下单**（`LiveData{RealOrders: true}`）。所以有两条路。

**可选项**：

| 选项 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A** | **新建 `LLMManager` engine 子系统**，直接调 `OrderManager.Submit` | 职责清晰；能访问全部引擎能力（ticker/orderbook/dispatch/comms）；对话式交互自然；改动集中 | 不能直接复用回测器的组合管理、统计报告、滑点模拟 |
| B | 实现 `strategies.Handler`，作为 Go plugin 加载到回测器，跑 `LiveData` 模式 | 复用回测器的数据管道、portfolio handler、统计报告；能在历史数据上"回放" | 回测器的 `data.Handler` **不提供 ticker/orderbook**（`backtester/README.md` 列为 planned），而 LLM 需要盘口做滑点估算；事件循环模型与"触发 + 截止时间"不匹配；回测器是**独立进程**，与主 bot 共享 OrderManager 需额外接线；对话交互无法嵌入 |
| C | 两者都做：A 用于实时决策，B 用于历史验证 | 能力最全 | 工作量翻倍，两套代码要同步维护 |

**取舍**：

- B 的致命问题是**盘口不可得**。风控的滑点检查（`RISK_SLIPPAGE_EXCEEDED`）依赖 `orderbook.Movement`，回测器的 `data.Handler` 给不了
- B 的第二个问题是**进程边界**。回测器是 `backtester/main.go` 独立程序，跑实盘时和主 bot 是两个进程。要么两个进程都连币安（权重翻倍、状态不一致），要么回测器通过 RPC 调主 bot（那还不如直接在主 bot 里做）
- A 的"不能复用回测器统计"其实不严重：`PAPER` 模式走 `SubmitFakeOrder`，订单会入 `order` 表，统计分析可以直接查库
- **A + 保留回测器作为独立的历史验证工具**是最优组合：想验证"如果用固定 MACD 规则会怎样"，写一个 `.strat` 配置在回测器里跑；想跑 LLM 实时决策，用 LLMManager

**推荐：A**，回测器保持现状不改，作为对照基线工具。详见 [07-策略与自动决策引擎](07-策略与自动决策引擎.md) §10。

**影响范围**：整个模块布局（[03-总体架构](03-总体架构设计.md) §4）；M0-11、M0-12 的实现方式；是否能复用回测器的 portfolio handler。

**你的决定**：**A（新建 `LLMManager` engine 子系统）**，直接调 `OrderManager.Submit`/`SubmitFakeOrder`。回测器保持现状不改，仅作历史验证与对照基线工具（配合 Q24）。

### Q21. 用户界面形态：gctcli 终端，还是 Web 控制台？

**背景**：原项目是 React 19 + Ant Design 6/X 的完整 Web 控制台（5 路由、30 面板、Playwright 验收）。GoCryptoTrader 是**无 UI 的守护进程**，只有 gctcli 和 gRPC/REST。

你的需求里有"**对话**分析实时数据"——对话体验在终端和 Web 上差别很大。

**可选项**：

| 选项 | 说明 | 工作量 | 体验 |
| --- | --- | --- | --- |
| **A** | **gctcli 优先**：新增 `llm` 子命令族 + REPL 式对话 | 小（含在 M3 里） | 对话可用；审批可用（结构化输出 + 确认提示）；K 线图表**没有**；监控要反复查 |
| B | REST 优先：只做 gRPC/REST 接口，交互靠 curl / Postman / 自建脚本 | 最小 | 差。不适合日常使用 |
| C | 独立 Web UI（React + AntD X + Lightweight Charts），按原项目规格 | 大（M7，4-6 周） | 好。流式对话、Markdown、K 线图叠加指标、版本 diff 可视化、审批倒计时、实时面板 |
| D | 现成的第三方终端 UI（如接一个 TUI 框架 bubbletea） | 中 | 比 A 好，比 C 差 |
| E | 接入现有 AI 客户端（把系统做成一个 MCP server 或 OpenAI 兼容端点，用 Claude Desktop / Cherry Studio 之类对话） | 中 | 对话体验好，但审批/监控仍需另做 |

**取舍**：

- **A 的最大缺陷是没有图表**。"看 MACD 形态"在终端里只能看数字，不能看曲线。但方案的设计是**派生事实由代码算好**（`CrossState: GOLDEN`、`BarsSinceCross: 3`、`HistogramTrend: EXPANDING`），所以文字描述其实够用
- **C 的工作量约等于核心链路的 40%**，且是纯前端，与 Go 侧解耦
- **E 是个有意思的选项**：把只读工具集暴露成 MCP server，就能用任何 MCP 客户端对话。但审批和风控必须留在本系统内，MCP 只能覆盖"分析对话"这一块
- **关键设计约束**：无论选哪个，**REST/gRPC 接口从第一天就按"UI 无关"设计**，这样后面加 UI 不改后端。方案已经这么做了（[08-对话与接口层](08-对话与接口层.md) §3、§7）

**推荐：A 先行（M3），C 作为 M7 可选阶段**。如果对话频率很高，可以在 M3 之后插入 E（MCP server）作为过渡——工作量小，体验提升明显。

**需要你明确的一点**：你在原项目里已经建了一套 React + AntD X 的 Web 控制台（30 个面板组件，含 ProvidersPage / StrategiesPage / TerminalPage）。**这套前端能否直接复用/改造？** 如果能，C 的工作量可以从 4-6 周降到 2-3 周（主要改数据源：从 Fastify `/v1/*` 换成 gocryptotrader 的 REST 网关）。

**影响范围**：M3 的范围；M7 是否纳入；是否需要新增前端技术栈到仓库（GoCryptoTrader 目前是纯 Go 仓库，加前端会改变仓库性质）。

**你的决定**：**C（直接做 Web UI）**，M7 纳入首期交付。技术栈按原项目规格：React 19 + Vite + Ant Design 6/X（对话组件 Bubble/Sender/Conversations/Sources）+ TradingView Lightweight Charts + RTK Query + Jotai。gctcli `llm` 子命令族**仍保留**，作为无 UI 兜底、自动化与 CI 验收入口。**待补充**：原项目 30 面板前端能否复用/改造（决定 2-3 周 vs 4-6 周），见文末开放问题 7。

### Q22. 模型密钥的隔离强度：包级隔离够吗，还是要独立进程？

**背景**：原项目把模型密钥的解密放在**独立的 `ai-worker` 进程**里，通过 0600 权限的 Unix socket（`HAT_AI_WORKER_SOCKET`）通信。主 API 进程只加载 RSA **公钥**，永远拿不到私钥。

本方案是单进程（见 [03-总体架构](03-总体架构设计.md) §7），改为**包级隔离**：只有 `llm/secrets` 能读私钥文件。

**这是相对原项目的隔离强度下降**，需要你确认是否可接受。

**可选项**：

| 选项 | 隔离强度 | 工作量 | 说明 |
| --- | --- | --- | --- |
| **A** | **包级隔离**（单进程） | 小 | `llm/secrets` 是唯一能读私钥的包；`llm/openai` 和 `llm/jev` 通过 `secretFn` 回调拿解密后的密钥，用完显式清零。架构测试保证 import 边界 |
| B | 独立 `gct-ai-worker` 进程 + Unix socket | 中（+1-2 周） | 完全对齐原项目。主进程只有公钥。需要定义 IPC 协议、进程生命周期管理、socket 权限 |
| C | 模型密钥也放 `config.dat`（复用现有配置加密） | 最小 | 隔离最弱：任何能读配置的代码都能拿到模型密钥，反之交易所 Key 也暴露给 LLM 层。**不推荐** |
| D | 环境变量 | 最小 | 违反编码规范（易泄露到日志/进程列表），不支持多档案。**不推荐** |

**取舍**：

- A 的威胁模型：**如果 gocryptotrader 进程本身被攻破**（比如某个依赖有 RCE 漏洞），攻击者能读到内存里的模型密钥。但同样的攻击者也能读到币安 API Key（它在同一个进程的内存里）。所以 A 的**边际风险**其实是"模型密钥泄露"，而不是"资金损失"——资金风险由币安 Key 的 IP 白名单 + 禁提现控制
- B 的价值在于**双向隔离**：ai-worker 被攻破拿不到交易所 Key，主进程被攻破拿不到模型 Key。这在多用户或高风险环境下有意义
- B 的成本：多一个进程要构建、部署、监控、升级；IPC 协议要设计和测试；进程崩溃恢复要处理
- 方案的目录结构已经为 B 预留：`llm/` 包不依赖 `engine/`，可以整体搬走（[03-总体架构](03-总体架构设计.md) §7）

**推荐：A 起步，B 作为可选加固**。理由：单机单用户开发环境下，A 的边际风险可控，而 B 的运维成本是实打实的。如果后续要部署到服务器或多用户环境，再升级到 B（届时 `llm/` 包可以整体抽出）。

**需要你明确的一点**：这套系统的**部署目标**是什么？

- 只在你自己的 Mac 上跑 → A 足够
- 部署到家里的 NAS / 云服务器长期运行 → 建议 B
- 未来可能给别人用 → 必须 B，且需要多租户设计（超出当前方案范围）

**影响范围**：`llm/secrets` 的实现；[09-数据存储与配置](09-数据存储与配置.md) §5；部署文档；M1-01 的工作量。

### Q4. `available` 但未 `enabled` 的合约，能否在只读对话里查询？

**背景**：你的需求是"追踪**任意**永续合约"。币安有 300+ 个 USDT-M 永续，但 `enabled` 列表建议只放 5-20 个（见 Q2）。那用户临时问一个不在 `enabled` 里的合约怎么办？

**可选项**：

| 选项 | 说明 | 取舍 |
| --- | --- | --- |
| A | 严格禁止。要查先 `setexchangepair --action enable` | 最安全，但体验差（每次都要手动启用） |
| **B** | **允许只读查询**：LLM 工具在 `READ_ONLY` 模式下可查 `available` 但未 `enabled` 的合约，标记 `onDemand = true`。**这类快照永远不能进入决策流水线**（风控要求市场在批准列表里） | 推荐 |
| C | 允许查询并允许决策（只要市场授权了） | 与 Q2 的权重预算冲突 |

**取舍**：B 的关键约束是"`onDemand` 快照不能进决策"——这保证了权重消耗可预测（只有 `enabled` 的合约被 SyncManager 轮询），同时满足"任意合约都能问一句"。

**推荐：B**，但明确限制为"只读、单次、不缓存、不进决策"。

**影响范围**：[04-数据层](04-数据层-K线与指标.md) §7.3；工具实现；权重预算。

**你的决定**：**B（只读可查、不进决策）**。READ_ONLY 下 LLM 工具可查 available 但未 enabled 的合约，标记 `onDemand=true`；该快照**永不进决策流水线**（风控要求市场在批准列表里）。Q2 全量启用后，此项主要约束'被手动 disable 的合约'与'新上市尚未被 autoPairUpdates 刷新的合约'。

### Q5. 自动决策的触发方式？

**背景**：[01-需求](01-需求与产品目标.md) §6 列了候选触发事件，但**默认开哪些**需要定。

**可选项**（可多选）：

| 触发器 | 频率 | 说明 | 推荐 |
| --- | --- | --- | --- |
| K 线收盘 | 按间隔 | 最可预测，权重消耗稳定。1h 间隔 = 每天 24 次/合约 | ✅ **默认开** |
| MACD 金叉/死叉 | 事件驱动 | 你明确提到 MACD。但会产生突发触发（多个合约同时交叉） | ⚠ 可选，默认关 |
| 均线穿越 | 事件驱动 | 同上 | ⚠ 可选，默认关 |
| ATR 突增（波动率飙升） | 事件驱动 | 捕捉异常行情，但容易误触发 | ⚠ 可选，默认关 |
| 资金费率结算前后 | 定时 | 永续特有，结算前平仓是常见策略 | ⚠ 可选 |
| 账户事件（成交/强平/保证金变化） | 事件驱动 | 重要，应该开 | ✅ **默认开** |
| 手动触发 | 按需 | 必须有 | ✅ **默认开** |

**取舍**：

- **K 线收盘 + 手动 + 账户事件**是最小可用集合，权重和成本都可预测
- 指标交叉触发的问题：它是**基于历史的确定性规则**，本质上等于"写死了指标规则"，与 [04-数据层](04-数据层-K线与指标.md) §8 的哲学有张力。但如果只作为**触发器**（触发后仍走完整 LLM+Jev+风控链路），是可以接受的
- 多触发器同时发生的去抖动：每策略版本 1 次/分钟（[06-Jev接入层](06-Jev接入层-SystemOne.md) §9）

**推荐**：默认只开 **K 线收盘（1h）+ 手动 + 账户事件**；指标交叉和 ATR 突增作为配置项，默认关，用户按需在策略版本里开。

**需要你明确**：你希望的**决策节奏**是什么？

- 每天几次（1h 或 4h K 线收盘）→ 成本低，适合"低频"定位
- 每小时几十次（1m/5m K 线收盘 × 多个合约）→ 成本显著上升，需要提高预约上限

**影响范围**：`LLMTriggerConfig`；预算上限；M4-06。

**你的决定**：**触发器 = 最小集 + 指标交叉**：默认开 K线收盘、手动、账户事件（成交/强平/保证金变化）、MACD 金叉/死叉、均线穿越；ATR 突增与资金费结算触发作为配置项默认关。多触发去抖：每策略版本 1 次/分钟。
**节奏 = 1h 扫描 + 4h 确认（双层）**：1h 间隔对全部 525 合约做便宜的触发扫描（复用 04 §7.4 第一层轮询的指标状态），仅对出现信号的合约再用 4h 数据做决策确认。这同时满足 Q2 的全量覆盖与低频定位。

### Q6. 策略审批的默认有效期和粒度？

**背景**：原项目规定审批 ≤7 天，市场授权 ≤30 天，`maxNewRiskIntents ≤ 5`（硬上限）。这些是**上限**，默认值需要定。

**可选项**：

| 项 | 原项目上限 | 建议默认 | 备选 |
| --- | --- | --- | --- |
| 策略审批有效期 | ≤7 天 | **4 小时** | 1 小时 / 24 小时 / 7 天 |
| 市场授权有效期 | ≤30 天 | **7 天** | 1 天 / 30 天 |

**取舍**：

### Q8. 默认风控信封的具体数值？

**背景**：这是**最需要你的实际判断**的一项。方案定义了风控信封的字段（[07-策略与自动决策引擎](07-策略与自动决策引擎.md) §2），但具体数值取决于你的资金规模和风险偏好。

**注意**：`null` 的金额字段会**阻止 LIVE 授权**（不是"无限制"）。所以 LIVE 模式下这些必须填。

**需要你填的表**（下面给的是"小额验证"档的示例，请按实际情况调整）：

| 字段 | 小额验证档（示例） | 中等档 | 你的值 |
| --- | --- | --- | --- |
| `maxOrderNotionalUsd` | 20 | 200 | **20**（已定：小额验证档） |
| `maxTotalExposureUsd` | 100 | 1000 | **100** |
| `maxDailyLossUsd` | 20 | 100 | **20**（触发后 FULL halt，人工解除） |
| `maxLeverage` | 1 | 3 | **1** |
| `maxSlippageBps` | 20 | 10 | **20** |
| `maxNewRiskIntents` / `riskWindowMinutes` | 2 / 300 | 5 / 300 | **2 / 300** |
| `maxConcurrentPositions` | 1 | 3 | **1** |
| `requiresProtectiveExit` | true | true | **true** |
| 止损距离 | 1.5 × ATR(14) | 2 × ATR(14) | **max(1.5×ATR(14), 2%) 取较紧**（已定） |
| 止盈 | 不设（靠指标信号平） | 2 × 止损距离 | **不设**（靠指标信号/手动/保护性止损；未单独决策，沿用小额档默认） |

**几个需要你明确的具体问题**：

1. **`maxSlippageBps` 怎么定？** 币安 BTC-USDT 永续流动性极好，正常情况滑点 < 5 bps。但小币种可能 50+ bps。建议：**主流币 10-20 bps，小币种不设自动交易**
2. **止损用 ATR 倍数还是固定百分比？** ATR 自适应波动率（推荐），固定百分比简单可预测。原项目的 `exitPolicy` 是自由文本，本方案建议结构化为 `{kind: "ATR_MULT" | "FIXED_PCT" | "PRICE_LEVEL", value: ...}`
3. **`maxDailyLossUsd` 触发后的行为？** 建议：当日剩余时间 FULL halt，次日 UTC 00:00 自动解除（但需人工确认）。**需要你确认是否接受"自动解除"**，还是必须人工清 halt
4. **资金费率要不要作为硬约束？** 例如"预测资金费率绝对值 > 0.1% 时不允许开仓"。原项目把资金费作为证据给模型，但不做硬约束。**建议：作为证据，不做硬约束**（因为它是可预测的成本，不是风险）
5. **要不要限制交易时段？** 例如"只在 UTC 08:00-20:00 交易"（避开流动性差的时段）。原项目没有这个约束

**影响范围**：`RiskEnvelope` 的校验；策略提取的澄清问题（缺这些字段时必须问）；M4-01、M4-11。

**你的决定**：**小额验证档**：`maxOrderNotionalUsd=20` / `maxTotalExposureUsd=100` / `maxDailyLossUsd=20` / `maxLeverage=1` / `maxSlippageBps=20` / `maxConcurrentPositions=1` / `maxNewRiskIntents=2 per 300min` / `requiresProtectiveExit=true`。止损方式与额外硬约束的子决策如下：

- **止损距离 = ATR 与固定百分比取较紧者**：`stop = entry − max(k×ATR(14), entry×p)`，小额档 k=1.5、p=2%。双保险且自适应。
- **日损触发后 = 人工解除**：触发 `maxDailyLossUsd` 置 FULL halt，必须人工清 halt 才恢复，不自动解除。
- **额外硬约束 = 可开关目录**：不做成固定清单，而是一组**独立、互不冲突、可运行时开关**的确定性规则（默认值见 07 §5.5「硬风控开关目录」，约 15 个开关）。打开时优先级高于任何提示词/模型输出；关闭时该约束不生效。可通过配置与 RPC 切换，切换写审计。

### Q9. 自动候选的时间窗口：10 秒还是 30 秒？

**背景**：原项目的规则是"自动候选截止时间 = 快照源时间 + 10 秒"。这是为**WebSocket 推送**设计的（数据是实时来的，10 秒已经很旧了）。

但**币安永续没有 WebSocket**（`binance_wrapper.go:75-79` 显式禁用），数据来自 SyncManager 的 REST 轮询，`timeoutREST` 默认 15 秒。**用 10 秒窗口会导致几乎所有快照都被判为过期。**

**可选项**：

| 选项 | 窗口 | 后果 |
| --- | --- | --- |
| A | 10 秒（照搬原项目） | 几乎全部 `MARKET_SNAPSHOT_STALE`，系统不可用 |
| **B** | **30 秒** | 推荐。约 2 倍轮询周期，留有余量 |
| C | 60 秒 | 更宽松，但决策基于 1 分钟前的数据，对 1m 级别策略偏旧 |
| D | 给币安 wrapper 加合约 WebSocket 支持，然后用 10 秒 | 最彻底，但是**大改动**（见 Q10） |

**取舍**：这个值和"策略的时间尺度"直接相关：

- 做 **1h / 4h 级别**的趋势策略 → 30 秒甚至 60 秒都无所谓（1 小时的价格不会因为 30 秒延迟而改变判断）
- 做 **1m / 5m 级别**的策略 → 30 秒延迟占比 10%-50%，**不可接受**，必须走 D

**推荐：B（30 秒）**，配合"策略最小间隔 ≥ 15m"的约束。如果你想做 1m/5m 级别，必须先解决 Q10。

**影响范围**：`LLMAnalysisConfig.AutoCandidateWindowSeconds`；`LLMFreshnessConfig` 全部阈值；[04-数据层](04-数据层-K线与指标.md) §6。

**你的决定**：**C（60 秒）**。自动候选截止时间 = 快照源时间 + 60s，且不超过共同流水线截止 90s。对应 `LLMAnalysisConfig.autoCandidateWindowSeconds = 60`，`LLMFreshnessConfig` 各阈值按 60s 校准。理由：币安永续无 WS、REST 轮询 15s，60s 给轮询与指标计算留足余量；配合策略最小间隔 ≥15m。注意此窗口只约束第二层决策快照，全量轮询周期由 Q2 的两层设计（04 §7.4）另行规定。

### Q10. 是否要给币安 wrapper 增加合约 WebSocket 支持？

**背景**：这是本方案遇到的**最大的平台能力缺口**。币安**其实提供** USDT-M 合约的 WebSocket（`wss://fstream.binance.com`，有 kline / depth / aggTrade / markPrice / 用户数据流），但 gocryptotrader 的币安 wrapper **只实现了现货 WS**，并在 `SetDefaults()` 里显式禁用了合约的 WS 资产支持。

**可选项**：

| 选项 | 说明 | 工作量 | 收益 |
| --- | --- | --- | --- |
| **A** | **不做**。接受 REST 轮询的延迟，策略时间尺度 ≥15m | 0 | — |
| B | 只加合约 **kline WS**（`kline_<interval>` 流） | 中（1-2 周） | K 线实时更新，收盘触发精准；指标更及时 |
| C | 加合约 kline + depth + aggTrade + markPrice WS | 大（3-5 周） | 完整实时行情，可支持 1m 级策略 |
| D | 加 C + 用户数据流（订单/成交/账户更新） | 很大（5-8 周） | 订单状态实时推送，`UNKNOWN` 大幅减少，对账更及时 |

**取舍**：

- **改动范围**：`binance_websocket.go` 目前只处理现货消息类型。合约的消息格式类似但字段不同（`e: "kline"` 结构一致，但 `depthUpdate` / `aggTrade` / `markPriceUpdate` 有差异），且需要新的 WS URL（`fstream.binance.com` 而非 `stream.binance.com:9443`）、新的订阅模板、移除 `DisableAssetWebsocketSupport` 调用
- **上游态度**：代码里的注释 `// TODO when multi-websocket support added`（`binance_wrapper.go:122`）说明上游知道这个缺口但没做。**给上游提 PR 是可能的**，但周期不可控
- **对 LLM 方案的实际影响**：如果策略时间尺度是 1h/4h（"低频"定位），REST 轮询完全够用。**只有想做 1m/5m 时才必须做 C 或 D**
- **风险提示**：改 wrapper 是**动核心交易代码**，与"优先复用，不重写"的立场（[README](README.md) 立场 6）有冲突。改坏了会影响所有币安功能

**推荐：A（首期不做）**。理由：

1. 你的定位是"低频"，1h 级别策略下 30 秒延迟无关紧要
2. 改 wrapper 的风险和工作量都不小，且不是 LLM 方案的核心价值
3. 如果后续验证确实需要更实时，再作为**独立项目**做（可以先给上游提 issue/PR）

**但如果你明确想做 1m/5m 级别的高频一些的策略，就必须选 C 或 D**，且要把它排在 M2 之前（因为数据层的新鲜度模型完全依赖它）。

**影响范围**：Q9 的答案；策略最小时间尺度；M2 的范围；是否修改 `exchanges/binance/`。

**你的决定**：**A（首期不做）**。接受 REST 轮询延迟。依据：Q9 已定 60s 新鲜度窗口、Q5b 已定 1h 扫描 + 4h 确认，轮询完全够用；改 `binance_websocket.go` 是动核心交易代码，与立场 6（优先复用不重写）冲突。若后续验证确需 1m/5m 级，再作为独立项目（可先给上游提 issue/PR）。

### Q11. UTC 日损基线的严格程度？

**背景**：原项目为"每日 USD 亏损上限"写了 `docs/17` 到 `docs/21` 加 `docs/26`-`docs/32` 共十几篇文档、20 多个迁移，因为它要处理：链上 USDC/USD 汇率（需要 Kraken 公共 WS 作外部参考）、外部本金中性化、独立历史源认证、精确 UTC 零点权益、封存窗口等。

**币安是中心化交易所**，`/fapi/v2/balance` 和 `/fapi/v2/account` 直接给 USDT 余额和权益。所以这块可以大幅简化。

**可选项**：

| 选项 | 说明 | 严格度 |
| --- | --- | --- |
| A | 简化版：每日 UTC 00:00 记一次权益快照作基线；每小时校正一次外部划转（从 `UAccountIncomeHistory` 的 TRANSFER 类型识别）；日损 = 基线 ± 划转 − 当前权益 | 中 |
| **B** | **简化版 + 缺失即拒**：同 A，但基线缺失或划转识别失败时 → `RISK_DAILY_LOSS_UNKNOWN` → 拒绝开仓 | 中高。**推荐** |
| C | 严格版：完整实现原项目的双源认证、独立历史校验、金融证书 | 高（工作量大） |
| D | 不做日损约束，只做单笔和总敞口约束 | 低 |

**取舍**：

- **B 的关键是"缺失即拒"**（原项目："reaches cap or source failure → preflight rejects"）。这保证了"不知道亏了多少"不会变成"当作没亏"
- A 和 B 的差别只在失败时的行为，实现工作量几乎一样，**没理由选 A**
- C 的工作量约是 B 的 5-10 倍，且大部分复杂度来自链上特性（USDC/USD 汇率、外部本金流），币安场景不需要
- D 不可接受——日损上限是最后一道防线，防止"连续小额亏损累积成大亏"

**推荐：B**。

**需要你确认的一点**：如果你会**手动**往合约账户划转资金（比如每周一追加保证金），划转识别必须准确，否则日损计算会错。币安的 `UAccountIncomeHistory` 有 `TRANSFER` 类型可以识别，但**该端点权重是 30**（`exchanges/binance/ratelimit.go`），不能频繁调。建议每小时调一次。

**影响范围**：`llm_day_start_inventory` / `llm_external_flows` 表；M5-09；风控检查 `RISK_DAILY_LOSS_*`。

**你的决定**：**B（简化版 + 缺失即拒）**。每日 UTC 00:00 记权益快照作基线；每小时从 `UAccountIncomeHistory` 的 TRANSFER 类型校正外部划转（该端点权重 30，每小时一次）；日损 = 基线 ± 划转 − 当前权益。基线缺失或划转识别失败 → `RISK_DAILY_LOSS_UNKNOWN` → 拒绝开仓。

### Q13. `order.Submit` 的 float64 精度问题怎么处理？

**背景**：`order.Submit.Amount` 和 `Price` 是 `float64`（`exchanges/order/order_types.go:46-117`）。原项目的原则是"decimal-string money, no JS float for signed values"。风控引擎内部用 `decimal.Decimal`，但最后转成 `order.Submit` 时必须转 float64。

**可选项**：

| 选项 | 说明 | 风险 |
| --- | --- | --- |
| **A** | 风控全程 `decimal` → 按 step/tick 向下取整 → 减一个容差 step → 转 float64 → 交给 `CheckOrderExecutionLimits` 兜底 | 低。**推荐** |
| B | 给 `order.Submit` 加字符串字段（`StrAmount` / `StrPrice`），改币安 wrapper 优先用字符串 | 改动核心类型，影响面大（所有交易所 wrapper） |
| C | 直接用 float64，靠 `CheckOrderExecutionLimits` 兜底 | 中。极端情况下可能差一个 step |

**取舍**：

- A 的"减一个容差 step"是关键：币安 step size 通常是 0.001 / 0.01 / 0.1 / 1，float64 表示 0.001 有微小误差（`0.001` 实际是 `0.001000000000000000020816681711721685...`）。向下取整后再减一个 step，保证转换后的 float64 一定 ≤ 目标值
- B 是"正确"的做法，但改的是 gocryptotrader 的**核心类型**，所有 20 个交易所的 wrapper 都受影响，且与上游分叉，后续 rebase 会很痛
- C 太冒险
- 实际上 A 的风险极低：`CheckOrderExecutionLimits` 会拦住不合规值，最坏结果是**订单被拒**（而不是下错数量）

**推荐：A**。并把"转换后重新校验"作为强制步骤。

**影响范围**：[07-策略与自动决策引擎](07-策略与自动决策引擎.md) §6.4；M4-12。

**你的决定**：**A（decimal + 向下取整 + 容差 step）**。风控全程 `decimal.Decimal` → 按 step/tick 向下取整 → 再减一个容差 step → 转 float64 → 交 `CheckOrderExecutionLimits` 兜底，且转换后强制重新校验。不改 `order.Submit` 核心类型（避免与上游分叉）。

### Q17. 会话内容的加密方案？

**背景**：策略原文含交易意图，泄露有风险。原项目用 AES-256-GCM 加密（`conversation-vault`），ID 作 AAD，标题不加密。

**可选项**：

| 选项 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A | 明文存 SQLite | 简单，可 SQL 全文搜索 | 策略原文泄露风险 |
| B | 全部 AES-GCM 加密 | 最安全 | 不能对内容做 SQL 搜索 |
| **C** | **标题/元数据明文 + 正文加密**（原项目做法） | 折中，可搜索标题和元数据 | 实现稍复杂 |

**推荐：C**。具体：

- `llm_conversations.title` —— 明文
- `llm_chat_messages.content_cipher` —— AES-256-GCM，nonce 单独存，`content_sha256` 存明文哈希用于完整性校验，AAD = `message_id`
- `llm_strategy_versions.source_prompt_cipher` —— 加密
- `llm_strategy_versions.frozen_json` —— **明文**（结构化条款需要在 UI/CLI 展示和 diff，且不含自由文本）
- `llm_decision_runs.candidate_json` / `jev_json` —— **明文**（审计需要，且已脱敏）
- 密钥文件 `<datadir>/llm-vault/conversation-key.bin`，权限 0600

**需要你确认**：`frozen_json` 里含 `sourcePrompt` 的引用吗？原项目的 `reviewable-v1` 不含原文（只有结构化条款）。**建议不含**，原文只存在加密的 `source_prompt_cipher` 里。

**影响范围**：[09-数据存储与配置](09-数据存储与配置.md) §5.4；M3-01。

**你的决定**：**C（标题/元数据明文 + 正文 AES-256-GCM 加密）**。nonce 单存、`content_sha256` 校验完整性、AAD = message_id；`frozen_json` 明文（结构化条款需展示/diff，不含自由文本，且不含 sourcePrompt 引用）；`decision_runs` 明文（审计需要且已脱敏）；密钥 `<datadir>/llm-vault/conversation-key.bin` 0600。

### Q20. 数据库选 SQLite 还是 PostgreSQL？

**背景**：GoCryptoTrader 两者都支持（`database.driver`）。方案的数据量估算见 [09-数据存储与配置](09-数据存储与配置.md) §1.1。

**可选项**：

| 选项 | 适用 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A** | **SQLite** | 零运维；单文件备份；已在 `docs/localDeploy` 里跑通 | 并发写锁（单写者）；大数据量下查询变慢 |
| B | PostgreSQL | 并发好；适合 1m 全量 K 线；触发器和事务更强 | 需要跑一个数据库进程（docker 或 brew services） |

**取舍**：

- **决策频率低**（`maxConcurrentAnalyses: 1`，串行），写并发不是问题 → SQLite 够
- **K 线量是唯一变量**：只存 1h 及以上 → SQLite 一年 < 100 MB，完全够；要存 1m × 20 个合约 → 一年 1.2 GB，SQLite 会变慢
- 方案的所有表设计都同时提供 postgres 和 sqlite 两份迁移（现有约定），**切换成本低**
- 原项目用 PostgreSQL + Redis + ClickHouse 是因为数据量大三个数量级

**推荐：A（SQLite）起步**，如果决定存 1m 全量 K 线或数据量超过 5 GB，切 PostgreSQL。切换步骤见 `docs/localDeploy/06-数据库与历史K线.md` §11。

**影响范围**：`docs/localDeploy` 的配置；M0-04 的迁移测试（两份都要测）；备份策略。

**你的决定**：**B（PostgreSQL）**。不采用推荐的 SQLite。理由由用户判定：Q2 全量 525 合约 + 决策/审计/会话数据量下，Postgres 的并发与查询性能更稳。影响：09 §1 存储选型改为 Postgres 为主（迁移仍双份提供）；`docs/localDeploy` 需补 Postgres  provisioning（docker）与切换步骤；备份策略改为 pg_dump + 加密；现有 dev 环境的 SQLite 库需迁移或弃用。

### Q12. `TimeInForce` 硬编码 GTC 是否可接受？

**背景**：币安 wrapper 把 `TimeInForce` 硬编码成 `"GTC"`（`binance_wrapper.go`），`order.Submit.TimeInForce` 字段被忽略。原项目的执行层大量使用 **IOC**（保护性退出的 IOC 准备、`protective-ioc.ts`），因为 IOC 能保证"要么立即成交要么取消"，避免挂单残留。

**可选项**：

| 选项 | 说明 | 取舍 |
| --- | --- | --- |
| **A** | **接受 GTC**。限价单挂着等成交，超时未成交则由 LLMManager 主动撤单（复用 `OrderManager.Cancel`） | **推荐**。需要自建挂单超时管理，但这本来就要做 |
| B | 改币安 wrapper 支持 `TimeInForce` 透传 | 小改动（几行），但动了核心交易代码 |
| C | 只用市价单（`MARKET` 不需要 TimeInForce） | 滑点不可控 |

**取舍**：

- A 需要自己实现"挂单超时管理"：意图里已经有 `expires_at`（默认 10 秒），到期未成交就撤。这比改 wrapper 更安全
- B 的改动很小（`binance_wrapper.go:896-940` 里把硬编码换成读 `s.TimeInForce`），但**会影响所有用币安的功能**，且与上游分叉

**推荐：A**。挂单超时管理本来就需要做（`llm_protective_exits` 的生命周期跟踪），IOC 不是必需的。

**影响范围**：M5-01、M5-07。

**你的决定**：**A（接受 GTC + 自建挂单超时管理）**。限价单超时未成交由 LLMManager 主动撤单（意图 `expires_at` 默认 10s）；保护性止损用 `STOP_MARKET`（币安侧 GTC 挂单，符合“止损单应一直挂着直到触发或撤”）。不改 `binance_wrapper.go`。

### Q14. 是否需要流式输出？

**背景**：原项目明确延后流式（"流式 `stream` 属于后续对话显示能力，策略候选在服务端得到完整响应并通过 schema 校验后才可进入风控"）。

**可选项**：

| 选项 | 说明 | 取舍 |
| --- | --- | --- |
| **A** | **首期不做**。对话响应等完整返回（4-20 秒），CLI 显示 spinner + 工具调用进度 | **推荐**。工具调用进度实时显示已能缓解大部分等待焦虑 |
| B | 做**展示层伪流式**：服务端拿到完整响应后，通过 `LLMChatStream` 逐字推送 | 体验接近流式，但不改变决策路径的安全性 |
| C | 做**真流式**（`stream: true`）：仅用于对话模式，决策模式禁用 | 体验最好，但要处理半截 JSON、中断恢复、token 计数延迟 |

**取舍**：

- **决策路径永远不能用流式**——半截 JSON 无法校验，进风控是灾难。这是底线
- 对话模式下 4-20 秒的等待确实影响体验，但**工具调用进度可以实时显示**（"正在查询 1h K 线…"、"正在计算 MACD…"），这已经缓解了大部分等待焦虑
- B 是个好折中：不改模型调用方式，只改推送方式
- C 的成本在于错误处理复杂度

**推荐：A 起步，B 作为 M3 的可选增强**。C 只在做了 Web UI（Q21 选 C）之后才值得。

**影响范围**：M3-07；`LLMChatStream` RPC。

**你的决定**：**C（真流式，仅对话模式）**。`stream: true` 只用于 `chat-analysis-v1` 对话路径；**决策路径（analysis/policy）永远非流式**，必须拿到完整响应并通过 schema 校验才进风控。需处理半截 JSON/中断恢复/token 计数延迟；Web UI（Q21=C）消费该流。

### Q15. 是否要做硬性的 USD 成本闸？

**背景**：原项目的诚实限制："`dailyBudgetUsd > 0` 是计划值而非硬闸；没有供应商价格表，没有每请求 USD 记账/结算"。

**可选项**：

| 选项 | 说明 |
| --- | --- |
| **A** | **保持原样**：`dailyBudgetUsd` 三态（null / 0=禁止 / 正数=计划值），硬闸用 token 计数 + 24h 预约次数 |
| B | 内置一张供应商价格表（手动维护），按 token 折算 USD，做硬闸 |
| C | 接供应商的用量/账单 API 做真实记账 |

**取舍**：

- A 的硬闸其实是够的：**预约次数上限（100 次/24h）+ 单次 token 上限（24000）= 每天最多 240 万 token**。按 DeepSeek 的价格（约 ¥1/百万输入 token）这是几块钱；按 GPT-4o 的价格（约 $2.5/百万输入 token）这是几美元。**上界是可算的**
- B 的问题是价格表会过期，且不同供应商、不同模型、不同时间价格差异大。维护成本高，准确性差
- C 最准但依赖供应商 API，且各家格式不同，与"不绑定供应商"的原则冲突

**推荐：A**，并在文档和 UI 里**明确展示 token 上界折算的成本估算**（用用户自己填的单价，而不是系统内置的价格表）。即：让用户在 Provider Profile 里填 `estimatedUsdPerMillionInputTokens` 和 `estimatedUsdPerMillionOutputTokens`（可选，仅用于展示和软告警）。

**影响范围**：`LLMBudgetConfig`；Provider Profile 字段；[05-LLM接入层](05-LLM接入层-OpenAI兼容.md) §7。

**你的决定**：**A（token 计数 + 24h 预约次数做硬闸）**。`dailyBudgetUsd` 保持三态语义（null 未设 / 0 禁止 / 正数计划值）。硬闸 = 100 次预约/24h × 24000 token/次 ≈ 240 万 token/天，上界可算。另在 Provider Profile 增加用户自估单价字段（`estimatedUsdPerMillionInput/OutputTokens`），仅用于展示与软告警，不做硬闸。

| MACD 参数 | 12 / 26 / 9 | **12 / 26 / 9** |

### Q19. 通知通道选哪个？

**背景**：GoCryptoTrader 支持 Telegram / SMTP / Slack / SMSGlobal（**没有通用 webhook**）。原项目只有 Web 展示，没有推送通道。

**可选项**（可多选）：

| --- | --- | --- | --- |
| **Telegram** | 低（建 bot 拿 token） | 高 | 需要代理（`communications.telegram.proxy` 支持） |

"communications": {

    "token": "<bot token from @BotFather>",

### Q24. 要不要保留并复用 gocryptotrader 的回测器？

**背景**：`backtester/` 是本仓库唯一的策略框架，支持实盘数据和真实下单。Q7 已经决定 LLM 决策走独立子系统，但回测器**本身**要不要用起来？

**可选项**：

| 选项 | 说明 | 价值 |
| --- | --- | --- |
| **A** | **保留作为对照基线工具**：写几个 `.strat` 配置（如"MACD 金叉买入、死叉卖出"的固定规则策略），在同样的历史数据上跑，与 LLM 决策的表现对比 | **高**。能回答"LLM 到底比固定规则好吗"这个根本问题 |
| B | 完全不管回测器 | 省时间，但失去对照 |
| C | 把 LLM 决策也做成回测器策略（Q7 的选项 B） | 已在 Q7 否决 |

**取舍**：

- A 的价值在于**科学方法**：没有对照组的实验说明不了什么。如果 LLM 决策的表现不如"MACD 金叉就买"这种最朴素的规则，那整套系统的价值就要打问号
- A 的成本很低：`backtester/eventhandlers/strategies/rsi/rsi.go` 已经是现成范例，照抄改成 MACD 版本约 100 行 Go + 一个 `.strat` 配置
- 回测器有完整的统计报告（收益、回撤、夏普等），不用自己写
- **这也是原项目缺失的一环**——它有 `paper_replays`（反事实估算）但没有真正的回测框架

**推荐：A**。作为 M6 的一部分（对照组实验），约 2-3 天工作量。

具体建议实现两个基线策略：

1. **MACD 交叉基线**：金叉开多、死叉平仓，固定仓位，无止损
2. **均线趋势基线**：价格上穿 200 SMA 开多、下穿平仓，固定仓位

然后在同一段历史数据上对比：LLM 决策 vs 基线 1 vs 基线 2 vs 什么都不做（buy & hold）。

**影响范围**：M6 的范围；是否需要写 `.strat` 配置和策略代码。

**你的决定**：**A（做两个固定规则基线）**。MACD 交叉基线（金叉开多/死叉平仓）+ 均线趋势基线（上穿 SMA200 开多/下穿平仓），固定仓位无止损，在同一段历史数据上与 LLM 决策、buy&hold 对比。纳入 M6，约 2-3 天。
