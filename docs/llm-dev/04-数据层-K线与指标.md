# 04 数据层：K 线、指标与快照

> **实现状态（2026-10-11）**：本文档是设计原稿。已实现落点、两处实测偏差（588 合约口径 / KlineWeight 分档）与全部已知残余见 [实现后状态对照](实现后状态对照.md)；进度与缺口以 [`taskProgress/`](taskProgress/) 为准。

本文定义"追踪任意一个永续合约的 K 线（MACD、均线）历史数据"这一核心需求的数据层设计。

**结论先行**：GoCryptoTrader 已经把这一层做完了。本方案的数据层工作**不是新建采集链路，而是设计如何有界地、带质量标签地把它喂给模型**。

## 1. 三条 K 线获取路径

| 路径 | 入口 | 数据源 | 延迟 | 权重消耗 | 适用 |
| --- | --- | --- | --- | --- | --- |
| **P1 数据库** | `kline.LoadFromDatabase(exch, pair, a, interval, start, end)` | SQLite/Postgres | 0 | 0 | 历史分析、对话问历史 |
| **P2 REST 现拉** | `IBotExchange.GetHistoricCandlesExtended(ctx, pair, a, interval, start, end)` | 币安 `/fapi/v1/klines` | 网络往返 | 1-10 / 请求 | 最新数据、数据库缺失区间 |
| **P3 回填任务** | `DataHistoryManager.UpsertJob(job, insertOnly)` | 币安 REST，批量分批 | 分钟级 | 受任务节流 | 首次建立历史库、补大段缺口 |

`kline.LoadFromDatabase` / `StoreInDatabase` 在 `exchanges/kline/kline_datastorage.go:15` / `:55`。

### 1.1 推荐组合策略

```text
需要 [start, end] 区间、间隔 I 的 K 线
   │
   ├─► 1. 查数据库：LoadFromDatabase(exch, pair, asset, I, start, end)
   │       └─ 用 TotalCandlesPerInterval(start, end, I) 对比实际根数
   │
   ├─► 2. 完整（且不含最近一根未收盘）？ → 直接用，quality = DATABASE_CACHED
   │
   ├─► 3. 缺最近 N 根？ → 只对缺失区间调 REST
   │       GetHistoricCandlesExtended(ctx, pair, asset, I, lastDBTime, now)
   │       quality = EXCHANGE_REST
   │
   ├─► 4. 缺中间大段？ → 合并 DB + REST 结果
   │       RemoveDuplicates() → SortCandlesByTimestamp(false) → addPadding()
   │       有零填充的区间标 quality = GAP
   │
   └─► 5. 需要比 DB 里更粗的间隔？ → ConvertToNewInterval(newI)
           前提：newI > I，整数倍，数据已 padding（否则 errCandleDataNotPadded）
```

`TotalCandlesPerInterval(start, end time.Time, interval Interval) uint64`（`exchanges/kline/kline.go:503`）是判断完整性的关键工具。

### 1.2 最后一根 K 线的处理

`Request.ProcessResponse`（`exchanges/kline/request.go:146`）会给时间窗口超过当前时间的最后一根打上 `ValidationIssues = "Partial Candle"`（常量 `request.go:25`），RPC 层映射成 `is_partial: true`。

**规则**：

- **算指标时默认排除未收盘的最后一根。** 理由：MACD 和均线对最后一根极其敏感，包含它会让指标随实时价格抖动，产生大量假信号，也会让"同一时刻的两次分析得出不同结论"，破坏可重放性。
- 但**要把未收盘 K 线的当前值单独作为一个事实**提供给模型（`liveCandle` 字段），标明 `quality = EXCHANGE_REST` + `partial = true`。模型需要知道"当前这一根走到哪了"。
- 触发器（K 线收盘事件）只在**收盘后**触发分析，此时最后一根已完整。

### 1.3 单次上限与分批

币安单次最多 1000 根（`GlobalResultLimit: 1000`，`binance_wrapper.go:167`）。`GetHistoricCandlesExtended` 会自动用 `CalculateCandleDateRanges(start, end, interval, limit)`（`kline.go:622`）切批，返回 `*IntervalRangeHolder`，逐批请求后合并，并打 `DataSummary` 缺口日志。

`GetHistoricCandles`（非 Extended）在窗口放不下时报 `kline.ErrRequestExceedsExchangeLimits`（`exchanges/exchange.go:1535`）。

**LLM 工具层一律用 Extended 版本**，避免模型请求一个拉不到的区间就报错。

### 1.4 间隔合成

币安启用 `1m,3m,5m,15m,30m,1h,2h,4h,6h,8h,12h,1d,3d,1w,1M`（`binance_wrapper.go:150-166`）。请求其它间隔时 `ExchangeIntervals.Construct`（`kline.go:812-874`）会尝试用更小间隔合成（例如 1h = 2×30m）。

`ConvertToNewInterval`（`kline.go:528`）的约束：**只能升采样**、必须整数倍、输入必须已 padding、末尾不完整组丢弃、零值 K 线跳过。

**规则**：LLM 工具的 `interval` 参数只接受币安原生间隔白名单，不让模型请求需要合成的间隔——合成路径的数据质量更难解释，而且会消耗更多权重。

## 2. 指标计算

### 2.1 用户明确要求的两个

| 指标 | 方法 | 签名 | 位置 |
| --- | --- | --- | --- |
| **MACD** | `GetMovingAverageConvergenceDivergenceOnClose` | `(fast, slow, signal int64) (*MACD, error)` | `exchanges/kline/technical_analysis.go:223` |
| **均线（SMA）** | `GetSimpleMovingAverageOnClose` | `(period int64) ([]float64, error)` | :163 |
| **均线（EMA）** | `GetExponentialMovingAverageOnClose` | `(period int64) ([]float64, error)` | :189 |

MACD 返回：

```go
type MACD struct {              // technical_analysis.go:214-218
    Results    []float64         // DIF / MACD 线
    SignalVals []float64         // DEA / 信号线
    Histogram  []float64         // 柱状图
}
```

**最小数据量**：`len(data) >= slow + signal - 2`，否则 `errNotEnoughData`（l.251）。默认 12/26/9 → **至少 33 根**。加上均线周期（比如 200 期 EMA），实际需要的窗口取所有指标需求的最大值。

### 2.2 建议的默认指标参数集

| 指标 | 参数 | 理由 |
| --- | --- | --- |
| MACD | fast=12, slow=26, signal=9 | 教科书默认，模型训练语料里最常见，减少误解 |
| SMA | 20, 50, 200 | 短/中/长期趋势 |
| EMA | 12, 26, 50, 200 | 与 MACD 的快慢线对齐 + 长期趋势 |
| **RSI（默认开，Q16）** | 14 | 超买超卖，模型熟悉 |
| ATR（可选） | 14 | **波动率，用于止损距离和仓位规模的参考**（不是权威） |
| **布林带（默认开，Q16）** | 20, 2, 2, SMA | 波动区间 |

### 2.3 窗口长度与权重的权衡

| 间隔 | 需要的根数（200 期均线） | 币安请求次数 | 权重 |
| --- | --- | --- | --- |
| 1m | 200 | 1 | 2（≤500 档） |
| 5m | 200 | 1 | 2 |
| 15m | 200 | 1 | 2 |
| 1h | 200 | 1 | 2 |
| 4h | 200 | 1 | 2 |
| 1d | 200 | 1 | 2 |

200 根远低于 1000 上限，**单次请求就够**。权重 2，2400 weight/min 的限额下每分钟可以拉 1200 次——完全不是瓶颈。

**但如果同时要多个间隔**（1m + 5m + 15m + 1h + 4h + 1d，用于多周期共振分析），一次分析就是 6 次请求 = 12 权重。加上 ticker、orderbook、funding、账户，单次决策约 20-30 权重。按每 5 分钟一次决策，每小时 240-360 权重，占限额的 10-15%。**安全**。

### 2.4 指标缓存

现有指标方法**无状态、无缓存**，每次调用重算。200 根的 MACD 计算是微秒级，**不需要缓存**。

需要缓存的是 **K 线本身**（避免重复打 REST）。缓存策略：

```text
LLMManager 内部维护 map[cacheKey]*kline.Item
cacheKey = {exchange, pair, asset, interval}
TTL：
  · 已收盘的 K 线 → 永久有效（历史不变）
  · 最后一根（未收盘）→ 不缓存，每次重取
淘汰：LRU，上限 = 启用交易对数 × 间隔数
失效：SetExchangePair 移除交易对时清除对应条目
```

**这是本方案唯一需要新建的"缓存"**，而且很简单。原项目没有指标层，所以没有这块。

## 3. MarketSnapshot 构造

一次决策运行的**有界事实输入**。构造后不可变，全程带同一个 `snapshotId`。

### 3.1 结构

```go
type MarketSnapshot struct {
    ID           uuid.UUID
    Exchange     string             // "Binance"
    Pair         currency.Pair      // BTC_USDT（config format）
    Asset        asset.Item         // asset.USDTMarginedFutures
    SourceTime   time.Time          // UTC，最新一根已收盘 K 线的结束时间
    BuiltAt      time.Time          // UTC，构造完成时间

    Candles      CandleWindow
    Indicators   IndicatorSet
    Ticker       TickerFacts
    OrderBook    OrderBookFacts
    Funding      FundingFacts
    Account      AccountFacts
    LiveCandle   *Candle            // 当前未收盘的那一根，可能为 nil

    Quality      map[string]DataQuality   // 键 = 事实类别
    FreshnessMS  int64
}

type CandleWindow struct {
    Interval    kline.Interval
    Start       time.Time
    End         time.Time
    Count       int
    Closed      []CandleFact        // 已收盘，用于指标
    Summary     CandleSummary       // 有界摘要，避免把 200 根全塞给模型
}

type CandleFact struct {
    Time   time.Time `json:"time"`    // UTC
    Open   string    `json:"open"`    // 十进制字符串
    High   string    `json:"high"`
    Low    string    `json:"low"`
    Close  string    `json:"close"`
    Volume string    `json:"volume"`
}

type IndicatorSet struct {
    MACD       *MACDFact
    MovingAverages []MovingAverageFact
    RSI        *SeriesFact          // 可选
    ATR        *SeriesFact          // 可选
    Bollinger  *BollingerFact       // 可选
    ComputedAt time.Time
    Params     IndicatorParams      // 记录实际用的参数，保证可重放
}

type MACDFact struct {
    Fast, Slow, Signal int64
    DIF                []string    // 只保留最后 N 个（默认 20）
    DEA                []string
    Histogram          []string
    CrossState         string      // "GOLDEN" / "DEATH" / "NONE"
    BarsSinceCross     int
    HistogramTrend     string      // "EXPANDING" / "CONTRACTING" / "FLAT"
}

type MovingAverageFact struct {
    Type   string    // "SMA" / "EMA"
    Period int64
    Values []string  // 最后 N 个
    Latest string
    PriceVsMA string // "ABOVE" / "BELOW"
    Slope     string // "UP" / "DOWN" / "FLAT"
}
```

### 3.2 有界性原则

原项目的工具返回上限是硬性的（`getMarketWindow` 最多返回 50 行，`getTradesWindow` 最多 30 条，单条工具响应 ≤12KB，总计 ≤32KB，Jev 请求体 ≤64KiB）。本方案沿用并具体化：

| 事实类别 | 上限 | 理由 |
| --- | --- | --- |
| K 线明细（`Candles.Closed`） | **最近 50 根** | 200 根全给模型是浪费 token 且无益；指标已经浓缩了长期信息 |
| 指标序列（每个） | **最近 20 个点** | 模型只需要看形态和最近趋势 |
| 盘口档位 | **每边 20 档** | 币安 REST 深度默认给到这个量级；再深对低频决策无意义 |
| 资金费率历史 | **最近 21 条**（约 7 天，8h 结算） | 覆盖一个完整周期 |
| 账户仓位 | **全部**（一般 < 10 个） | 不能截断，风控要用 |
| 单个工具响应 | **12 KB** | 原项目规则 |
| 全部工具响应合计 | **32 KB** | 原项目规则 |
| Jev 请求体 | **64 KiB UTF-8** | 原项目规则，超了整体拒绝不截断 |
| LLM 响应体 | **256 KB** | 原项目规则（`limitedJson`） |
| LLM 最终内容 | **12000 字符** | 原项目规则 |

**为什么给"摘要"而不是"原始序列"**：模型不需要 200 个 MACD 数值来判断金叉。它需要的是 `CrossState: "GOLDEN"`、`BarsSinceCross: 3`、`HistogramTrend: "EXPANDING"` 这种**结构化事实** + 最近 20 个点用于验证。这样：

1. token 消耗降一个数量级
2. 减少模型算错数的机会（模型不擅长数值计算）
3. 派生事实（金叉、斜率）由确定性 Go 代码算，可测试、可重放

### 3.3 派生事实的计算规则

这些是**确定性代码算出来的**，不是让模型看的原始数据里自己找的：

| 派生事实 | 计算规则 |
| --- | --- |
| `MACD.CrossState` | 比较 `Histogram[i-1]` 和 `Histogram[i]` 的符号：负→正 = `GOLDEN`，正→负 = `DEATH`，同号 = `NONE` |
| `MACD.BarsSinceCross` | 从末尾往前找最近一次符号翻转的位置 |
| `MACD.HistogramTrend` | `abs(H[i]) > abs(H[i-1])` = `EXPANDING`；`<` = `CONTRACTING`；相等（容差 1e-9）= `FLAT` |
| `MA.PriceVsMA` | `Close[last] > MA[last]` = `ABOVE`，否则 `BELOW` |
| `MA.Slope` | `MA[last] - MA[last-3]`，正 = `UP`，负 = `DOWN`，绝对值 < 0.01% × 价格 = `FLAT` |
| `OrderBook.SpreadBPS` | `(Ask[0] - Bid[0]) / Mid × 10000` |
| `OrderBook.ExecutablePrice` | 用 `Book.Movement` 按目标名义额算成交均价 |
| `Funding.AnnualisedPct` | `LatestRate × 每日结算次数 × 365 × 100` |
| `Account.UnrealisedPNLUSD` | 从 `futures.Position` 读，本地跟踪值 |

**这些派生事实是模型的"读数"，不是"结论"。** 明确禁止派生出 `SHOULD_BUY` 这类字段。

## 5. 数据质量分级（重新定义）

原项目的 `FULL / TOP20_ONLY / MID_ONLY / PUBLIC_AGGREGATE / GAP / STALE / UNKNOWN` 是为"自建 Hyperliquid 全深度节点"设计的——它的核心焦虑是"公共 `l2Book` 只有 20 档，不能冒充全深度"。

**这个焦虑在币安上不存在**：币安是中心化交易所，REST `/fapi/v1/depth` 直接给完整深度快照，不需要自建节点。原项目 22 个未完成点里的 12 个（节点采集）在本项目里**直接消失**。

但质量分级本身**必须保留**——它是"fail-closed"哲学的基础。重新定义：

| 标签 | 含义 | 触发条件 | 对决策的影响 |
| --- | --- | --- | --- |
| `EXCHANGE_REST` | 直接来自币安 REST，权威 | 本次请求成功返回 | 允许进入决策 |
| `LOCAL_TRACKED` | 本地 PositionController 跟踪值 | 来自 OrderManager 缓存 | **仅供模型参考**；风控放行前必须用 `EXCHANGE_REST` 复核 |
| `DATABASE_CACHED` | 数据库里的历史 K 线 | `LoadFromDatabase` 命中 | 允许（历史数据不变） |
| `DERIVED` | 由原始数据计算的指标/派生事实 | MACD、均线、金叉状态等 | 允许，但必须记录计算参数 |
| `PARTIAL` | 未收盘的 K 线 | `ValidationIssues == "Partial Candle"` | 只能作为"当前进展"，**不能用于指标计算** |
| `GAP` | 区间有缺口（含 `addPadding` 补的零值） | `TotalCandlesPerInterval` 对不上，或存在零值 K 线 | **强制 HOLD / TOOL_EVIDENCE_UNVERIFIED** |
| `STALE` | 超过新鲜度阈值 | 见 §6 | **强制 HOLD / MARKET_SNAPSHOT_STALE** |
| `UNKNOWN` | 无法确定 | 请求失败、盘口校验失败（`ErrBidEqualsAsk`）、数据源缺失 | **强制 HOLD** |

**核心不变量**（继承原项目）：**质量标签只能降级，不能升级。** 一旦某个事实被标成 `GAP` / `STALE` / `UNKNOWN`，后续任何处理都不能把它改回 `EXCHANGE_REST`。

## 6. 新鲜度阈值

**币安永续没有 WebSocket**（`binance_wrapper.go:75-79` 对 USDT-M 调 `DisableAssetWebsocketSupport`），所有实时数据来自 SyncManager 的 REST 轮询。所以阈值必须按**轮询周期**设定，不能按 WS 推送设定。

SyncManager 的 `timeoutREST` 默认 15 秒（`config_types.go:43`）。据此：

| 事实类别 | 阈值 | 超时行为 |
| --- | --- | --- |
| Ticker | 60 秒（Q9 定案） | `STALE` → 强制 HOLD |
| Orderbook | 60 秒（Q9 定案） | `STALE` → 强制 HOLD |
| 最新已收盘 K 线 | 2 × 间隔 + 60 秒 | `STALE` → 强制 HOLD |
| 资金费率 | 10 分钟 | `STALE`，但**不阻断**（变化慢）；标记后继续 |
| 本地仓位 | 60 秒（OrderManager 每 10s 同步） | `STALE` → 风控用交易所实时值 |
| 交易所实时仓位（执行前复核） | **5 秒** | 超时 → 拒绝提交 |
| 执行前盘口（滑点复核） | **5 秒** | 超时 → 拒绝提交 |

**为什么执行前是 5 秒而分析时是 60 秒**：原项目的规则是 `maxAccountInventoryAgeMs ∈ {5000, 10000}`（`ReviewablePolicySchema`），分析可以用稍旧的数据，但**签名/提交前必须是刚查的**。本方案沿用，并收紧到 5 秒。

**自动候选的截止时间（Q9 已定案 = C，60 秒）**：原项目是 `snapshot source time + 10 s`（为 WS 推送设计）。本项目数据源是 REST 轮询（15s），故定为 `snapshot source time + 60 s`，且不超过共同流水线截止时间（手动 90s）。对应 `LLMAnalysisConfig.autoCandidateWindowSeconds = 60`。

## 7. "追踪任意一个永续合约"的实现

用户明确要求"任意一个永续合约"。三种粒度的实现：

### 7.1 运行时动态启用（推荐）

```bash
gctcli pair enable --exchange Binance --asset usdtmarginedfutures --pairs SOL-USDT
```

对应 RPC `SetExchangePair`（`rpc.proto:1776`）。会写回配置（除非 dry-run）。**不需要重启。**

LLM 层需要提供一个对话式的封装：

```text
用户："帮我加上 SOL 永续"
  → LLM 调 listMarkets 工具确认 SOL_USDT 在 available 列表里
  → 返回"需要启用 SOL_USDT，确认？"
  → 用户确认
  → 调 SetExchangePair RPC（这是一个写操作，不能是 LLM 工具，必须由用户在 UI/CLI 显式触发）
```

**关键约束**：`SetExchangePair` 是**写操作**，绝不能进 LLM 的只读工具集。模型只能**建议**，用户或确定性代码才能**执行**。

### 7.2 全量启用（已定案，见 OPEN-QUESTIONS Q2）

配置里 `available` 由 `autoPairUpdates: true` 在启动时自动刷新（`exchange.Bootstrap`，`exchanges/exchange.go:1787-1829`，走 `/fapi/v1/exchangeInfo`，只把 `ContractType == "PERPETUAL"` 的当 base/quote 对）。`enabled` 直接放**全部 USDT-M 永续**。

实测规模（2026-10-10）：**USDT-M PERPETUAL 且 TRADING 状态 = 525 个**（含 USDC 等其它 quote 的全部 PERPETUAL 为 568 个）。

> ⚠ 旧的顾虑是"启用几百个交易对会让 SyncManager 每轮轮询几百次 ticker + orderbook，很快撞限频"。这个顾虑**只对 orderbook 成立**。ticker 有批量端点（`TickerBatching: true`），一次拿全部；orderbook 则改为**不进轮询、决策时按需拉取**。配合下面的两层轮询设计（§7.4），全量启用在权重预算内完全可行。

### 7.3 只查不追踪

对于"临时问一下某个合约"的场景，可以绕过 `enabled` 列表直接调 REST：

```go
// 不经过 enabled 校验的路径：直接用 exchange wrapper 的底层方法
candles, err := binanceExchange.UKlineData(ctx, pair, "1h", 200, start, end)
```

但这绕过了 `GetKlineRequest` 的交易对启用校验（`exchanges/exchange.go:1482`），**不推荐**。更干净的做法是允许 LLM 工具在 `READ_ONLY` 模式下查询 `available` 但未 `enabled` 的交易对，标记 `quality = EXCHANGE_REST` + `onDemand = true`，并且**这类快照永远不能进入决策流水线**（因为风控要求市场在批准列表里）。

**已定案（Q4 = B）**：允许 LLM 工具在 `READ_ONLY` 模式下查询 `available` 但未 `enabled` 的合约，标记 `onDemand = true`；**这类快照永远不能进入决策流水线**。Q2 全量启用后，此路径主要服务于"被手动 disable 的合约"与"新上市尚未被 autoPairUpdates 刷新的合约"。

### 7.4 全量覆盖的两层轮询预算设计（Q2 定案的落地）

**目标**（用户原话）：覆盖全部 525 个 USDT-M 永续，但不追求高频；**全量合约的最新一批数据在 5-10 分钟内刷新完**即可。

**核心思路：把"全量保温"和"决策取鲜"拆成两层。** 全量轮询只负责让 525 个合约的指标状态和触发器保持温热；真正进入决策的快照在决策时刻按需现拉，保证新鲜度是秒级而不是分钟级。这样既满足"5-10 分钟全量刷新"，又不让 Q9 的新鲜度门禁（60 秒）形同虚设。

#### 第一层：全量保温轮询（CoverageRotator）

新增组件 `CoverageRotator`（挂在 LLMManager 下，或作为独立 engine 子系统），周期 `rotationCycleMinutes`（默认 10，可配 5-10）。

| 数据 | 端点 | 调用次数/周期 | 权重/周期 | 说明 |
| --- | --- | --- | --- | --- |
| Ticker（全部 525） | `/fapi/v1/ticker/24hr`（无 symbol，批量） | **1** | 40 | `TickerBatching: true`，一次拿全部。SyncManager 设 `synchronizeTicker: true` |
| K 线增量（每合约） | `/fapi/v1/klines?limit=5` | 525 | 525 × 1 = 525 | `limit ≤ 100` → weight 1。只拉最近几根，检测是否收盘 + 更新未收盘值 |
| 资金费率（全部） | `/fapi/v1/premiumIndex`（批量）或 `GetLatestFundingRates` 批量 | 1 | 低 | `FundingRateBatching: {usdtmarginedfutures: true}` |
| **Orderbook** | — | **0** | **0** | **不进轮询**。决策时按需拉（见第二层） |

**合计 ≈ 565 weight / 周期**。摊到 10 分钟 = **56.5 weight/min**，仅占 2400 上限的 **2.4%**。

**错峰**：525 次 kline 调用不要集中在 1 秒内发出。按周期均摊：10 分钟 = 600 秒，525 次 → 约 0.875 次/秒，即每秒 1 次、weight 1/min 的匀速流。用一个 ticker channel + 速率令牌实现，或直接复用 gocryptotrader 内置限频器（`request.WithLimiter`，`-ratelimiter` 默认开）做兜底。

**新 K 线收盘时的全量重载**：1h 间隔在整点收盘，此时 525 个合约都需要拉 250 根重算指标（`limit ≤ 500` → weight 2），合计 **1050 weight**。在 5 分钟内摊开 = 210 weight/min，加上常规轮询仍 < 2400。**可接受**。若担心尖峰，可只对"当前有批准策略的市场"做整点全量重载，其余合约延后到下一个周期。

**触发器检测**：第一层维护每个合约的指标增量状态（MACD 柱符号、均线相对位置）。整点重载后扫描 525 个合约，产出触发事件（如"BTC_USDT MACD 柱翻正"）。这就是"全量覆盖"对决策的实际价值：**任何合约出现信号都能被发现**，而不限于少数几个。

#### 第二层：决策时刻按需取鲜

当某个合约被触发（或手动触发）进入决策流水线时，`MarketSnapshotBuilder` 对该**单个**合约现拉：

| 数据 | 权重 | 新鲜度 |
| --- | --- | --- |
| K 线（最近 1 根已收盘 + 当前未收盘） | 1 | 秒级 |
| Ticker | 0（读第一层缓存，但校验 `LastUpdated` ≤ 30s；超了则现拉，weight 1-2） | 秒级 |
| Orderbook（`limit=100` → weight 5，或 `limit=20` → weight 2） | 2-5 | 秒级 |
| 资金费率 | 读第一层缓存 | ≤ 周期 |
| 账户/仓位 | 1-5 | 秒级（执行前复核 ≤5s） |

**单次决策 ≈ 10-15 weight**。即使每分钟触发几次决策，也远在预算内。

**这就是 Q9（60 秒新鲜度窗口）作用的地方**——它约束的是第二层的快照，不是第一层的轮询周期。两层各司其职：

- 第一层周期（5-10 min）决定**触发器能多快发现信号**
- 第二层现拉决定**决策依据的数据有多新**

#### 存储与间隔选择

| 间隔 | 行/天（525 合约） | 一年 | SQLite 可行性 |
| --- | --- | --- | --- |
| 1h | 12,600 | ~460 万行 | ✅ 可行（建议） |
| 4h | 3,150 | ~115 万行 | ✅ |
| 15m | 50,400 | ~1840 万行 | ⚠ 勉强，建议 Postgres |
| 1m | 756,000 | ~2.8 亿行 | ❌ 不可行 |

**默认只持久化 1h / 4h / 1d**。15m 及以下间隔的指标在内存里按需算（从 1h 无法降采样到 15m，所以 15m 指标需要现拉 15m K 线，不入库）。

#### 配置项

```json
"coverage": {
  "enabled": true,
  "scope": "ALL_USDTM_PERPETUAL",     // 或显式列表
  "rotationCycleMinutes": 10,          // 5-10
  "klineIncrementLimit": 5,
  "klineFullLimit": 250,
  "fullReloadSpreadMinutes": 5,        // 整点全量重载的摊开时长
  "weightBudgetFraction": 0.6,         // 轮询最多占用限频上限的 60%，留余量给按需查询
  "persistIntervals": ["1h", "4h", "1d"]
}
```

`weightBudgetFraction` 是硬闸：CoverageRotator 自己维护一个滑动窗口权重计数，超过 `2400 × 0.6 = 1440 weight/min` 就暂停轮询让路。这保证用户手动查询和决策取鲜永远不会被轮询挤占。

## 8. 指标是证据，不是权威

这是本方案对用户原项目哲学的**继承 + 调整**，需要明确说清楚。

### 8.1 原项目的立场

`hyperliquid-auto-trader/docs/04-strategy-ai.md` 原文：

> 因此，系统不是"写死买卖指标"；买卖假设由用户策略和当时数据驱动，LLM/Jev 协助分析。硬风控使用确定性规则，是安全边界而非获利策略。

该项目**全仓库没有任何指标计算**（grep `MACD|均线|moving average|EMA|indicator` 零命中），这是刻意的。

### 8.2 本方案的调整

用户明确要求 MACD 和均线，而且 GoCryptoTrader 已经有完整实现。所以：

**保留的哲学**：

- ❌ 不写 `if MACD 金叉 then 买入` 这类硬编码规则
- ❌ 指标不直接产生订单
- ❌ 指标不参与仓位规模计算
- ✅ 指标作为**只读工具的输出**进入模型上下文，和 K 线原始数据、盘口、资金费率、账户事实**平等地**构成证据链
- ✅ 模型必须**引用证据**（`evidenceRefs`）才能给出非 HOLD 的候选
- ✅ 派生事实（金叉状态、斜率）由确定性代码算，但**只是描述，不是指令**

**新增的能力**：

- ✅ 指标可以作为**触发器**（K 线收盘 + MACD 柱翻正 → 触发一次分析）。触发≠决策，触发后仍然走完整的 LLM + Jev + 风控链路。
- ✅ 用户可以在自然语言策略里引用指标（"MACD 金叉且价格在 200 期 EMA 上方时考虑做多"）。这句话被提取成**结构化的策略条款**，作为模型的 `strategyInstruction`，而不是硬编码的 if-else。

### 8.3 为什么这样设计

如果把指标写成硬规则，就不需要 LLM 了——直接写个 Go 策略就行（`backtester/eventhandlers/strategies/rsi/rsi.go` 就是这种形态）。用户要 LLM 的价值在于：

1. **综合多个弱信号**（MACD + 均线 + 资金费率 + 持仓量 + 波动率 + 账户状态）做整体判断
2. **理解用户的自然语言意图**（"趋势明确时才做"、"避免在结算前开仓"）
3. **给出可解释的理由**（`thesis` + `invalidation`）
4. **在证据不足时明确说不知道**（`HOLD` + `uncertainty: HIGH`）

指标是这个综合判断的**输入之一**，不是**输出**。

## 9. 与 DataHistoryManager 的协作

首次建立历史库的流程：

```bash
# 1. 启用数据库 + DataHistoryManager（配置）
# 2. 跑迁移和 seed
cd cmd/dbmigrate && go run . -command up
cd ../dbseed && go run .

# 3. 为每个要追踪的合约建回填任务
gctcli datahistory addjob savecandles \
  --nickname=binance-usdtm-btc-1h --exchange=binance \
  --asset=usdtmarginedfutures --pair=BTC-USDT --interval=3600 \
  --start_date="2023-01-01 00:00:00" --end_date="2026-10-01 00:00:00" \
  --request_size_limit=1000 --max_retry_attempts=3 --batch_size=3

# 4. 监控
gctcli datahistory getjobstatussummary --nickname binance-usdtm-btc-1h
gctcli findmissingsavedcandleintervals --exchange Binance --pair BTC-USDT \
  --asset usdtmarginedfutures --interval 3600 \
  --start "2023-01-01 00:00:00" --end "2026-10-01 00:00:00"
```

**LLMManager 应该在建任务这件事上提供辅助**：用户在对话里说"我要追踪 BTC 永续最近三年的 1 小时线"，系统计算出需要 3×365×24 = 26280 根，分 27 批（每批 1000），预计权重 27×10 = 270，然后**生成任务提案让用户确认**——而不是自己建任务（建任务是写操作）。
