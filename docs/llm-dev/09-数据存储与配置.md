# 09 数据存储与配置

> **实现状态（2026-10-11）**：本文档是设计原稿。已实现落点、两处实测偏差（588 合约口径 / KlineWeight 分档）与全部已知残余见 [实现后状态对照](实现后状态对照.md)；进度与缺口以 [`taskProgress/`](taskProgress/) 为准。

## 1. 存储选型

### 1.1 不引入新存储

原项目用 **PostgreSQL（104 表 / 118 迁移）+ Redis + ClickHouse + 不可变对象归档**四种存储。

本方案**只用 GoCryptoTrader 已有的数据库层**（SQLite 或 Postgres，`database/` 包 + sqlboiler 模型 + goose 迁移）。理由：

| 原项目的存储 | 动机 | 本方案是否需要 |
| --- | --- | --- |
| PostgreSQL | 应用事实与审计 | ✅ 需要，但 SQLite 也够（单机低频） |
| Redis | 热缓存 + 频率快速预检 | ❌ 不需要。频率计数直接查 SQL（低频，每分钟几次） |
| ClickHouse | 海量逐笔 + 盘口 diff 的列式投影 | ❌ 不需要。不采集逐笔，K 线走现有 `candle` 表 |
| 对象归档 | 节点小时级原始文件 | ❌ 不需要。没有自建节点 |

**数据量估算**（SQLite 可行性）：

| 数据 | 单条大小 | 每天条数 | 每天体积 | 一年 |
| --- | --- | --- | --- | --- |
| K 线（20 个合约 × 1h） | ~120 B | 480 | 56 KB | 20 MB |
| K 线（20 个合约 × 1m） | ~120 B | 28800 | 3.4 MB | 1.2 GB |
| decision_runs | ~8 KB（含转录） | 48 | 384 KB | 140 MB |
| chat_messages | ~4 KB | 200 | 800 KB | 290 MB |
| audit_events | ~1 KB | 500 | 500 KB | 180 MB |

**结论（Q20 已定案 = B，PostgreSQL 为首选）**：全量 525 合约（Q2）+ 决策/审计/会话数据下，Postgres 的并发与查询性能更稳，故**首选 PostgreSQL**；SQLite 仅作为无 docker 环境下的回退。迁移文件仍按仓库约定同时提供 postgres 与 sqlite 两份。provisioning 与切换步骤见 `docs/localDeploy/06-数据库与历史K线.md` §11（该节已随 Q20 升级为推荐配置）。

### 1.2 事实表不可变

原项目用数据库触发器禁止 UPDATE/DELETE。本方案沿用：

```sql
-- sqlite 版
CREATE TRIGGER llm_decision_runs_immutable
BEFORE UPDATE ON llm_decision_runs
BEGIN
    SELECT RAISE(ABORT, 'llm_decision_runs is immutable');
END;

CREATE TRIGGER llm_decision_runs_no_delete
BEFORE DELETE ON llm_decision_runs
BEGIN
    SELECT RAISE(ABORT, 'llm_decision_runs is immutable');
END;
```

Postgres 版用 `RAISE EXCEPTION`。

**不可变的表**：`llm_decision_runs`、`llm_chat_messages`、`llm_strategy_approvals`、`llm_audit_events`、`llm_order_intents`、`llm_risk_evaluations`、`llm_budget_reservations`、`llm_day_start_inventory`、`llm_provider_probe_results`。

**可变的表**：`llm_conversations`（标题、归档）、`llm_strategies`（名字、归档）、`llm_strategy_versions`（state 字段，走状态机）、`active_model_pair`（CAS 更新）、`llm_provider_profiles`（enabled 标志）、`llm_market_trade_grants`（撤销字段）、`llm_halts`（清除字段）。

**注意**：`llm_strategy_versions.state` 可变，但 `frozen_json` / `strategy_hash` / `risk_envelope_hash` 一旦写入就不可改——用触发器做**列级**保护：

```sql
CREATE TRIGGER llm_strategy_versions_frozen_immutable
BEFORE UPDATE ON llm_strategy_versions
WHEN OLD.frozen_json IS NOT NULL
     AND (NEW.frozen_json <> OLD.frozen_json
          OR NEW.strategy_hash <> OLD.strategy_hash
          OR NEW.risk_envelope_hash <> OLD.risk_envelope_hash
          OR NEW.source_prompt_cipher <> OLD.source_prompt_cipher)
BEGIN
    SELECT RAISE(ABORT, 'frozen strategy version fields are immutable');
END;
```

```sql
SELECT COUNT(*) FROM llm_new_risk_counters
WHERE account_id = ?
  AND scope = 'ACCOUNT'
  AND counted_at > ?          -- now - 300min，UTC
  AND released_at IS NULL;
```

## 3. 迁移策略

### 3.1 遵循现有约定

`database/migrations/` 下每个迁移是一个目录，含 postgres 和 sqlite 两份 SQL，目录名 `<timestamp>_<name>`。现有 23 个，从 `20190916104959_audit_event` 到 `20210709133512_candle_details`。

新增（按依赖顺序，**不要合成一个大迁移**）：

```text
database/migrations/
├── <ts>_llm_provider_core/          # profiles, revisions, active_pair, probes, switches
│   ├── 20261008_llm_provider_core.sql        (postgres)
│   └── 20261008_llm_provider_core.sql        (sqlite)
├── <ts>_llm_conversation_store/     # conversations, chat_messages
├── <ts>_llm_strategy_store/         # strategies, versions, approvals, grants, transitions
├── <ts>_llm_decision_store/         # snapshots, decision_runs, risk_evaluations
├── <ts>_llm_order_store/            # order_intents, protective_exits
├── <ts>_llm_budget_store/           # reservations, new_risk_counters
├── <ts>_llm_reconciliation_store/   # day_start_inventory, external_flows, reconciliations, halts
├── <ts>_llm_audit/                  # audit_events
└── <ts>_llm_immutability_triggers/  # 全部不可变触发器（单独一个迁移，便于审查）
```

**目录名格式**要与现有一致（`database/database_types.go:33-34` 的 `MigrationDir`）。跑迁移：

```bash
cd cmd/dbmigrate && go run . -command up
```

### 3.2 sqlboiler 模型

迁移写完后重新生成模型：

```bash
make gen_db_models        # Makefile:72-83，DRIVER ?= psql
```

### 4.3 配置版本迁移 v18

按 `docs/CODING_GUIDELINES.md` §配置迁移的规则：

1. 新建 `config/versions/v18/`（对照现有 `v17`）
2. 在 `config/versions/register.go` 注册
3. `config/config_types.go` 里 `Config.Version` 的当前版本常量改成 18
4. 迁移逻辑：v17 → v18 只做一件事——**如果 `llm` 段缺失，插入默认值（`enabled: false`）**
5. **绝不改写历史版本**
6. 迁移专用类型保持本地（在 `v18/` 包内定义，不污染 `config` 包）

**Migration Guards 要求**（规范里明确列的）：

- 归一化匹配：不能因为键顺序或大小写差异漏判
- 通配符范围：本迁移不涉及
- 显式 false / true / omitted / null 要区分：如果用户已经写了 `"llm": {"enabled": false}`，迁移**不能**覆盖成默认值
- 守卫两侧都要测：有 `llm` 段和没有 `llm` 段的配置都要测
- no-op 时也要推进版本号：即使配置已经有 `llm` 段，版本号也要从 17 升到 18

**关键规范**：改默认值和 `config_example.json` **不会**迁移已有安装。必须通过真实加载器测试（`config.ReadConfigFromFile`），不能只测迁移函数。

## 5. 密钥保管

### 5.1 方案选择

| 方案 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 复用 gocryptotrader 配置加密** | LLM/Jev key 放 `config.json`，整个文件用 `encryptConfig: 1` 加密成 `config.dat` | 零新增代码，与交易所 Key 同一套体系 | 整个配置一起加解密，粒度粗；每次读配置都要解密全部 |
| **B. 独立 vault 文件（原项目做法）** | 单独的 `llm-vault/` 目录，RSA-OAEP 包裹 AES-GCM 数据密钥，PG 只存 `secret://llm/<uuid>` 引用 | 粒度细，模型密钥与交易配置物理隔离；可以只让 LLM 子系统解密 | 需要新增 `llm/secrets` 包 |
| **C. 环境变量** | `GCT_LLM_API_KEY` | 最简单 | **违反编码规范**（不便于审计、易泄露到日志/进程列表）；不支持多档案 |

**已定案（Q22 = A 包级隔离 + 独立 vault，即原 B 方案的密钥结构）**，理由：

1. **底线 2 要求模型层与交易层隔离**。方案 A 下，任何能读 `config.dat` 的代码（包括交易所 wrapper）都能拿到模型密钥，反之亦然。
2. 原项目已验证这套设计（`docs/14-local-https-model-secrets.md`）：`model-vault:init` 生成 3072 位 RSA 密钥对，每个模型 API Key 用随机 AES-256-GCM 数据密钥加密，数据密钥再用 RSA-OAEP-SHA256 包裹；文件权限 0600/0700；数据库只存 `secret://model/<UUID>` 引用 + 截断的 SHA-256 指纹。
3. Go 侧实现成本低：`crypto/rsa` + `crypto/aes` + `crypto/cipher` 都是标准库。

**简化点**：原项目把解密放在**独立的 ai-worker 进程**里，通过 0600 权限的 Unix socket 通信（`HAT_AI_WORKER_SOCKET`）。本方案在单进程内，改为**包级隔离**：只有 `llm/secrets` 包能读私钥文件，`llm/openai` 和 `llm/jev` 通过 `secretFn func(ctx) (string, error)` 回调拿解密后的密钥，用完立即从内存清除（`defer runtime.KeepAlive` + 显式清零字节切片）。

**这是相对原项目的隔离强度下降，需要用户确认。见 OPEN-QUESTIONS Q22。**

### 5.2 Vault 目录结构

```text
~/.gocryptotrader/llm-vault/          （权限 0700）
├── vault-private.pem                 （0600，RSA 3072 私钥）
├── vault-public.pem                  （0644，公钥，用于加密新密钥）
├── secrets/
│   ├── <uuid-1>.json                 （0600，{wrappedDataKey, ciphertext, nonce, fingerprint}）
│   └── <uuid-2>.json
└── conversation-key.bin              （0600，AES-256 会话加密密钥）
```

初始化命令（新增到 gctcli 或独立 `cmd/llmvault`）：

```bash
gctcli llm vault init            # 生成 RSA 密钥对 + 会话密钥
gctcli llm vault add --kind LLM_OPENAI_COMPAT --name "DeepSeek"   # 从 stdin 无回显读 key
gctcli llm vault list            # 只显示指纹，绝不回显密钥
gctcli llm vault remove --id <uuid>
```

**读密钥必须无回显**（原项目：`live probe takes keys via no-echo TTY stdin only`）。Go 侧用 `golang.org/x/term.ReadPassword`。

### 5.3 永不回显

编码规范明确要求："never log or return credentials in errors, RPC responses or test output"。具体落地：

- 数据库只存 `api_key_ref` (`secret://llm/<uuid>`) + `api_key_fingerprint`（SHA-256 前 8 字节 hex）
- `GetConfig` RPC 返回的配置里，LLM 段**不含**任何密钥字段
- 日志里只打指纹
- 错误信息里绝不包含请求体（可能含 `Authorization` header）
- `llm_chat_messages` 的 `tool_transcript` 已经过敏感键扫描（[05](05-LLM接入层-OpenAI兼容.md) §4.3 的第四道闸）

### 5.4 会话内容加密（Q17 已定案 = C：标题明文 + 正文加密）

沿用原项目的三态方案（[05](05-LLM接入层-OpenAI兼容.md) §8.3 推荐 C）：

- `llm_conversations.title` —— **明文**（可 SQL 搜索）
- `llm_chat_messages.content_cipher` —— **AES-256-GCM 加密**，`content_nonce` 单独存，`content_sha256` 存明文哈希用于完整性校验
- AAD（附加认证数据）= `message_id`，防止密文被搬到别的行
- 密钥 = `llm-vault/conversation-key.bin`

## 6. 数据保留与备份

### 6.1 保留策略

| 数据 | 保留期 | 理由 |
| --- | --- | --- |
| `llm_decision_runs` | **永久** | 审计链的核心，删了就断了 |
| `llm_market_snapshots` | 90 天 | 体积大（每条 8-32 KB），但复盘需要 |
| `llm_risk_evaluations` | 永久 | 体积中等，是"为什么拒了"的唯一记录 |
| `llm_order_intents` | 永久 | 订单溯源 |
| `llm_chat_messages` | 180 天 | 对话量大，价值随时间衰减 |
| `llm_audit_events` | 永久 | 体积小，价值高 |
| `llm_budget_reservations` | 90 天 | 只用于成本分析 |
| `llm_provider_probe_results` | 90 天 | 只需最近的 |
| K 线（现有 `candle` 表） | 用户决定 | 见 `docs/localDeploy/06-数据库与历史K线.md` |

**注意**：不可变触发器禁止 DELETE。清理要走**归档 + 分区**或显式的 `PRAGMA` / 迁移，不能用普通 DELETE。

**已定案（Q18 = A，永久保留）**：不做归档/分区/删除。事实表的不可变触发器（禁 DELETE）与永久保留天然一致；Q20 已定 PostgreSQL，容量无忧（估算一年约 700 MB，不含 1m K 线）。不引入归档与恢复工具的复杂度。

### 6.2 备份

```bash
# PostgreSQL（Q20 定案）：pg_dump 逻辑备份 + 加密
pg_dump -h 127.0.0.1 -U postgres gocryptotrader | gzip | age -r <recipient> > gct-$(date +%Y%m%d).sql.gz

# SQLite（仅当回退到 SQLite 时）：停程序后备份
kill -INT "$(cat /tmp/gct.pid)"
cp ~/.gocryptotrader/database/gocryptotrader.db ~/backups/gct-$(date +%Y%m%d).db
cp ~/.gocryptotrader/config.dat ~/backups/config-$(date +%Y%m%d).dat
tar czf ~/backups/llm-vault-$(date +%Y%m%d).tar.gz -C ~/.gocryptotrader llm-vault
chmod 600 ~/backups/*.tar.gz ~/backups/*.db ~/backups/*.dat

# 在线备份（不停程序）
sqlite3 ~/.gocryptotrader/database/gocryptotrader.db ".backup '~/backups/gct-live.db'"
```

原项目的做法：AES-256-GCM 加密的 PG 逻辑备份 + 隔离的恢复演练。本方案建议至少做到：

1. 备份文件加密（`age` 或 `gpg`）
2. **定期做恢复演练**——没验证过的备份等于没有备份
3. `llm-vault` 单独备份且异地存放（丢了就解不开所有模型密钥）
