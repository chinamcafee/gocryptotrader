## 3. 交叉是"去看一眼的理由"，不是"动手的理由"

这是 Q5b 双节奏的实现：

```text
1h 扫描（全部合约）→ 出现信号 → 记入待确认集
                    ↓ 等 4h
4h 复核：信号仍在 → 升级为事件；信号已反转 → 不算数
```

`Event.NeedsConfirmation` 标记哪些需要复核。`ConfirmInterval` 默认 4h。

**为什么必须这样**：1 小时级 MACD 柱翻转噪声太多，直接据此调用 LLM+Jev 会让系统在噪声上抽搐，每个信号还都要花掉几千 token。**降低触发次数比提高模型判断力便宜得多**。

**复核不是定时器**，是"下一次观察到同一市场再次出现同一信号"。定时器会确认一个已经反转的信号——而那正是这条规则要滤掉的噪声。

**复核时钟不因再次出现而重置**：否则一个持续闪烁的信号永远等不到复核（每次都把窗口往后推）。

## 4. 测试抓出的一个真实缺陷：死叉会"确认"金叉

第一版待确认集的键是 `(market, kind)`。测试 `TestScannerDropsASignalThatDoesNotSurvive` 直接把它抓出来：

- 金叉出现 → 记入待确认（键 = `BTC_USDT|MACD_CROSS`）
- 4 小时后**死叉**出现 → 查同一个键 → 找到待确认项且已过窗 → **升级为事件**

也就是说：**一个反向信号会替前一个信号完成确认**，死叉会给金叉背书。而这两者是同一条线的相反读数——升级哪一个，风控都会据此决策。

**修法**：`Event.Subject` 带上"变动的方向/内容"（交叉记新符号 `+`/`-`，穿越记新位置 `ABOVE`/`BELOW`），键变成 `(market, kind, subject)`。

这条也解释了为什么"复核"必须识别**内容**而不只是**种类**：种类相同、内容相反的两个信号，语义上是对立的。

修完后 `Pending` 变成 2（两个信号各自等待），这是正确行为——测试改为断言这一点，并断言较早的那个先被 `Settle` 淘汰。

## 5. 其余五个判断

### 5.1 经过零点不算穿越

```go
if fact.HistogramSign != fact.PreviousHistogramSign &&
	fact.HistogramSign != SignZero && fact.PreviousHistogramSign != SignZero {
```

柱值从负走到**恰好 0** 不是穿越——零点不属于任何一侧。若把"到 0"和"离 0"都算穿越，那么一次由负到正的翻转会**双触发**（负→0 一次、0→正一次）。

`Sign` 用三态而不是 float 正是为此：**问的是"在零点哪一侧"，而比较浮点是否变号会把平值那一步读成两次穿越**。

### 5.2 首次读数不算突增

`PreviousATR == 0` 时不可比。若把 0 当基准，每个市场在**第一次扫描**时都会看起来像波动率暴涨——几百个假触发一次涌出来。测试专门断言这一条。

### 5.3 去抖动按市场

`MinInterval`（默认 1 分钟）把同一市场同时刻的多个触发收敛成**一条"去看"的理由**。几个触发器一起说"这个市场该看看"是一个时刻，不是几个时刻。

测试同时断言它是**按市场**而非全局的——否则一个活跃市场会把其它市场全压住。

### 5.4 队列有界，且丢最旧

消费者（决策流水线）**可能很慢，甚至还不存在**。生产者永不停止而消费者可能缺席 ⇒ 无界队列就是内存泄漏的另一种写法。上限 256，满了丢最旧：问"刚刚发生了什么"的人要的是最近的答案。

`Dropped` 计数上报，让慢消费者可见。测试断言丢的是最旧的那几个。

### 5.5 待确认集要淘汰

只出过一次信号、之后再也不出的市场会**永久留在待确认集里**，集合随"历史上出过信号的市场数"增长。`Settle` 在超过两倍复核间隔后丢弃它（两倍：一个间隔等复核，一个因为复核本身按扫描节奏走）。测试断言窗口内不淘汰、过窗后淘汰。

## 6. 整点全量重载（M2-16）

并进 `Rotator.Step`，作为第三种步类型。

**为什么重载要优先于增量**：指标只与**它算自的那个窗口**一样好。增量只拉最近几根，**重建不了**指标窗口——所以整点（1h 收盘）之后必须把每个市场的完整历史重新拉一遍。优先级不是偏好，是正确性。

**窗口**：整点后 `fullReloadSpreadMinutes`（默认 5）分钟。**为什么不一次性全拉**：这是本文件里唯一一条瞬时权重会是"所有市场之和"而非"一个市场"的路径。摊开的算术已经在 `coverage.Budget` 里算好（1176 weight ÷ 5min = 235/min，加轮询 63.8/min，峰值 299/min < 预算 1440/min）。

**每市场每小时一次**：`reloadHour` 记本次重载属于哪个整点，同一小时内已完成就不再开始——否则一个市场的重载会在整个 5 分钟窗口里反复触发。

**权重计入同一个闸**：重载与增量共用滑动窗口，所以决策取鲜依旧找得到额度。`klineWeightFor` 是 `coverage` 分档表的一份本地副本（那张表未导出），并有测试断言它**等于** `coverage.Budget` 里的每市场重载假设——**副本与权威之间加了机器化对照**，否则预算描述的是轮询并不产生的负载。

## 7. 测试夹具的时间（一次批量修正）

新增重载后，**11 个既有夹具从 12:00:00 挪到 12:10:00**。原因：整点是重载窗口，而它们测的是增量路径。夹具停在整点会走到另一条代码路径上——测试仍然"通过"，但测的不是它想测的东西。

`TestFullReloadDoesNotRepeatWithinTheSameHour` **刻意**留在 12:00:30（它问的正是"窗口还开着时已完成的这次重载会不会重来"）。

**顺带记录一个顺序事实**：整点那一步先是 TICKER_BATCH（ticker 检查在 `Step` 里排第一），然后才是重载。三处测试因此都需要 "先一步 ticker、再几步重载" 的结构。这不是实现细节——**ticker 到周期就该刷，重载到整点就该跑，两者都不能被对方跳掉**。

## 10. 给接手模型的具体建议

**第一层（温数据 + 扫描）与组装器都齐了。链路的下一个断口在决策流水线（M3/M4/M5）** ——没有任何东西会读触发事件、问模型、过风控、下单。

按杠杆排序：

1. **`M2-16` 已闭环，但扫描器没有调用方**（§8 第一项）。**这是一处需要设计的接缝**：执行器只取数、不组装快照，而事实来自快照。两条路——(a) 执行器为每个市场组装一次轻量快照（贵：588 次指标计算/周期），(b) 扫描器直接从增量结果构造事实（省，但需要从 `kline.Item` 现算 MACD 柱符号与均线位置）。**建议 (b)，并且在写之前先确认 `coverage` 的权重预算能否覆盖它**。
2. **`M0-06` → `M0-07` → `M1-09`~`M1-13`**——决策记录要落库。pg 前置已就位（`docker compose up -d postgres`）。
3. **proto 工具链校准**（`TASKS.md` §0.1）——挡 `M1-14`/`W7-07`/W5-W6 接口层，挡面最广的单项。

**做下一段时请沿用本会话的两条做法**：

- **注入时间**：`Detect` 是纯函数，`TriggerScanner` 的时钟可注入，所以 22 个测试没有一个真的等过 4 小时。**能注入的时间不要自己取**。
- **写"必须拒绝"的同时写"必须放行"**：本会话的四个缺陷里，两个（经零点、首次读数）会让**假触发大量涌出**，另外两个（按种类建键、队列无界）会让**真信号被吞或内存增长**。只测一侧的测试抓不到另一侧。

**另**：`TriggerScanner.limit` 默认 256 是**猜的**，依据是"一次决策队列不该超过这个量"。没有实测支撑——若后续发现触发风暴是真的，这个值需要重算。
