### 后端

1. `gctrpc/rpc.proto` +`LLMGetUsage`（GET `/v1/llm/usage`）+ `LLMUsageLine`/请求/响应；`buf generate` 连跑幂等 `4ac5592c7794cfb74fac8958de6d2eb7c662ae0a`。
2. `engine/rpcserver_llm_usage.go`（新）：
   - 窗口缺省 24h、**上限 720h**——无界扫描是一个 RPC 背后的延迟炸弹；
   - **只计 `state=USED`**：在途（RESERVED）没结算、已释放（RELEASED）没跑起来——把后者计入用量就是把没花掉的算成花了；
   - 按 provider kind × purpose 聚合（次数/token/均值延迟），排序保证响应确定性；
   - **未激活配对 = 空用量是状态**（与 LLMGetStatus 同口径）；未装配 fail-closed。
   - **「自估成本刻意缺席」**：schema 无任何价目源（provider 修订版没有价格列）——猜出来的美元数字比缺席的字段更糟（session-40 诚实纪律）；成本展示等有价目源的那天。
3. 测试（真库）：两 kind×三 purpose 聚合 + 均值延迟 + **窗口外（30h 前）/RELEASED 均不入账** + totals + 720 钳制 + fail-closed。**测试坑**：token 列在**结算时**写入——直插初始行不带 token（首跑全零），seed 必须走生产路径（insert RESERVED → `SettleBudgetReservation`）。另修正一处断言算式笔误（50+80+300+120=550 而非 600）。
