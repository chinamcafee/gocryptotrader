# 06 数据库与历史 K 线

要让系统"追踪任意永续合约的 K 线历史数据"，需要把 K 线落到数据库里。本文覆盖从建库到批量灌历史数据的完整流程。

## 1. 为什么需要数据库

不开数据库也能用：`gethistoriccandles` / `gethistoriccandlesextended` 每次都直接打币安 API 现拉。但这样有三个问题：

| 问题 | 影响 |
| --- | --- |
| 权重消耗 | USDT-M 合约限额 2400 weight/min，K 线按 limit 分档计费：≤100 根 = 1，≤500 根 = 2，≤1000 根 = 5，>1000 根 = 10（`exchanges/binance/binance_ufutures.go:183-222`） |
| 延迟 | 每次分析都要等网络往返，LLM 对话场景体验差 |
| 无法回溯 | 币安 K 线虽然历史很长，但反复拉同一段是纯浪费 |

**本仓库没有内存态的 K 线缓存子系统**（没有 `engine/candles*.go`）。唯一的持久化路径是数据库，实现在 `exchanges/kline/kline_datastorage.go`：

```go
func LoadFromDatabase(exch string, pair currency.Pair, a asset.Item, interval Interval, start, end time.Time) (*Item, error)  // l.15
func StoreInDatabase(in *Item, force bool) (uint64, error)                                                                    // l.55
```

数据库模型在 `database/models/{postgres,sqlite3}/candle.go`，仓储层 `database/repository/candle/candle.go`。

## 6. 启用 DataHistoryManager

这是负责"把你指定时间区间内的 K 线/成交同步到数据库"的子系统（`engine/datahistory_manager.md:26-56`）。

### 6.1 配置

```json
"dataHistoryManager": {
  "enabled": true,
  "checkInterval": 60000000000,
  "maxJobsPerCycle": 5,
  "maxResultInsertions": 0,
  "verbose": false
}
```

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `false` | 必须开 |
| `checkInterval` | 1 分钟 | 调度轮询间隔（纳秒） |
| `maxJobsPerCycle` | 5 | 每轮最多处理几个任务 |
| `maxResultInsertions` | 0（= 用代码默认 10000） | 单次最多插入多少行 |
| `verbose` | `false` | 打印任务细节 |

结构 `config/config_types.go:139-145`，默认值在 `engine/datahistory_manager_types.go:112-124`：`defaultDataHistoryMaxJobsPerCycle=5`、`defaultMaxResultInsertions=10000`、`defaultDataHistoryBatchLimit=3`、`defaultDataHistoryRetryAttempts=3`、`defaultDataHistoryRequestSizeLimit=500`。

也可以用命令行开（会强制 dry-run）：

```bash
./gocryptotrader -datahistorymanager -connectivitymonitor=false
```

或者运行时开：

```bash
gctcli enablesubsystem --subsystem data_history_manager
```

**依赖数据库子系统**。数据库没开的话它会起不来。

### 6.2 任务类型

`DataHistoryJob.DataType` 支持（`engine/datahistory_manager_types.go:26-33`）：

1. 拉 K 线（candles）
2. 拉成交（trades）
3. 成交 → K 线转换
4. **K 线 → K 线转换**（比如用 1m 合成 5m、1h；走 `Item.ConvertToNewInterval`）
5. K 线数据校验
6. 用第二个交易所的数据交叉校验

任务状态（l.36-43）：`active`、`failed`、`complete`、`removed`、`issues-found`、`paused`。

### 6.3 创建任务

用 gctcli（`cmd/gctcli/data_history.go`）：

```bash

  --nickname=binance-usdtm-btc-1h \
  --exchange=binance \
  --asset=usdtmarginedfutures \
  --pair=BTC-USDT \
  --interval=3600 \
  --start_date="2025-01-01 00:00:00" \
  --end_date="2026-01-01 00:00:00" \
  --request_size_limit=500 \
  --max_retry_attempts=3 \
  --batch_size=3
```

参数说明：

| 参数 | 说明 |
| --- | --- |
| `--nickname` | 任务名，后续查询/状态变更都用它 |
| `--interval` | 秒。3600 = 1 小时 |
| `--start_date` / `--end_date` | `time.DateTime` 格式，UTC |
| `--request_size_limit` | 单次 API 请求拉多少根，最大 1000（币安限制） |
| `--batch_size` | 并发批次数，默认 3 |
| `--max_retry_attempts` | 失败重试次数，默认 3 |

`DataHistoryJob` 结构体的全部字段（`engine/datahistory_manager_types.go:148-174`）：`ID, Nickname, Exchange, Asset, Pair, StartDate, EndDate, Interval, RunBatchLimit, RequestSizeLimit, DataType, MaxRetryAttempts, Status, Results, OverwriteExistingData, ConversionInterval, DecimalPlaceComparison, SecondaryExchangeSource, IssueTolerancePercentage, ReplaceOnIssue, PrerequisiteJobID/Nickname`。

## 10. K 线数据结构

存进库和从 API 拿的都是同一个结构（`exchanges/kline/kline_types.go`）：

```go
type Item struct {                        // l.130-140
    Exchange        string
    Pair            currency.Pair
    UnderlyingPair  currency.Pair
    Asset           asset.Item
    Interval        Interval
    Candles         []Candle
    SourceJobID     uuid.UUID
    ValidationJobID uuid.UUID
}

type Candle struct {                      // l.142-152
    Time             time.Time
    Open             float64
    High             float64
    Low              float64
    Close            float64
    Volume           float64
    QuoteVolume      float64
    ValidationIssues string
}
```

`Interval` 是 `time.Duration` 的别名类型（l.179），JSON 里可以是纳秒整数或者 `"1h"` / `"15m"` / `"1M"`（月）这种文本（`UnmarshalJSON`，`kline.go:235`；`ParseInterval(text string) (Interval, error)`，`kline.go:313`）。

时间**一律 UTC**（`FormatDates()` 强制 `.UTC()`，`kline.go:428`；`alignIntervalStart` 按间隔截断，`kline.go:159`；月/年这种日历间隔锚定到真实 UTC 月界，`calendarIntervalMonths` l.140）。

常用工具方法：

| 方法 | 位置 | 作用 |
| --- | --- | --- |
| `RemoveDuplicates()` | `kline.go:390` | 按 `Time.Unix()` 去重 |
| `RemoveOutsideRange(start, end)` | `kline.go:407` | 裁掉区间外的 |
| `SortCandlesByTimestamp(desc bool)` | `kline.go:419` | 排序 |
| `FormatDates()` | `kline.go:428` | 转 UTC |
| `addPadding(start, exclusiveEnd, purgeOnPartial)` | `kline.go:330` | 缺口补零 K 线 |
| `ConvertToNewInterval(newInterval)` | `kline.go:528` | **升采样**（1m → 1h） |
| `GetClosePriceAtTime(t)` | `kline.go:697` | 取某时刻收盘价 |
| `EqualSource(i *Item)` | `kline.go:795` | 校验两个 Item 是否同源 |
| `TotalCandlesPerInterval(start, end, interval)` | `kline.go:503` | 算区间内应有多少根 |
| `CalculateCandleDateRanges(start, end, interval, limit)` | `kline.go:622` | 按 API 上限切分请求批次 |

`ConvertToNewInterval` 的约束：**只能升采样**（`newInterval > k.Interval`）、必须是整数倍（`newInterval % k.Interval == 0`）、输入必须已完整填充（否则 `errCandleDataNotPadded`）、末尾不完整的组会被丢弃。

### 11.1 实测记录（2026-10-10，PostgreSQL 17.11）

上面三步在本机实测走通过，附实测细节与两个坑：

**起 Postgres 有两条路，都不必用 `docker run` 手敲**：

```bash
# A. 仓库已提供 compose 服务（本会话新增，只监听回环）
docker compose up -d postgres        # postgres:17-alpine，127.0.0.1:5432，库/用户/密码都是 gocryptotrader

# B. 本机原生 Postgres（Homebrew 装过 postgresql@17 时最省事，且完全不碰已有实例）
initdb -D /tmp/gct-pg -U gct --auth=trust
pg_ctl -D /tmp/gct-pg -o "-p 55432 -k /tmp/gct-pg -c listen_addresses=127.0.0.1" -l /tmp/gct-pg/pg.log start
createdb -h 127.0.0.1 -p 55432 -U gct gocryptotrader
```

`initdb` 在 macOS 上需要 `LC_ALL`（未设时报 collation 错）。

**跑迁移**：`dbmigrate` 要指定配置文件才会连 Postgres——

```bash
cd cmd/dbmigrate && ../../dbmigrate -config /tmp/pg-config.json -command up
```

实测结果：**10 个迁移全部 `OK`**（含 8 个 LLM 迁移 + 1 个触发器迁移），`current version: 20261010120800`；建出 **24 张 `llm_*` 表 + 20 个触发器 + 2 个 plpgsql 函数**。方言翻译核对无误：`TIMESTAMPTZ` / `BOOLEAN` / `BYTEA` 都按预期落地。

**⚠ 坑 1：Postgres 真的会校验外键，SQLite 默认不校验。** 在 SQLite 上"能插进去"的测试夹具，在 Postgres 上会因 FK 失败——必须先插父行（`llm_provider_profiles` → `..._revisions`、`llm_strategies` → `..._versions`、`llm_decision_runs` → `llm_risk_evaluations` → `llm_order_intents`）。**同一个故障（触发器没生效）会表现为两种完全不同的错误**（sqlite 静默放行 / pg 报 FK），只测一种方言会漏。

**⚠ 坑 2：`psql -f` 默认不因错误中止。** 夹具插入失败后，后续断言会**在空表上跑**并全部"通过"（`UPDATE 0`）。测触发器行为时必须确认**表里有行**，例如先 `select count(*)`，或把断言包在 `DO`/函数里把异常转成可读文本（本会话用的就是这个办法，见 `taskProgress/workLog/2026-10-10-session-17-postgres-provisioning.md`）。

**触发器行为在 pg 上实测通过**：18 条断言全过——10 条"必须被拒"（含 3 条**置 NULL 逃逸**用例，靠 `IS DISTINCT FROM` 拦住）、3 条"必须放行"（撤销/生命周期/结算）、5 条冻结门控（冻结本身放行、`state` 流转放行、3 种冻结列改动被拒）。`-command down` 也验过：触发器与函数清空、表保留。

## 12. 常见错误

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| `Database support is disabled` | `database.enabled=false` | 改成 `true` 并重启 |
| `no such table: candle` | 没跑迁移 | `cd cmd/dbmigrate && go run . -command up` |
| 迁移报找不到目录 | 不在 `cmd/dbmigrate` 下运行 | `MigrationDir` 是相对路径 `../../database/migrations` |
| 任务一直 `active` 不推进 | DataHistoryManager 没启用 | 配置 `enabled: true` 或 `-datahistorymanager` |
| 任务 `failed`，日志说交易对不存在 | 没跑 dbseed | `cd cmd/dbseed && go run .` |
| `kline.ErrRequestExceedsExchangeLimits` | 单次请求区间超过 1000 根 | 用 `Extended` 版本，或减小 `--request_size_limit` |
| `errCandleDataNotPadded` | 对未填充的数据做 interval 转换 | 先用 `Extended` 拉全（会自动 `addPadding`） |
