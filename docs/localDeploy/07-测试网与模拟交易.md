# 07 测试网与模拟交易

在真钱下单之前，有四层由轻到重的验证手段。本文按推荐顺序讲。

## 1. 四层验证手段总览

| 层级 | 手段 | 打真实交易所 | 需要 API Key | 产生真实订单 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| L1 | `-dryrun` | ✅ | ✅ | ❌（配置不回写） | 改配置后先试跑 |
| L2 | `SubmitFakeOrder`（**仅 Go 代码可调**） | ❌ | ❌ | ❌（只入本地库） | 验证订单参数和风控逻辑 |
| L3 | 币安合约测试网 | ✅（测试网） | ✅（测试网 Key） | ✅（测试网） | **验证完整下单链路** |
| L4 | 主网小额 | ✅ | ✅ | ✅ | 最终验收 |

**L3 是最有价值的一层**：测试网的接口行为和主网一致，能真正验证签名、精度、杠杆、保证金模式、reduce-only 这些细节，但资金是假的。

## 2. L1：dry-run

```bash
./gocryptotrader -dryrun -connectivitymonitor=false
```

`-dryrun` 的语义（`main.go:35` 的帮助文本原文）：**"dry runs bot, doesn't save config file"**。

也就是说它**只阻止配置回写**，不阻止下单。`submitorder` 照样会打真实 API。别把它当模拟交易用。

### 2.1 会隐式触发 dry-run 的 flag

`engine/engine.go:927-937` 的 `dryRunParamInteraction` 列出了这些 flag，设了就进 dry-run（在 `engine.go:942-971` 应用）：

```text
-enableallpairs
-enableallexchanges
-exchangeverbose
-exchangewebsocketsupport
-exchangeautopairupdates
-exchangedisableautopairupdates
-httpuseragent
-httpproxy
-httptimeout
-exchangehttpdebugging
-exchanges
```

外加 `-datadir`（`engine/engine.go:137-144`，日志会打 `Command line argument '-datadir' induces dry run mode.`）。

后果是：运行时通过 gctcli 改的配置（比如 `setexchangepair`）**不会持久化**，重启就丢。开发期通常无所谓，但要知道。

## 3. L2：纸面下单

### 3.1 先破除一个误解：`simulateorder` 不是纸面下单

> ⚠ **实测更正：`simulateorder` 不能用于永续合约，也不是纸面下单。**
> `SimulateOrder` 的 handler（`engine/rpcserver.go`）里**硬编码了 `asset.Spot`** 两次
> （`checkParams(r.Exchange, exch, asset.Spot, p)` 和 `GetCachedOrderbook(p, asset.Spot)`），
> 而 `SimulateOrderRequest` proto 里根本没有 `asset_type` 字段。关掉现货后调用会直接报：
> `rpc error: code = Unknown desc = spot asset type not enabled`。
> 而且它调的是 `orderbook.SimulateOrder(amount, buy)`，返回的是**盘口成交档位和最高/最低价**，
> 本质是**盘口冲击模拟器**（等价于 `orderbook buy/sell`），从来不调 `SubmitFakeOrder`。

所以本文说的 L2 指的是 **`OrderManager.SubmitFakeOrder`**，它**没有 RPC / gctcli / REST 入口**，
只能从 Go 代码里调用（回测器和本方案设计的 LLMManager 都是这么用的）。

想在命令行做"不花钱的下单演练"，现实可用的替代是：

```bash
# 盘口冲击 / 滑点估算（支持 --asset，永续可用）
gctcli orderbook buy quote --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures --amount 1000
gctcli orderbook whalebomb --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures --side BUY --price 90000

# 挂一个远离市价的限价单验证参数合法性，然后立刻撤掉（会产生真实挂单，但不成交）
gctcli submitorder --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures \
  --side BUY --type LIMIT --amount 0.001 --price 30000 --client_id param-check-001
gctcli cancelorder --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures \
  --orderid <上一步返回的订单号> --side BUY --type LIMIT --amount 0.001 --price 30000
```

> 注意 BTC-USDT 永续的 `MIN_NOTIONAL` 实测是 **50 USDT**，`stepSize` 是 **0.001**。
> 0.001 BTC 在 8 万价位约 80 USDT，满足最小名义额；但价格 30000 距离市价太远，
> 币安可能因超出价格保护范围拒单——这本身就是有价值的参数校验。

### 3.2 `SubmitFakeOrder` 做了什么

`OrderManager.SubmitFakeOrder`（`engine/order_manager.go:529`）：

```go
func (m *OrderManager) SubmitFakeOrder(newOrder *order.Submit, resultingOrder *order.SubmitResponse, checkExchangeLimits bool) (*OrderSubmitResponse, error)
// engine/order_manager.go:529
```

跟真实 `Submit`（l.478）的区别：

| 步骤 | `Submit` | `SubmitFakeOrder` |
| --- | --- | --- |
| `m.validate` | ✅ | ✅ |
| `CheckOrderExecutionLimits` | ✅ | 可选（`checkExchangeLimits` 参数） |
| `CanTradePair` | ✅ | ✅ |
| **调交易所 API** | ✅ | **❌** |
| 存 `order.Detail` | ✅ | ✅ |
| `TrackNewOrder` 更新本地仓位 | ✅ | ✅ |

所以它能验证：订单参数合法性、数量/价格精度、交易对白名单、币种状态、本地仓位跟踪。**不能**验证：币安侧的真实拒单原因（保证金不足、杠杆不匹配、持仓模式冲突）。

### 3.4 回测器用的就是这套

`backtester/eventhandlers/exchange/exchange.go:360-375` 的 `placeOrder`：

```go
useRealOrders ? orderManager.Submit : orderManager.SubmitFakeOrder
```

`useRealOrders` 来自策略配置的 `LiveData.RealOrders`（`backtester/config/strategyconfig_types.go:192-206`）。这是**在本地跑策略而不花钱**的官方路径，也是唯一现成可用的 `SubmitFakeOrder` 调用方。

> **对 `docs/llm-dev` 方案的影响**：`PAPER` 模式必须由新增的 LLMManager 子系统**在进程内直接调**
> `OrderManager.SubmitFakeOrder`，不能指望复用 RPC。方案里 ExecutionGateway 的设计正是如此
> （见 `docs/llm-dev/07-策略与自动决策引擎.md` §6.2），这条实测结论验证了该设计是必需的而非可选的。

### 3.5 盘口冲击模拟

```bash
gctcli orderbook whalebomb --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures \
  --side BUY --target 100000
```

对应 RPC `WhaleBomb`（`gctrpc/rpc.proto:1656`），基于当前盘口算大单的滑点影响。做仓位规模决策时很有用。

## 4. L3：币安合约测试网

### 4.1 为什么不能用 useSandbox

`config.Exchange` 结构里确实有 `useSandbox` 字段（`config/config_types.go:186`），但**全仓库只有 Gemini 读它**（`exchanges/gemini/gemini_wrapper.go:130`）。币安 wrapper 里没有任何 `useSandbox` 处理。设了只会通过 RPC `GetExchangeInfo` 回显一下（`engine/rpcserver.go:390`），不改变实际端点。

币安的测试网 URL 在代码里是**未被使用的常量**（`exchanges/binance/binance.go:40-41`）：

```go
testnetSpotURL = "https://testnet.binance.vision/api" //nolint:unused // Can be used for testing via setting useTestNet to true
testnetFutures = "https://testnet.binancefuture.com"  //nolint:unused // Can be used for testing via setting useTestNet to true
```

两个都带 `//nolint:unused`，说明代码里没引用。

### 4.2 正确做法：覆盖 urlEndpoints

改 `config.json` 里 Binance 条目的 `api.urlEndpoints.RestUSDTMarginedFuturesURL`：

```json
"api": {
  "authenticatedSupport": true,
  "authenticatedWebsocketApiSupport": false,
  "credentials": {
    "key": "测试网的KEY",
    "secret": "测试网的SECRET"
  },
  "credentialsValidator": { "requiresKey": true, "requiresSecret": true },
  "urlEndpoints": {
    "RestUSDTMarginedFuturesURL": "https://testnet.binancefuture.com",
    "RestSpotURL": "https://sapi.binance.com",
    "RestSpotSupplementaryURL": "https://api.binance.com",
    "RestCoinMarginedFuturesURL": "https://dapi.binance.com",
    "EdgeCase1URL": "https://www.binance.com",
    "WebsocketSpotURL": "wss://stream.binance.com:9443/stream"
  }
}
```

基础层的 `SetAPIURL()`（`exchanges/exchange.go:793+`）会应用这个覆盖，并打一条警告：

```text
Config is overwriting default endpoint URL values from https://fapi.binance.com to https://testnet.binancefuture.com
```

**看到这条警告就说明切换成功了。** 如果启动时没有这条警告，说明你在打主网。

### 4.3 建议维护两份配置

```bash
cp ~/.gocryptotrader/config.json ~/.gocryptotrader/config.testnet.json
# 编辑 config.testnet.json：改 urlEndpoints + 换测试网 Key
```

用 `-datadir` 或 `-config` 切换。注意 `-datadir` 会触发 dry-run；`-config` 不会：

```bash
# 推荐：用 -config 指定不同配置文件（不触发 dry-run）
./gocryptotrader -config ~/.gocryptotrader/config.testnet.json -connectivitymonitor=false
```

但配置查找顺序（`config/config.go:1366-1395`）里，`<可执行文件目录>/config.json` 优先级最高。用 `-config` 显式指定可以绕过这个逻辑。

### 4.4 测试网已知差异

| 项 | 主网 | 测试网 |
| --- | --- | --- |
| 资金 | 真实 USDT | 免费领取的模拟 USDT |
| 交易对数量 | 300+ | 明显更少，很多小币种没有 |
| 流动性/盘口 | 真实 | 很薄，滑点大，限价单可能长期不成交 |
| K 线历史 | 完整 | 较短 |
| 资金费率 | 真实市场博弈 | 可能是固定值或不结算 |
| WebSocket | 有（现货） | 本项目不接 |
| 限频 | 2400 weight/min | 通常更宽松 |

**交易对可用性是最大的坑**：如果配置里 `enabled` 写了 `BTC_USDT` 之外的合约而测试网没有，启动时 `autoPairUpdates` 会把它从 `available` 里剔掉，后续操作报"交易对未启用"。测试网建议只留 `BTC_USDT` 和 `ETH_USDT`。

测试网 K 线历史短，做 MACD（需要 ≥33 根）之类的指标时把 `--granularity` 调小或缩短 `--start`。

### 4.5 测试网完整验收清单

```bash
# 0. 确认端点已切到测试网（启动日志里应有 overwriting 警告）
gctcli getexchangeinfo --exchange Binance

# 1. 公共接口
gctcli getticker --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures

# 2. 鉴权接口（验证测试网 Key）
gctcli getaccountbalances --exchange Binance --asset usdtmarginedfutures

# 3. 持仓模式设为单向
gctcli futures getcollateralmode --exchange Binance --asset usdtmarginedfutures
gctcli futures setcollateralmode --exchange Binance --asset usdtmarginedfutures --collateralmode one_way

# 4. 保证金模式 + 杠杆
gctcli futures setmargintype --exchange Binance --asset usdtmarginedfutures --pair BTC-USDT --margintype isolated
gctcli futures setleverage --exchange Binance --asset usdtmarginedfutures --pair BTC-USDT --leverage 3 --margintype isolated
gctcli futures getleverage --exchange Binance --asset usdtmarginedfutures --pair BTC-USDT

# 5. 限价开多
gctcli submitorder --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures \
  --side BUY --type LIMIT --amount 0.001 --price <当前价-1%> --client_id testnet-long-001

# 6. 查订单
gctcli getorders --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures
gctcli getmanagedorders --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures

# 7. 撤单
gctcli cancelorder --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures \
  --orderid <订单号> --side BUY --type LIMIT --amount 0.001 --price <同上>

# 8. 市价开多（必然成交）
gctcli submitorder --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures \
  --side BUY --type MARKET --amount 0.001 --client_id testnet-long-002

# 9. 查仓位（等 10 秒让订单管理器同步一轮）
gctcli futures getmanagedposition --exchange Binance --asset usdtmarginedfutures --pair BTC-USDT
gctcli futures getfuturespositionsummary --exchange Binance --asset usdtmarginedfutures --pair BTC-USDT

# 10. 市价平仓
gctcli submitorder --exchange Binance --pair BTC-USDT --asset usdtmarginedfutures \
  --side SELL --type MARKET --amount 0.001 --client_id testnet-close-001

# 11. 确认已平 + 看盈亏
gctcli futures getallmanagedpositions
gctcli getaccountbalances --exchange Binance --asset usdtmarginedfutures

# 12. 资金费率
gctcli futures getlatestfundingrate --exchange Binance --asset usdtmarginedfutures --pair BTC-USDT
gctcli futures getfundingrates --exchange Binance --asset usdtmarginedfutures --pair BTC-USDT \
  --startdate "2026-01-01 00:00:00" --enddate "2026-02-01 00:00:00"

# 13. K 线与指标
gctcli gethistoriccandlesextended --exchange Binance --pair BTC-USDT \
  --asset usdtmarginedfutures --interval 3600 \
  --start "2026-01-01 00:00:00" --end "2026-02-01 00:00:00" --sync=true
gctcli technicalanalysis macd --exchange Binance --pair BTC-USDT \
  --asset usdtmarginedfutures --granularity 3600
```

13 步全过 = 下单链路完整可用，可以上主网小额。

## 5. L4：主网小额

切回主网：把 `RestUSDTMarginedFuturesURL` 改回 `https://fapi.binance.com`，换回主网 Key，重启。**确认启动日志里没有 overwriting 警告**。

第一次真单的建议：

1. 杠杆设 1 倍（`--leverage 1`），逐仓
2. 数量取该合约的最小步长（`curl -s "https://fapi.binance.com/fapi/v1/exchangeInfo?symbol=BTCUSDT" | jq '.symbols[0].filters'` 查 `LOT_SIZE`）
3. 先挂一个远离市价的限价单，确认能挂上、能撤掉
4. 再下一笔最小额市价单，确认能成交、仓位能查到、能平掉
5. 全程盯日志，看有没有意外的告警

## 6. 订单管理器自带的风控

`orderManagerConfig`（`engine/order_manager_types.go:34-42`）里有这些字段：

```go
EnforceLimitConfig, AllowMarketOrders, CancelOrdersOnShutdown bool
LimitAmount float64
AllowedPairs currency.Pairs
AllowedExchanges []string
OrderSubmissionRetries int64
```

在 `validate`（`engine/order_manager.go:385-402`）里生效：拒绝市价单（若 `!AllowMarketOrders`）、拒绝超过 `LimitAmount` 的数量、检查交易所和交易对白名单。

**但有个重要 caveat**：`SetupOrderManager` 只从 `config.OrderManager` 里接了 `CancelOrdersOnShutdown` 这一个字段（`engine/order_manager.go:61-63`）。`config.OrderManager`（`config/config_types.go:129-136`）在当前版本里**没有对应的 limit 配置段**，所以这些限额字段目前恒为零值、处于休眠状态。也**没有 `maxOrdersPerCycle` 这个配置键**。

结论：**不要指望配置能帮你限制下单金额**。要么在代码层自己加校验，要么靠币安侧的 API Key 权限和账户余额做硬约束。这一点在 `docs/llm-dev` 的自动决策方案里是必须自建的一层。

真正生效的交易所侧约束：

- `CheckOrderExecutionLimits(a, cp, price, amount, orderType)` —— 最小/最大数量、价格精度（`exchange/order/limits.MinMaxLevel`，由 `UpdateOrderExecutionLimits` 刷新，`exchanges/interfaces.go:87-89`）
- `CanTradePair(pair, asset)` —— 币种状态 halt（CurrencyStateManager，`interfaces.go:136`）

## 7. 关闭时撤单

```json
"orderManager": { "cancelOrdersOnShutdown": true }
```

开启后 `Engine.Stop` 会调 `OrderManager.CancelAllOrders(ctx, exchanges)`（`engine/order_manager.go:148`）。每个交易所最多等 10 秒（`-exchangeshutdowntimeout`，默认 `time.Second*10`）。

跑自动化策略时建议开，避免程序挂了还留着一堆挂单。

## 8. 通知

想让每次下单成功/失败推消息，配 Telegram：

```json
"communications": {
  "telegram": {
    "enabled": true,
    "verbose": false,
    "token": "你的bot token",
    "targetChat": 你的chatID,
    "proxy": "socks5://127.0.0.1:7890",
    "timeout": 6000000000,
    "requireConfirmation": false
  }
}
```

订单管理器已经在推事件（`engine/order_manager.go:449-452` 成功、`469-472` 失败，`base.Event{Type: "order", Message: ...}`），走 `CommunicationsManager.PushEvent`（`engine/communication_manager.go:87`）。

支持的通道（`communications/`）：Telegram、SMTP、Slack、SMSGlobal。**没有通用 webhook**。

`requireConfirmation: true` 会让通知变成需要确认的交互（Telegram 按钮），自动化场景设 `false`。
